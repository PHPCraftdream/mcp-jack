# mcp-jack threat model

**Status and evidence boundary.** Static analysis of checked-in protocol, SDK and Go CLI source in this worktree; not a runtime assessment, audit, release approval, or claim that tests/CI ran here. Current protocol text is draft v0.1 and not frozen. The owner-selected D2/D3 directions and candidate requirements below are future work, not current protections. PR #22 delivered the design baseline after 32 successful PR checks and six successful post-merge workflows. Main ancestry and source-preserving cleanup were verified. Those receipts do not establish candidate/runtime acceptance.

## Purpose and security objectives

mcp-jack authenticates each HTTP request and response, checks freshness and replay, offers protocol-native user administration, and hands verified caller identity to the wrapped MCP handler. Signatures do not provide confidentiality. TLS is required for non-loopback connections and supplies transport confidentiality/certificate validation. Ordinary authenticated MCP is passed through; authorization for it is application-owned. The protocol `admin` flag gates only reserved native administrative tools ([01](../spec/01-authentication.md), [02](../spec/02-authorization.md)).

A client independently configures its endpoint, audience and server public-key pin. First-server trust is out of band; a credential's embedded server key is data, not a trust root. Current profiles use one static server pin. User-key rotation (`jack.key.rotate`) changes a user key and is not server response-key rotation.

Owner-selected future directions, explicitly **not implemented**:

- **D2 restart/replay:** durably reserve an authenticated `(kid, nonce)` before native authorization/state mutation or handler dispatch. Unknown durable-write outcome fails closed; never automatically retry. A timestamp startup floor is rejected as the selected remedy. Current SDK/server and CLI gateway nonce stores remain in memory.
- **D3 server response-key rotation:** owner direction permits arbitrarily many pending announcements without a one-pending rule or cooldown; the OLD key remains in use until NEW takes over 48 hours after announcement. This is direction, not a normative contract.

Candidate technical defaults for D3—not additional owner decisions—express each announcement with a fixed logical publication time `P_i` and activation `A_i=P_i+172800`; a key's response interval ends at its successor's activation, and ordinal ties may leave an empty intermediate interval. The candidate's logical publication-authorization anchor is not first physical visibility; it does not promise 48 hours from first delivery. Strict cutoff at a known successor and the suppressed-suffix limitation are likewise candidate choices. No server response-key rotation is implemented; there is no automatic on-connect or periodic refresh. See [candidate index](../spec/candidate/README.md), [D2](../spec/candidate/durable-nonces.md), [D3](../spec/candidate/server-key-rotation.md), and [protocol transition policy](protocol-transition.md).

## Assets and trust boundaries

- Client user private keys and signer access; server response-signing private key and custody; public server pin and endpoint/audience configuration.
- Registry entries (public keys, names, admin flags and validity intervals), invitation records and one-time invite codes; first-admin bootstrap authority.
- Exact request/response bytes, authenticated caller identity, application data and availability. Message signatures protect only their specified fields, not secrecy.
- Nonce state and clocks; audit events and their optional sink; local profiles and imported credentials.
- CLI configuration, local key/state files, gateway-to-upstream Unix socket, bridge stdio frames and process lifecycle.

Actors include clients/users, server operator, network attacker, wrapped MCP application/upstream, local host/process and signer. A key proves key possession, not that a human or agent is safe or entitled to an ordinary tool. Host, signer, trusted configuration, filesystem and local process compromise are not prevented by message signatures. The application must enforce its own ordinary MCP authorization.

Server compares configured audience, not `Host`. Endpoint routing and TLS still matter. |
| Response authentication | Signature binds status, corresponding request signature, server `kid`, timestamp and exact response-body hash. Client verifies configured pin, freshness, signature and body. | Response headers are not signed. Do not infer integrity for cookies, `Location`, session metadata or other headers. |
| TLS and destinations | Spec requires HTTPS off loopback. SDK URL policies reject selected malformed/insecure destinations. ## Inferred attacks and future acceptance candidates

These are plausible risks at named trust boundaries, not observed incidents or proof of exploitability. Checks below are candidate CI/release acceptance, not tests currently present or run.

### Restart replay and durable-state failure (D2)

The selected mechanism is authenticated durable nonce reservation before native authorization, state mutation or wrapped-handler dispatch. Unknown outcome fails closed with no automatic retry. The current Go, Rust and TypeScript stores and CLI gateway remain in-memory, so this protection is not implemented. A timestamp-startup floor is rejected; `ts < server_start` does not cover same-second or previously accepted future timestamps. The design requires a confirmed durable receipt for the exact authenticated request before any dispatch; a definite noncommit or unknown outcome must not dispatch. Persisted high-water/expiry, owner exclusion, corrupt/missing state, recovery, unknown-outcome fencing and migration from volatile history require independent review and backend evidence. Current `server/statefile.go` registry persistence is not nonce history.

Candidate acceptance should distinguish replay across restart, concurrent duplicate reservation, inclusive expiry equality and +1, delayed crypto/freshness recheck, invalid-signature zero-write, storage-full behavior, definite/unknown commit failures, clock rollback, old volatile history, crash before/after commit, and refused dispatch after committed reservation. Test handler non-redelivery, but do not claim exactly-once application effects. bbolt v1.5.0 is the proposed Go backend candidate following parent source inspection, not an added dependency, selected production adapter or qualified durability guarantee. The Go 1.25 floor is approved for the whole Go SDK/CLI but the checked-in `go.mod` remains 1.22; migration/CI adaptation and actual adapter/filesystem/crash/dependency qualification remain. Rust is at 1.88 in source; TypeScript stays Node 20/22.

### Server response-key compromise, suppression and transition (D3)

Current clients trust one statically configured server key; server response signing uses one configured key. Rotation is not implemented. A compromised currently trusted key can authorize a malicious successor in a chained scheme; next-key possession proves control of that key, not an independent root. Suppressed announcements leave clients that have not learned a successor unable to authenticate its response. Unknown signing keys must fail closed; there is no TOFU, fallback or trust from an unsigned header/body. Static profiles/pins and credentials are unchanged until a separately approved transition.

The selected D3 direction permits arbitrarily many pending announcements without a one-pending rule or cooldown; OLD remains in use until NEW takes over 48 hours after announcement. Candidate technical defaults—logical publication-time anchor, successor cutoff, ordinal tie behavior (including empty intervals), strict client cutoff and suppressed-suffix behavior—are not literal owner decisions. The candidate logical publication-authorization time is not first physical visibility and provides no 48-hour first-delivery guarantee. These behaviors remain non-normative; no automatic connect-time or periodic refresh, fallback or TOFU is selected.

Candidate acceptance should cover multiple pending records, out-of-order/duplicate/conflicting records, same-second tie, empty intervals, exact activation/cutoff boundaries, delayed receipt, restart without timer reset, OLD-until-switch, NEW-after-switch, wrong prior key/proof/audience/binding, unknown outer key, tampering, missing suffix and OOB recovery. The strict final cutoff can reject an old-key response at equality even when it was signed before the cutoff; a client that has not received a successor cannot know the eventual upper bound. No automatic connection or periodic refresh is selected. No receipt/restart timer reset. The detailed candidate's codec, storage, final-gate and delivery requirements must not be presented as implemented.

### Authentication, refusal and persistence boundaries

The current server verification order is header syntax/version, key resolution/active interval, inclusive freshness, signature verification, nonce check/record, then body classification, native authorization or handler dispatch. This means unauthenticated failures do not consume a nonce, while an authenticated admin/shape/dispatch refusal does. Go middleware signs a refusal only when it has a recorded nonce and request signature; pre-auth failures may be unsigned. The Go client buffers responses to 1 MiB, verifies the configured static pin, and treats a missing-auth HTTP 401 as status-only without parsing its body. Do not generalize this special case to malformed auth or other statuses, and do not trust unsigned bodies/headers as retry instructions.

Go `FileState` uses a same-directory temporary file, file sync, rename and then in-memory state replacement for registry/invite edits. This is not D2 nonce history, cross-file ACID, or proof of directory metadata/power-loss durability. Its mutex is per state object. Go audit `Record` errors are ignored by the verifier; audit sink delivery is not a transaction or proof of application effect.

### Gateway/upstream identity and MCP compatibility

A caller can try spoofing identity headers, reach an upstream outside the gateway, or exploit a misconfigured trusted hop. The gateway implementation creates identity headers from the SDK's verified identity and only forwards selected headers; the configured Unix socket and loopback bind constrain this implementation. Deployment must still keep the upstream private and trust identity headers only on that hop. Recheck when config/implementation evolves; do not describe a future design as current. The checked-in gateway uses a bounded legacy Streamable HTTP 2025-11-25 profile, not general MCP compatibility. `docs/design/mcp-compatibility.md` is source research and future acceptance design, not runtime evidence. The existing Jack 3×3 interop and credential-transfer matrices are distinct from proposed official MCP client × bridge × gateway × server tests.

Future integration checks should forge inbound identity headers, verify they are not forwarded as authority, inspect exact allowlisted headers and protected socket routing, test direct-upstream bypass assumptions and configured-target escape, and exercise supported protocol version/session/framing behavior with official SDKs. Do not claim all clients, servers, streams, sessions, or modern MCP profiles are supported based on source presence.

### Unsigned metadata, wrong endpoint and credentials

Signatures cover defined request/response fields, not all headers. An intermediary could alter an unsigned header; TLS and endpoint validation remain necessary. Go URL policy does not perform DNS resolution; caller-supplied transports can alter trust. A credential's embedded server tuple must not replace independent configuration. Import should continue to reject any mismatch against expected URL/audience/pin without silently mutating a pin/profile. Test unsigned 401 bodies containing misleading instructions and prove clients do not parse/act on them; verify malformed auth is not treated as absent-auth fallback. Test signed-field tampering separately from unsigned-header changes.

### Admin misuse, stolen keys and prompt injection

A stolen user key acts as that identity; a stolen admin key can administer users and invites. Caller-supplied admin fields/headers do not grant privilege; registry identity supplies the snapshot. Ordinary MCP authorization remains application-owned. A valid signature indicates key use, not user intent or approval. Untrusted tool/log content can prompt an agent to request destructive operations; no protocol human-confirmation mechanism exists. Keep useful signer custody, least-privilege and operator guidance. Credential import validates the document before comparing it with the independently trusted exact `{url,aud,server_public_key,server_kid}` tuple; the embedded server key is not its own trust root, and import does not silently update a pin/profile. User-key issuance intentionally hands plaintext credential bytes to the local caller in memory; public user-key identity is distinct from the server response signer. No OS keystore, zeroization, secure delivery or recovery guarantee follows. Candidate checks should cover identity spoofing, admin-only native calls, revocation timing/in-flight snapshot, each expected-identity tuple mismatch, no pin mutation, and secret redaction.

### Resource exhaustion, hangs and local process boundary

Go server adapters cap request/response bodies, but byte limits are not deadlines. A wrapped handler can ignore cancellation or delay; nonce stores have no protocol-defined rate limit. CLI gateway adds timeout, connection/concurrency, rate and cache-count controls, but these are executable bounds, not general SDK guarantees or durable storage. Bridge framing, stdout purity, EOF, blocked pipes, cancellation and backpressure remain sensitive process boundaries even where source contains bounded handling. Candidate acceptance should cover cap and cap+1, slow bodies/upstreams, cancellation, stdout/stderr separation, malformed/truncated frames, bounded queues and no automatic retry of a possibly delivered side effecting request.

## Release status and residual limitations

PR #22 merge, six successful post-merge workflows, and completed cleanup establish delivery of the reviewed design baseline. They do not establish D2/D3 implementation or candidate acceptance. The main generated fixture assets and `spec/tests/CASES.md` were not changed by these docs.

Current residual limitations include: message signatures provide no confidentiality and do not cover arbitrary headers; ordinary MCP authorization belongs to the application; stolen user/admin keys inherit their registry authority; nonce state is in-memory and lost on restart; server response-key rotation is absent; file sync/rename is not a general power-loss guarantee; and optional audit delivery may fail. Static pins and user-key credentials/profiles remain unchanged. No freeze, registry RC, version bump, new dependency, D2/D3 SDK support, independent audit or release readiness is asserted.

No test, build, runtime probe, scan or audit was run for this documentation portion. Local execution was skipped under the owner's no-executable-commands restriction.
