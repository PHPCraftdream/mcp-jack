# mcp-jack threat model

**Status and evidence boundary.** Static analysis of checked-in protocol, SDK and Go CLI source; not a runtime assessment or audit. The protocol is v0.1.x with the durable-nonce + server-key-rotation profile implemented; it becomes normative and wire-frozen for the 0.1.x line only when the freeze is accepted on an exact commit ([protocol transition policy](protocol-transition.md)); the release is not independently audited and nothing is published.

## Purpose and security objectives

mcp-jack authenticates each HTTP request and response, checks freshness and replay, offers protocol-native user administration, and hands verified caller identity to the wrapped MCP handler. Signatures do not provide confidentiality. TLS is required for non-loopback connections and supplies transport confidentiality/certificate validation. Ordinary authenticated MCP is passed through; authorization for it is application-owned. The protocol `admin` flag gates only reserved native administrative tools ([01](../spec/01-authentication.md), [02](../spec/02-authorization.md)).

A client independently configures its endpoint, audience and server public-key pin. First-server trust is out of band; a credential's embedded server key is data, not a trust root. Profiles default to one static server pin; a rotation-enabled client pins the out-of-band anchor (ordinal zero) and accepts only chain-verified successors. User-key rotation (`jack.key.rotate`) changes a user key and is distinct from server response-key rotation.

The implemented D2/D3 model:

- **D2 restart/replay (implemented):** durable authenticated nonce reservation before native authorization, state mutation or handler dispatch. Unknown durable-write outcome fails closed, is never retried, and never dispatches. A timestamp startup floor was evaluated and rejected.
- **D3 server response-key rotation (implemented):** arbitrarily many pending announcements without a one-pending rule or cooldown; one fixed publication time `P` per announced key, sampled once and immutable; activation `A = P + 172800` seconds; OLD signs until `A`; strict client cutoff at the successor activation; explicit single-page client refresh with no hidden retry or reset; durable client ClockGuard against clock rollback; server-side dirty/fence gates. The suppressed-successor limitation is retained: a client that has not learned a successor cannot know the true cutoff.

See [candidate index](../spec/candidate/README.md), [D2](../spec/candidate/durable-nonces.md), and [D3](../spec/candidate/server-key-rotation.md).

## Assets and trust boundaries

- Client user private keys and signer access; server response-signing private key and custody; public server pin and endpoint/audience configuration.
- Registry entries (public keys, names, admin flags and validity intervals), invitation records and one-time invite codes; first-admin bootstrap authority.
- Exact request/response bytes, authenticated caller identity, application data and availability. Message signatures protect only their specified fields, not secrecy.
- Nonce state and clocks; audit events and their optional sink; local profiles and imported credentials.
- CLI configuration, local key/state files, gateway-to-upstream Unix socket, bridge stdio frames and process lifecycle.

Actors include clients/users, server operator, network attacker, wrapped MCP application/upstream, local host/process and signer. A key proves key possession, not that a human or agent is safe or entitled to an ordinary tool. Host, signer, trusted configuration, filesystem and local process compromise are not prevented by message signatures. The application must enforce its own ordinary MCP authorization.

## Inferred attacks and residual risk

These are plausible risks at named trust boundaries, not observed incidents or proof of exploitability.

### Restart replay and durable-state failure (D2)

The durable store reserves an authenticated `(kid, nonce)` in a bbolt-backed store before native authorization, state mutation or wrapped-handler dispatch, and is available to the Go server SDK and the CLI gateway (`durable_nonces` profile). A definite noncommit or unknown outcome fails closed: no dispatch, no automatic retry. A timestamp startup floor was rejected. Rust and TS SDK nonce stores remain in-memory.

What this guarantees: an accepted request's nonce is persisted before dispatch, and an abnormal stop cannot admit an unknown result. What it does not guarantee: no exactly-once application effects (a committed reservation followed by a dispatch failure still consumes the nonce); bbolt v1.5.0 is the shipped backend, but durable private-file stores are Linux-only and Windows stores fail closed by design; dirty or unknown store state keeps every entry point refusing to serve, and recovery is a manual operator procedure; the durable nonce store provides no cross-file ACID with registry state (`server/statefile.go`).

### Server response-key compromise, suppression and transition (D3)

Server response signing supports key rotation. Announcements are hash-linked records; each key is published at one fixed logical time `P`, sampled once and immutable, and activates at `A = P + 172800` seconds. OLD signs until `A`; clients apply a strict cutoff at the successor activation and refresh explicitly (no automatic on-connect or periodic refresh). Clients pin the out-of-band anchor (ordinal zero) and accept only chain-verified successors, with a durable client ClockGuard against clock rollback; servers gate serving on dirty/fence state.

Honest security limits that remain true: a compromised currently-trusted key can authorize a malicious successor — next-key possession is not an independent root. Hash-linked records are local continuity, not global fork prevention. Suppressed announcements leave un-refreshed clients unable to verify a successor's responses. Unknown signing keys fail closed; there is no TOFU, fallback or trust from an unsigned header/body. Static pins are unchanged unless an operator provisions rotation. Backup rollback of clock/trust state is undetectable locally.

### Authentication, refusal and persistence boundaries

The current server verification order is header syntax/version, key resolution/active interval, inclusive freshness, signature verification, nonce check/record, then body classification, native authorization or handler dispatch. This means unauthenticated failures do not consume a nonce, while an authenticated admin/shape/dispatch refusal does. Go middleware signs a refusal only when it has a recorded nonce and request signature; pre-auth failures may be unsigned. The Go client buffers responses to 1 MiB, verifies the configured pin (static or rotation chain), and treats a missing-auth HTTP 401 as status-only without parsing its body. Do not generalize this special case to malformed auth or other statuses, and do not trust unsigned bodies/headers as retry instructions.

Go `FileState` uses a same-directory temporary file, file sync, rename and then in-memory state replacement for registry/invite edits. This is not durable nonce history, cross-file ACID, or proof of directory metadata/power-loss durability. Its mutex is per state object. Go audit `Record` errors are ignored by the verifier; audit sink delivery is best effort and not proof of application effect.

### Gateway/upstream identity and MCP compatibility

A caller can try spoofing identity headers, reach an upstream outside the gateway, or exploit a misconfigured trusted hop. The gateway implementation creates identity headers from the SDK's verified identity and only forwards selected headers; the configured Unix socket and loopback bind constrain this implementation. Deployment must still keep the upstream private and trust identity headers only on that hop. The checked-in gateway uses a bounded legacy Streamable HTTP 2025-11-25 profile: one JSON-RPC object per POST, no sessions, no GET stream — not general MCP compatibility. Upstream SSE answers are unsupported: the gateway closes the stream and answers a signed 501; the official TypeScript MCP server 2.4.0 answers `initialize` with `text/event-stream` even in JSON mode, which is a documented known limit. `docs/design/mcp-compatibility.md` is design research, not runtime evidence. The official-SDK MCP end-to-end CI job exists, but it does not establish support for all clients, servers, streams, sessions or modern MCP profiles.

### Unsigned metadata, wrong endpoint and credentials

Signatures cover defined request/response fields, not all headers. An intermediary could alter an unsigned header; TLS and endpoint validation remain necessary. Go URL policy does not perform DNS resolution; caller-supplied transports can alter trust. A credential's embedded server tuple must not replace independent configuration. Import rejects any mismatch against expected URL/audience/pin without silently mutating a pin/profile. Unsigned 401 bodies must not be parsed or acted on, and malformed auth is not treated as absent-auth fallback. Test signed-field tampering separately from unsigned-header changes.

### Admin misuse, stolen keys and prompt injection

A stolen user key acts as that identity; a stolen admin key can administer users and invites. Caller-supplied admin fields/headers do not grant privilege; registry identity supplies the snapshot. Ordinary MCP authorization remains application-owned. A valid signature indicates key use, not user intent or approval. Untrusted tool/log content can prompt an agent to request destructive operations; no protocol human-confirmation mechanism exists. Keep useful signer custody, least-privilege and operator guidance. Credential import validates the document before comparing it with the independently trusted exact `{url,aud,server_public_key,server_kid}` tuple; the embedded server key is not its own trust root, and import does not silently update a pin/profile. User-key issuance intentionally hands plaintext credential bytes to the local caller in memory; public user-key identity is distinct from the server response signer. No OS keystore, zeroization, secure delivery or recovery guarantee follows.

### Resource exhaustion, hangs and local process boundary

Go server adapters cap request/response bodies, but byte limits are not deadlines. A wrapped handler can ignore cancellation or delay; nonce stores have no protocol-defined rate limit. CLI gateway adds timeout, connection/concurrency, rate and cache-count controls, but these are executable bounds, not general SDK guarantees. Bridge framing, stdout purity, EOF, blocked pipes, cancellation and backpressure remain sensitive process boundaries even where source contains bounded handling. No automatic retry of a possibly delivered side-effecting request exists.

## Release status and residual limitations

The v0.1.x wire profile is not yet declared frozen: that declaration is made at the freeze decision on an exact commit; SDK/API/version decisions remain governed by [versioning](versioning.md). Nothing is published and no release has been made; the work is not independently audited.

Current residual limitations include: message signatures cover defined fields only and provide no confidentiality; ordinary MCP authorization belongs to the application; stolen user/admin keys inherit their registry authority; without the durable profile, nonce state is in-memory and lost on restart — with the profile, stores are durable but recovery after an abnormal stop is manual and serving stays refused until operator action; one owner of nonce/ring state per deployment, no cluster/HA; upstream SSE answers are unsupported (signed 501); Windows CLI stores fail closed; optional audit delivery is best effort; Rust/TypeScript rely on deterministic property/mutation tests plus a shared corpus rather than coverage-guided fuzzing.

Further limitations found by the internal pre-review (see [security review package](security-review-package.md) for all findings and their disposition):

- **Unauthenticated nonce slots.** A request that is self-signed with a key the registry does not know is accepted as far as `jack.enroll` signature verification and reserves a nonce before the invite is checked. The reservation lives until `ts + window`, so unauthenticated traffic can occupy nonce capacity, within the gateway's global admission rate (64 per second) and the 4096-slot capacity. The gateway therefore rejects a durable `window` above 30 seconds. `spec/01-authentication.md` section 4 states this exception and the rule that the request rate times `2 * window + 1` must stay below the cache capacity; whether unknown keys should get a separate budget is open for the external review. Global limits apply before authentication, so heavy unauthenticated traffic can also deny service to everyone: run the gateway behind a rate-limited front.
- **Bridge.** The stdio bridge answers `tools/call` for `jack.*` tools locally and never signs or forwards them, so a stdio client or a prompt-injected agent cannot reach enrollment or administration through the bridge.
- **Clock jumps.** The nonce store, the server key ring and every client trust store keep a high-water mark of the clock. A single forward jump followed by the clock returning latches the store unsafe for good, and 0.1.0 has no recovery command (see the crash recovery runbook in [operations](operations.md)).
- **Cost of rotation.** Each signed response in the rotation profile re-verifies the server-key chain several times, so cost grows with the ring length; rotations are at least 48 hours apart, keep the ring short. Compaction of retired keys is not implemented.
- **Invites.** The gateway stores at most 1024 invites; expired invites are removed when an invite is created, enrolled with or revoked, so only live invites count.
- **Divergence between SDKs.** Go, Rust and TypeScript agree on lone surrogate escapes, nesting depth, GET bodies and the version scheme; the shared corpus covers them. Request-target edge forms (absolute-form, fragment, non-ASCII bytes) are still handled differently, but only a non-conforming client can produce them, except for non-ASCII bytes in the target, which is open for the external review. Only the Go SDK has a durable nonce store.

No test, build, runtime probe, scan or audit was run for this documentation portion; verification happens in the project's CI workflows.
