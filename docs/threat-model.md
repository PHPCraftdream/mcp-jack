# mcp-jack threat model

**Status and evidence boundary.** This is a static threat model for the implemented SDK/protocol surfaces inspected in this worktree, not a runtime assessment, security audit, release approval, or statement that CI is green. The reported HEAD `777771f` adds `docs/release-plan.md` atop main baseline `e681f07`; the release plan is a plan, not approval of its recommendations (`docs/release-plan.md:3-4,40-49`). The owner subsequently approved Go CLI/gateway/bridge scope, chose no version changes yet, and chose an artifact-only RC without publication; see [versioning policy](versioning.md). D-2/D-3 and exact restart/rotation semantics remain unresolved. Server-key rotation, restart replay guard, gateway, bridge, and CLI remain release gaps, not existing protections (`docs/release-plan.md:13-24,26-38`). The current server-key rotation proposal is explicitly unimplemented and non-normative (`docs/design/server-key-rotation.md:1-5`). This document makes no new crypto prescription and does not approve any proposed policy.

## Purpose and security objective

mcp-jack authenticates each HTTP request and response and provides message integrity, freshness/replay checks, protocol user management, and a verified caller identity for the wrapped MCP handler. **These signatures do not provide confidentiality.** TLS is required for non-loopback connections and supplies transport confidentiality and certificate validation; signatures do not replace TLS (`spec/01-authentication.md:7-12`). Authenticated ordinary MCP operations are passed through. The application, not the protocol, decides authorization for those operations; the protocol's `admin` bit gates only reserved `jack.admin.*` tools (`spec/02-authorization.md:4-5,35-50,64-74`).

The trust root for a client is its independently configured endpoint, audience, and server public-key pin. First-server trust is out of band; a credential's embedded server key is not itself trust (`spec/01-authentication.md:113-128`; `docs/design/user-keys.md:133-139`).

## Assets

- Client user private keys and signer access; server response-signing private key.
- Server registry (public keys, names, mutable admin flags and validity intervals), invite records and the one-time invite code at handoff; first-admin bootstrap authority.
- Client's configured endpoint, audience (`aud`) and pinned server key; server's configured `aud` and trust in the connection to the wrapped application.
- Request/response bytes, caller identity, application data and availability. Signatures protect integrity/authentication, not the secrecy of any of these bytes.
- Nonce-cache entries and clocks used for freshness; audit events and the sink that receives them.
- For future, separately approved work: server-rotation continuity state and its acknowledgement/persistence, gateway-to-upstream identity channel, and bridge process framing and secrets. None of these future executable roles exists in the current release plan's implementation (`docs/release-plan.md:17-23,79-89`).

## Actors and trust boundaries

- **Clients and users:** an authenticated user controls its own signing key; an administrator can manage protocol users/invites. A signature proves possession/authority of a key, not that its holder is a human, safe agent, or entitled to a particular ordinary MCP operation.
- **Server operator:** supplies the audience, server signing key, initial registry and out-of-band first administrator. Compromise of this host, its signer, or operator account is outside message-signature protection.
- **Network attacker:** can observe, alter, delay, suppress, replay, reorder or inject traffic. TLS plus signatures address different parts of this threat; the endpoint and its TLS configuration must still be trusted.
- **Wrapped MCP application/upstream:** receives accepted ordinary MCP traffic and the SDK-provided verified identity. It is separately trusted to apply its own authorization and to protect its own data.
- **Local host/process boundary:** SDK state, key memory, files, signer provider, logs and stdio caller are trusted deployment components. Current SDKs do not supply a general OS keystore, secure secret delivery, or recovery service.
- **Future gateway/bridge boundary:** planned gateway identity headers are trustworthy only on a protected gateway-to-upstream hop. Planned bridge stdio framing and stdout are a separate local process boundary. These are candidate requirements, not current guarantees (`docs/release-plan.md:79-89`).

## OBSERVED protections and limits

| Request authentication and binding | Request signature includes method, exact origin-form target, configured `aud`, `kid`, `ts`, `nonce` and SHA-256 of exact body bytes; body is hashed before parsing (`spec/01-authentication.md:39-64`; `signing.go:8-21`). Go transport buffers and signs the same body bytes and takes `RequestURI` as target (`client/transport.go:162-190`). | Most HTTP headers are **not** signed: neither `Host` nor arbitrary request headers, cookies or session headers are part of that signing string. Server compares against configured audience, never `Host` (`spec/01-authentication.md:54-64`; `server/verify.go:88-105`; `server/middleware.go:125-130`). The signature is not a substitute for trusted endpoint routing or TLS.
| Response authentication and binding | Response signature includes HTTP status, the request signature, server `kid`, timestamp and exact response-body hash (`spec/01-authentication.md:92-128`; `signing.go:24-35`). Client verifies the configured pinned key, freshness, signature and body (`client/auth.go:72-117`). | Response headers are not signed. Do not infer integrity for `Location`, cookies, session or other headers from the body signature; use the authenticated TLS connection for headers. The response's request-signature field links it to a request whose signature binds method/target/body, but it does not bind other request headers.
| TLS and destination | Spec requires HTTPS except loopback (`spec/01-authentication.md:9-12`). Go URL policy rejects insecure non-loopback destinations, userinfo, authority escapes, controls and backslashes; its policy is explicitly pure and does no DNS (`client/urlpolicy.go:53-63,85-118`). Go client refuses redirect statuses rather than following them (`client/transport.go:94-99,123-131,199-213`). Rust's optional HTTP transport configures TLS roots and no redirects/proxy/insecure mode (`rust/src/client/http_transport.rs:1-3,29-36,61-114`). | Go's caller-supplied `http.Client`/round-tripper remains part of transport trust (`client/profile.go:106-128`); the URL policy does not isolate destinations by IP, resolve DNS, or protect a caller that supplies an unsafe transport. A no-follow rule is not TLS enforcement. Client URL policy and endpoint isolation must not be conflated.
| Keys and encoding | Base64url decoding enforces alphabet, no padding and decode/re-encode canonicality (`base64.go:9-11,16-56`). Public-key admission validates 32-byte canonical curve points, rejects identity and non-prime-order points (`ed25519.go:196-214`; `spec/03-user-management.md:16-18`). Request verification checks signatures only after time-window checking (`server/verify.go:197-249`). | Strict public-key admission is not identical to every signature-verifier edge case. Go and TypeScript explicitly reject noncanonical `S` then delegate equation verification to their crypto backend (`ed25519.go:170-184`; `ts/src/ed25519.ts:126-146`); Rust uses `verify_strict`, which additionally rejects noncanonical/small-order `R` (`rust/src/ed25519.rs:19-50`). Do not claim identical backend acceptance beyond what source/contract tests establish; future cross-language tests must discriminate these cases without inventing a new rule.
| Nonces and time | Server checks `abs(now-ts) <= window` (default 30 seconds), then verifies the signature and atomically checks/inserts `(kid,nonce)` (`spec/01-authentication.md:66-90`; `server/verify.go:197-248`). Go nonce entries live through `now <= ts+window` and are held in a mutex-protected map (`server/nonce.go:5-27,30-48`). | The cache is in memory and is not durable across process restart; the spec expressly identifies shared-cache/routing needs for multiple instances (`spec/01-authentication.md:86-90`). Do not claim durable replay prevention or a restart guard. Timestamp bounds are inclusive: both past and future timestamps within the window pass the time check. Deployment assumption for the current v0.1 single-instance scope: operate one active server owner per state store; this is a deployment constraint, not a cross-process ownership lock implemented by the state-store mutex (`docs/release-plan.md:30-34`; `server/state.go:164-221`).
| Refusals | Once signature verification succeeds, the nonce is consumed even if dispatch/authorization later refuses (`spec/01-authentication.md:86-90`; `server/verify.go:237-248`). Go middleware signs rejections when a request nonce was recorded; otherwise it writes an unsigned error (`server/middleware.go:140-155`). | Not all failures are signed. Go rejects unsupported methods before authentication and emits unsigned errors for method, oversized/unreadable body (`server/middleware.go:109-123`). Authentication failures can be unsigned. Go client special-cases a response with missing response-auth and HTTP 401 as status-only and never parses its body, after response buffering is bounded (`client/transport.go:215-233`; `client/transport.go:22-32`). A signed refusal is authenticated only after the usual response verification; never report “all failures signed.”
| Caller identity and admin | Identity is copied from the registry entry at verification time; Go seals it in an SDK-private context token and returns a read-only view (`server/verify.go:243-248,251-258`; `server/middleware.go:205-220`; `server/identity.go:5-19,22-78`). `admin` gates reserved admin tools; ordinary MCP is forwarded for application policy (`spec/02-authorization.md:35-50,64-74`). | `{kid,name,admin}` identifies the registry snapshot, not a human or a complete application authorization decision. Admin is mutable and applies to subsequent requests; in-flight requests retain their snapshot (`spec/02-authorization.md:66-74`). First admin is provisioned out of band (`spec/03-user-management.md:114-117`).

Protocol audit is not proof of complete, durable logging or of application effects.

## INFERRED attack narratives and candidate acceptance checks

The narratives below are reasoned risks at the described boundaries, not observed incidents or proof of exploitability. The checks are **proposed future CI/release acceptance candidates**, not present tests or approved policy.

### INFERRED P0 — Replay across restart or divergent server instances

An attacker records a valid signed request, then replays it after the server restarts. The nonce map starts empty; a still-fresh request can be accepted again. Multiple instances with independent caches can likewise accept the same request once each. Current verification uses `abs(now-ts) <= window`; only the nonce store detects reuse, and it is in-memory (`server/verify.go:224-248`; `server/nonce.go:9-18`; `spec/01-authentication.md:77-90`).

The proposed comparison `ts < server_start` does not solve this. With a 30-second window, the event timeline is:

1. Old process: at wall time 100.1 seconds (Unix-second verifier sample `now=100`), it accepts a signed request with `ts=100` and nonce N.
2. Restart: at wall time 100.5; if `server_start` is Unix seconds, it records `100`. Its in-memory nonce cache is empty.
3. Replay: at wall time 100.6 (`now=100`), the old request has `ts=100`, so `100 < server_start(100)` is false and freshness difference is zero; absent durable replay state, it can be accepted again.

Future timestamps defeat even higher-resolution startup time. The old process can accept `ts=125` at `now=100` (25 seconds in the future). After restart at 101, replay at `now=101` still has `125 < 101 == false` and freshness difference 24 seconds; it remains within the inclusive 30-second window, which would permit that timestamp through `now=155`. Rejecting equality with `ts <= server_start` closes the equality case but not future-dated requests. High-resolution start time likewise cannot identify every timestamp a prior process could have accepted. Any approved alternative must distinguish already accepted requests or conservatively exclude every timestamp that might have been accepted before restart, with an explicit clock/availability trade-off; this document does not select a mechanism or claim a durable solution. D-2 remains an unapproved recommendation (`docs/release-plan.md:40-48`).

**Candidate CI checks:** use a deterministic clock to accept a request in the old process, restart, then replay the exact request; cover same-second equality, old timestamps, and future timestamps at both window edges. Include nonce/cache persistence failures and restart outcome. Test the approved remedy's behavior under clock skew and state loss; do not pass by asserting only `ts < server_start`. Where single-instance operation is required, verify/document the one-owner-per-store deployment assumption; do not claim a cross-process lock exists.

### INFERRED P0 — Trusted identity reaches the wrong upstream or is bypassed (future gateway)

A future gateway that forwards identity in HTTP headers can be tricked if it trusts caller-supplied identity headers, leaves spoofed headers intact, exposes the upstream directly, or routes a verified request to an attacker-controlled upstream. Sending a caller-selected target to an upstream is an SSRF risk; direct requests to an unwrapped upstream bypass mcp-jack entirely. Reused, mixed, or cross-user upstream session identifiers can also confuse principals: session/header handling must not substitute for fresh per-request authentication or the application's ownership/authorization of sessions. The release plan describes verified identity headers on a “trusted hop” but the gateway is not implemented (`docs/release-plan.md:79-89`). Current message signing binds the target and body, not identity-forwarding or session headers (`signing.go:8-21`; `spec/01-authentication.md:41-64`).

**Candidate CI checks:** send forged identity/admin headers and show the gateway strips/replaces them from the SDK identity; prove the upstream is reachable only through the trusted gateway path in the documented deployment; exercise malformed/alternate targets, DNS changes/rebinding, redirects and disallowed destinations against any configured upstream policy; verify that a valid signature for one configured target cannot be used to make the gateway fetch a caller-selected target (SSRF); test session-ID reuse and cross-user/session mixing, and ensure each request still receives fresh authentication while application session ownership is enforced. Do not assert a gateway or endpoint isolation exists today.

### INFERRED P0 — Server key compromise, rotation suppression, or unsafe pin update (future rotation)

Today response verification trusts one configured server key; compromise permits forged responses until clients are independently re-pinned. Server-key rotation is not implemented. The release plan's minimal candidate is a dual-signed announcement binding `aud`, old `kid`, new `kid` and new public key, and `switch_at`; it proposes one pending rotation, no cancel, server signing with old key before switch and new key from switch, client dual-key acceptance in `[switch_at - window, switch_at + window]` then old-key retirement, and manual re-pinning for clients that miss the switch. This is a plan, not approved policy or implementation (`docs/release-plan.md:17-18,40-48,60-75`). It is distinct from the unimplemented, non-normative sr1 proposal (`docs/design/server-key-rotation.md:1-5`).

A valid old-key signature establishes continuity only while the old key remains trustworthy. If the currently trusted old key is compromised, its holder can authorize an attacker-selected next key; next-key proof of possession does not establish an independent trust root. Announcement suppression leaves offline/missed clients needing manual recovery. The candidate must define delivery, replay/reuse and transition handling. Rejection of “stale” announcements needs a precise, approved definition; do not invent stale semantics. A candidate can reject reused keys found in retained history, but bounded retained history cannot promise detection of every previously used key (`docs/design/server-key-rotation.md:130,473`). The plan's pin-update callback leaves acknowledgement semantics with the application; callback failure, crash, lost/ambiguous acknowledgement, or pin rollback can diverge from server state unless success/failure/unknown persistence outcomes and recovery are specified (`docs/release-plan.md:72-75`). No sr1 chain/fork/quarantine/durable-store guarantee applies to this minimal candidate.

**Candidate CI checks:** reject unsigned and wrong-old-key announcements, bad new-key proof, wrong `aud`/binding, altered signed fields, and any transition behavior not authorized by the final contract. Prove a valid announcement is verified against the pre-existing pin and never authorizes its own enclosing response. Exercise switch/overlap boundaries and duplicate/replay/reuse cases; test announcement timing against an approved stale/expiry definition only. Inject pin callback success, failure-before-write, write-then-unknown-ack, process crash/restart and stale backup/rollback; an unknown callback outcome must never be silently treated as a durably acknowledged pin update. Define recovery for suppressed/offline clients and old-key compromise. Fix a clock and test backward and forward clock jumps, same-second and schedule boundaries, plus concurrent pin updates and conflicting/stale revisions. Specify no durability promise unless separately designed and demonstrated. These checks require explicit approval of the exact contract; none of these rotation policies is approved here.

### INFERRED P1 — Request/header confusion, response metadata changes, or wrong endpoint

The request signature binds exact method, origin-form target, configured audience and exact body bytes; the response signature binds status, request signature and response body. This is strong protection against alteration of the signed fields, but not a blanket signature over HTTP. An intermediary can change unsigned headers; a `Host` value is not the audience; a cookie or session header is not authenticated by this signing format. TLS endpoint validation and isolation remain necessary. Go's no-follow/URL checks reduce certain client-side redirect and malformed-destination cases, but the policy deliberately does no DNS (`client/urlpolicy.go:53-63`; `client/transport.go:94-99,123-131`).

**Candidate CI checks:** mutate each signed request field/body byte and require signature failure; change only an unsigned header and do not misrepresent that header as signature-protected; alter response status/body/request-sig and require verification failure; change response headers and verify the documented TLS/header trust boundary rather than expecting a signature failure. Also, on an authenticated admin refusal and an authenticated shape/dispatch refusal, prove the nonce is consumed, the refusal's signed HTTP status/body verify against the request signature, and replaying the exact request yields a replay refusal. Feed an unsigned 401 with a deceptive body containing config, pin, rotation, or retry instructions and prove the client surfaces status only without parsing or acting on that body. A malformed or invalid response-auth header must remain a verification failure, not fall back to trusted unsigned content; only the documented missing-auth 401 path is status-only (`client/transport.go:215-233`; `client/transport.go:22-32`). Test valid and invalid TLS certificate paths with each supported transport, exact configured audience despite hostile `Host`, URL-policy boundary cases, redirect refusal, and endpoint-resolution/isolation behavior chosen by the deployment. No bearer/cookie/session or header-integrity guarantee should be inferred.

### INFERRED P1 — Admin misuse, identity spoofing, and credential trust confusion

A stolen user key can act as that registry identity; a compromised admin can create/revoke users, issue admin invites, and change admin flags. A caller who merely sets `admin` in JSON or HTTP headers must not become an admin: the verifier derives identity from the registered key snapshot. Ordinary MCP policy remains the application's responsibility. `jack.admin.*` refusals after successful authentication consume the nonce; middleware signs the refusal, binding status/body to the originating request signature (`spec/03-user-management.md:5,70-88,97-117`; `server/identity.go:22-78`; `server/verify.go:237-248`; `server/middleware.go:140-155`; `signing.go:24-35`). The server only receives public keys for user management; local transfer tools make a deliberate asymmetric distinction between client signing keys and server-side issuance handoff. The user-key record is not the server's separate response-signing key (`userkey/key.go:37-73,95-113,145-157`).

A valid signature proves key use, not the caller's intent or approval. Untrusted tool or log content can prompt-inject an agent into asking a legitimate signer for a destructive request; this is an application/signer boundary, not a protocol approval feature. Least privilege and any confirmation policy belong to the deployment and are not provided here (`spec/01-authentication.md:134-135`; `spec/03-user-management.md:118-124`).

Credential import must compare the credential with an independently trusted expected tuple `{url,aud,server_public_key,server_kid}`; its embedded server identity is data, not trust. The document is validated before the expected identity check and no signer/configuration is returned unless it matches (`userkey/transfer.go:186-207`; `docs/design/user-keys.md:133-139`). The tuple fields are compared as exact decoded values, without normalization; import does not mutate a pin or profile. Client profiles contain only public data (`client/profile.go:14-25`). The issuance credential/private seed is plaintext in memory and is intentionally exposed through a server-role handoff (`userkey/transfer.go:227-291`; `userkey/key.go:145-157`); this provides no secure-delivery, zeroization, or OS-keystore guarantee.

**Candidate CI checks:** forge identity/admin headers and body fields and prove identity still comes only from the authenticated registry record; test ordinary callers against every `jack.admin.*` operation and verify ordinary-MCP authorization is explicitly delegated to the application; test revocation/admin change timing and immutable in-flight snapshot. For credentials, vary each member of the trusted tuple independently, omit/invalidate it, conflict it with an existing pin, and ensure no signer/configuration is returned or pin changed. Test role APIs for no private accessor or unintended serialization from client key types; separately verify the issuance handle's intentional plaintext seed/credential handoff, redaction of logs/debug/errors, and public-only user-key records distinct from the server response-signing key. Model out-of-band delivery and storage as operator responsibilities.

### INFERRED P1 — Stdio bridge framing, signer authority, and process lifecycle (future bridge)

The planned bridge will place an MCP stdio caller and a signed HTTP client in one process and may use a key file or external signer; it does not exist yet (`docs/release-plan.md:85-87`). Framing/parser mistakes could merge, truncate, interleave, or misroute messages; unbounded frames or message queues could exhaust memory. stdout must remain exclusively protocol output: diagnostics, credentials, private keys, and signer material must not leak there. A local process able to invoke the bridge may exercise whatever authority its configured signer grants; local stdio is not a human-approval boundary. Key-file permissions and external-signer access/custody remain deployment responsibilities; no private material should be sent upstream or written to logs. EOF, broken pipes, cancellation, and slow consumers can strand work or responses; automatic retries of side-effecting MCP calls can duplicate effects.

**Candidate CI checks:** bound input frame bytes, per-message work, outstanding request/response queues and aggregate buffering; exercise malformed, truncated, oversized, interleaved and back-to-back frames; correlate each request that expects a response by JSON-RPC ID, emit no fabricated replies to notifications, and neither merge nor duplicate frames. Capture stdout/stderr separately and prove stdout contains only valid protocol frames, diagnostics go to stderr, and secret material goes to neither. Use a fake signer/upstream to verify the bridge invokes only the configured signer, sends no private material, and preserves signed request/body binding. Inject EOF, broken pipe, cancellation during read/write, slow downstream/backpressure, signer errors and child termination; require bounded cleanup with no detached workers or leaked queued work. Prove there is no automatic retry after a request may have reached the server, especially for side-effecting calls. Add this to the planned bridge/gateway end-to-end coverage, not as a claim that such tests exist (`docs/release-plan.md:85-89,91-99`; `client/transport.go:162-194,215-237`).

### INFERRED P1 — Key/parser disagreements across language SDKs

Strict canonical encodings and public-key admission reduce ambiguous identities, but backend verification differs: Rust's source calls out additional strict `R` and small-order checks compared with Go's backend (`ed25519.go:170-184`; `rust/src/ed25519.rs:19-50`; `ts/src/ed25519.ts:126-146`). Treat this as an interoperability/security acceptance question, not proof of an exploit or permission to expand the crypto contract by assumption.

**Candidate CI checks:** share a reviewed signature corpus that distinguishes canonical/noncanonical `S`, `R` edge encodings, and invalid public keys; run it through all three verifier implementations and assert identical outcomes required by the approved spec. Keep key-admission vectors separate from signature-verification vectors. Add cross-language request/response cases for duplicate JSON names, exact raw body bytes, header multiplicity, URL target bytes and response binding; report any discrepancy for protocol review rather than silently choosing a new rule.

### INFERRED P2 — Resource exhaustion, hangs, and incomplete cancellation

Go server adapters cap request and buffered response bytes (Go defaults to 1 MiB each), but byte caps are not deadlines. Go cancels a wrapped-handler context on response overflow/stream refusal but cannot forcibly stop a handler that ignores cancellation or write errors; an idle handler can delay the response (`server/middleware.go:23-43,56-84,109-123,205-244`). Rust module documentation directly states that response caps do not bound time, body consumption can wait indefinitely, and a caller must wrap the whole service in a deadline (`rust/src/server/http.rs:8-20`). Nonce storage has no explicit entry-count/rate cap and the spec does not define rate limits (`server/nonce.go:9-48`; `spec/02-authorization.md:76-84`). Go client buffers the request body before signing and leaves HTTP timeout behavior to caller configuration (`client/transport.go:162-194`; `client/profile.go:106-128`).

**Candidate CI checks:** test exact body/response cap and cap+1, slowloris/never-ending body, slow or idle upstream, response overflow, stream refusal, cancellation ignored by upstream, client timeout/abort, and bounded cleanup/backpressure. Measure that accepted input, response buffering, queued work and audit storage are bounded or explicitly caller-controlled; exercise valid-key request floods and confirm the documented rate/resource controls. Keep deadlines caller-owned where that is the approved API contract; do not imply a byte cap is a time limit or that cancellation forcibly stops arbitrary handler code.

These are proposed security gates and currently observable limitations, not claims of implementation or security approval. D-1/D-4/D-5 owner answers are recorded in [versioning policy](versioning.md): include the Go programs, keep current versions and publication restrictions, and validate an artifact-only RC. 1. **Decisions:** preserve the recorded D-1/D-4/D-5 answers and obtain explicit maintainer decisions for D-2/D-3, including exact restart/rotation semantics, before implementation. Approval of Go executable scope is not approval of any particular security mechanism; this document does not choose one.
2. **Contract and SDK acceptance:** after approval, extend shared fixtures and run conformance in all three SDKs plus the applicable 3×3 interop and credential-transfer matrices. The workflow currently defines Go/Rust/TS and fixture jobs at `.github/workflows/ci.yml:11-114`, and interop/credential-transfer matrices at `:116-178`; those definitions are not results for this task or a future change. ## Release boundary and explicit non-guarantees

- No authenticated encrypted session/channel, streaming signatures, session-header integrity, or confidentiality from message signatures is implemented; v0.2 is only a future direction (`docs/release-plan.md:30-38`; `spec/02-authorization.md:48-50`).
- No server-key rotation or restart-persistent nonce store is implemented. In-memory nonces disappear on restart; do not infer durable pin/replay state from the registry state file (`server/nonce.go:9-18`; `server/statefile.go:22-38`).
- No gateway, stdio bridge, CLI bootstrap/keygen, automatic TLS endpoint isolation, OS key store, or generalized secure secret-delivery implementation is supplied by the plan's current source (`docs/release-plan.md:17-23,79-89`).
- No claim of power-loss-safe persistence follows from file sync and rename; no claim of distributed ownership follows from an object-local mutex (`server/statefile.go:30-38,264-325`). The planned one-server-instance-per-store restriction is a deployment assumption, not an implemented cross-process owner lock; multi-instance clusters are deferred (`docs/release-plan.md:30-34`).
- No policy in this document silently approves the proposed minimal rotation, restart guard, gateway, bridge, timeout, identity-header, or state-owner behavior. Obtain explicit design/maintainer approval and define discriminating CI acceptance before relying on any as a release guarantee.
- No test, build, runtime probe, external audit, or vulnerability scan was run for this document; tests were not run due to the task's restrictions.
