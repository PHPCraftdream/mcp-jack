# Design candidate: restart replay guard

**Status:** Task 52 consolidated design-only candidate; not normative, approved, or implemented. Task 52 consolidation covers restart replay; companion rotation was originally Task 53. Design baseline supplied for this work: `42c42560180be8ee316360b5d58d5d5372f0fe37`. Foundation Task 54 is complete: PR16 merged at c98f7eb0dac9ad22f11f712a80a3fe9c537426ee with verified green PR and post-merge CI and source-preserving cleanup. This integration uses that merged baseline; D2/D3 remain unapproved. No merge, implementation, approval, test, CI, runtime, or release-readiness claim is made.

**Scope:** replay after an in-memory nonce cache is reset, including a process restart or any other cache reset. This document proposes no source changes, test additions, fixture changes, version/dependency/MSRV changes, publication changes, or artifact/tag actions. The separately patched Go security-toolchain policy remains unchanged.

## 1. Recommendation in brief

**INFERRED candidate recommendation, conditional on owner decisions:** retain the existing in-memory nonce map and add a strict per-boot timestamp floor. The nonce-cache/boot-lease lifetime has one immutable `Wcurrent`, tied to that lease, `F`, map, and high-water mark `H`. Both preliminary and final gates use that same captured lease window. No in-place config reload may change it: both increases and decreases are refused, even when a proposed value is at or below `Wmax`. A requested live change may be reported as candidate local `window_change_requires_reset` (non-normative). `Wmax` is only a historical upper bound used to construct a **new** floor, never a live-window mitigation. For a controlled reset to a different `Wnew`, close admission, drain old work, prove the required clock/window history, sample `S`, and atomically install the new lease carrying `Wnew`, `F`, map, and `H`; readiness may reopen after readiness checks under the same strict `ts > F` floor used for a same-window reset, with no additional delay. Full quarantine until checked `now > F+Wnew` remains an optional owner alternative, not the recommendation. With one fixed window `W`, `B=0`, this is `F=S+W`.

This is the smallest candidate that avoids new wire fields and persistent nonce storage, but it makes a strong clock/ownership assumption and intentionally delays ordinary requests. Neither ordinary NTP synchronization nor a fresh sample after a crash proves the required clock history or discrepancy bound. It is **not** a guarantee when clock/history is unknown, a prior owner may still run, or the required global history premise fails. Under those conditions the server must fail closed and require operator recovery or a different approved mechanism; it must not claim replay protection. A startup with an existing cache/lease whose stored window differs from the actual effective configured `Wcurrent` must fail candidate 503 with readiness closed. More generally, an actual effective-configuration mismatch with the active lease, whether observed or externally supplied, at startup/open or either admission gate closes readiness and returns candidate 503 before any further nonce reservation or dispatch authorization. Keep readiness closed until the exact old configuration is restored and normal readiness succeeds, or a controlled safe reset installs a new lease/window/floor/map. Already-authorized handler effects may finish as documented; they are not revoked. This is distinct from rejecting a proposed hot reload, which leaves active configuration and lease unchanged.

The floor also requires a serialized clock/nonce admission gate: verify the captured boot lease at the final admission gate, and atomically apply the fence and nonce check/insert against the same current lease. A stale in-flight request must not pass a newer fence or a cache reset. Any runtime clock rollback is an operational failure (candidate 503), not a reason to clamp the clock and call the clamped value fresh.

## 3. Why the two startup comparisons are insufficient

The existing freshness interval is inclusive on both sides. Thus an old process at `now=100` can accept a signed `ts=130` with `W=30`, even though `ts` is in the future. Restart at `S=101`; a replay at `now=101` still has `abs(101-130)=29`.

| Candidate rule | Same-second example | Future-timestamp counterexample |
|---|---|---|
| Reject `ts < S` | Old verifier accepts `ts=100` at `now=100`; restart samples `S=100`. Since `100 < 100` is false, the exact replay can pass freshness at `now=100`. | Old verifier accepts `ts=130` at `now=100`; restart `S=101`. `130 < 101` is false and replay freshness is 29 seconds. |
| Reject `ts <= S` | The same-second example is rejected (`100 <= 100`), closing that one case. | `ts=130` at old `now=100`, restart `S=101`: `130 <= 101` is false; the replay remains within the inclusive window. |

The defect is not timestamp precision: the old verifier may accept timestamps as high as its last `now + W`. For the zero-discrepancy premise, excluding every possibly accepted old timestamp requires a floor at least `S + Wmax`, and strict `ts > S + Wmax`. With a proven all-lifetime backward-discrepancy bound `B`, replace that with `F = S+B+Wmax`; an unproven estimate is not sufficient.

## 4. INFERRED candidate: memory nonce map plus a per-boot floor

### 4.1 Assumptions and definitions

- **One owner:** there is one active verifier owner for the audience/state deployment. Before sampling `S`, the previous owner is known to have stopped and all its in-flight verifier operations are drained. No older owner may continue accepting requests after `S`. This is an operational prerequisite, not a cross-process lock supplied by `StateStore` or its mutex.
- **Clock history and discrepancy:** The simplest candidate requires that every verifier-time sample across all earlier lifetimes be `<= S`, with globally nondecreasing trusted wall time. Alternatively, choose a justified finite nonnegative bound `B` on backward discrepancy and prove that every sample from every earlier lifetime was `<= S+B`; then use `F = S+B+Wmax`. `B` is not an estimate: ordinary NTP synchronization does not prove it, and a crash/restart cannot infer unknown historical samples. A conditional bound that covers only the immediately preceding process is insufficient if still-replayable requests could have been accepted earlier. If neither premise can be established, do not use this floor as a replay guarantee.
- **Window history and representable floor:** `Wcurrent` is a positive configured integer window immutable for the entire nonce-cache/boot-lease lifetime and is part of that lease's identity alongside `F`, the map, and `H`. Both admission gates use its exact value. In-place increase or decrease is refused, including an equal-to-or-below-`Wmax` increase; an equal-value reload is a no-op. `Wmax` is at least the largest window that could have accepted requests in any prior lifetime whose messages may still be replayed, and is used only to form a new floor. A safe reset to `Wnew` requires `Wmax >= max(Wold,Wnew)` and the independent history proof; unknown prior window history requires recovery. Compute `F=S+B+Wmax` with checked sums. `S` must be an integer in `0..999999999999`, and the resulting `F` must satisfy `0 <= F < 999999999999`, so its strict successor is representable as a 12-digit request timestamp. A sum overflow or `F >= 999999999999` makes startup unavailable (candidate 503/recovery-required), not merely a machine-overflow error. Here `B=0` in the global-nondecreasing-time variant.
- **New lifetime:** after prior-owner shutdown/drain, sample integer-second `S`, establish a new empty nonce map and a new boot lease carrying its immutable `Wcurrent`, then set `F=S+B+Wmax` and initialize lifetime high-water mark `H=S`. For a controlled reset to `Wnew` (same or different), prove the required clock history and `Wmax >= max(Wold,Wnew)`, keep readiness closed through close/drain/sample and atomic installation of the new lease/window/`F`/map/`H`, then reopen after readiness checks under the strict `ts > F` floor. A different `Wnew` adds no delay beyond this floor; full quarantine is a separate optional owner alternative. Treat any nonce-map reset—even in the same process—as a new lifetime requiring this safe fence procedure. A later lifetime must preserve/prove history for **all** earlier lifetimes, not merely the immediately preceding one.

### 4.2 Admission rule and consequences

For each otherwise eligible request, apply the existing timestamp freshness rule at both serialized decision gates using the same immutable `Wcurrent` captured in the boot lease: the preliminary gate may make a final rejection, while only the authoritative final gate may accept. A request never crosses either gate using a different window from the other. Require there, in addition:

```text
abs(now - ts) <= Wcurrent    // existing inclusive freshness rule
and ts > F                  // candidate restart fence; strict
```

For every lifetime covered by the proof, every previously accepted request had `ts <= old_now + Wprevious <= S+B+Wmax = F`; therefore strict `ts > F` excludes those timestamps after a nonce-map reset. Here `B=0` under the global nondecreasing-time premise. A request with timestamp `F` is rejected even if it is exactly on the ordinary freshness boundary. The signature bytes, request header, nonce format, key scope, and response signing format need not change for this candidate.

This remains conditional on evidence for the full history: a bound on the current restart interval alone cannot exclude timestamps accepted in an earlier lifetime if the clock later regressed. If any earlier sample/window may exceed the established bound, the inequality is not established and the candidate must remain unavailable pending recovery or another approved mechanism.

Availability under the **recommended strict-floor candidate (not approved)** (separate from the optional full-quarantine alternative) is material. With `now=S`, the inclusive freshness window contains no timestamp greater than `F`; therefore an honest same-clock client (`ts=now`) first becomes eligible at `now = F+1 = S+B+Wmax+1`. A future-dated request can pass earlier only when it is both above `F` and within `Wcurrent`; the earliest integer sample is `now = F-Wcurrent+1` when that value is in the admissible time domain. In the zero-discrepancy fixed-window case, this is `now=S+1`, with `ts=F+1` at the inclusive future edge.

For example, `S=101`, `B=0`, `Wmax=30`, `F=131`:

- At `now=101`, `ts=131` is ordinarily fresh (future edge) but is fenced.
- At `now=102`, `ts=132=F+1` is ordinarily fresh at the future edge and may be accepted with a valid signature and a new nonce.
- At `now=131`, an honest `ts=131` is still fenced. Same-clock availability begins at `now=132`.

For the bounded-discrepancy variant, take `S=101`, `B=5`, `Wmax=30`, so `F=136`. This candidate is justified only if every verifier sample from every earlier lifetime is independently known to be `<=106`; at `now=107`, `ts=137=F+1` is at the inclusive future edge and may pass, but `ts=136` is fenced. If that history/bound cannot be proven, this calculation is not a recovery method.

### 4.3 Inclusive edges, restart repetition, and full-quarantine alternative

At `now=F+Wcurrent`, the old upper-bound timestamp `ts=F=S+B+Wmax` is exactly `Wcurrent` seconds old and remains freshness-valid because the existing window is inclusive. It must still be rejected by the floor. Merely sleeping `Wmax` after restart is insufficient.

The recommended timestamp-floor candidate (not approved) uses strict `ts > F` at the same point in the unchanged authentication order (after ordinary freshness, before signature, then atomic nonce check/record); it does not close admission for an extra full-window quarantine. The optional full-quarantine alternative, if separately chosen by the owner, instead keeps all application admission closed until checked `now > F+Wcurrent`. Its strict edge matters: at equality `ts=F` remains freshness-valid. Both alternatives need the same clock-history/discrepancy, nondecreasing-clock, and owner assumptions; service is unavailable with 503 throughout any selected quarantine. No NTP setting proves those premises.

On repeated resets, each new fence must cover every verifier sample and window in **all** earlier lifetimes that may have accepted a still-replayable request. A latest-lifetime-only comparison is insufficient unless a trusted global nondecreasing-time/history premise establishes that it dominates all earlier samples. Use the same fixed `Wmax` or a larger explicitly bounded history. A process restart is not itself evidence that the clock or owner condition holds.

### 4.4 Serialized clock, lease, and nonce critical point

A candidate implementation must make the fence meaningful under concurrency, rather than merely read an immutable startup timestamp: lease identity includes `Wcurrent`, `F`, map, and `H`; the preliminary and final gates compare against that same lease and window. Any window change request during a live lease fails locally with a candidate `window_change_requires_reset` error (non-normative); do not reload it in place.

1. Service readiness remains closed with candidate 503 until owner shutdown/drain, clock/history/window premises, valid `S` and representable `F`/successor, checked arithmetic, the new immutable window/floor, empty nonce map, and boot lease are established, and the actual effective configured window matches the selected lease. At startup/open and each admission gate, an actual configuration/lease mismatch closes readiness with candidate 503; reopen only after exact old configuration is restored and normal readiness succeeds or a controlled safe reset atomically installs a new lease/window/floor/map. Already-authorized handler effects may finish as documented and are not revoked. A sum overflow or `F >= 999999999999` requires recovery; do not open readiness. No lock is held across crypto or handler execution.
2. Preliminary checks may reject malformed headers/versions or an unknown key with existing errors; preserve the existing pending-enrollment exception rather than treating every unregistered submitted key as `unknown_key`. An eligible pending enrollment may use its submitted public key only when its hash matches `kid`; this does not change enrollment parsing. For a request reaching the preliminary rejection gate, enter the serialized gate, require service readiness—including an exact match between the actual effective configured window and the accepting lease—and an accepting lease; on mismatch, close readiness and return candidate 503. Sample raw integer-second `now`, reject candidate 503 on any decrease from `H`, and otherwise update `H` immediately. Check registered active-key status (skipping only that interval check for the existing eligible pending-enrollment exception), inclusive freshness `abs(now-ts) <= Wcurrent`, then strict floor `ts > F`, in that order. These checks are a final rejection decision at this preliminary gate; they reserve no nonce and dispatch nothing, and later state/time changes do not defer or replace the rejection. If they pass, capture under that gate the current registered-key snapshot or eligible submitted-key snapshot (with hash matching `kid`), the accepting lease and its immutable `Wcurrent`, and register an in-flight operation. Preliminary and final gates must both use this captured lease's same `Wcurrent`; a configuration reload cannot change it. A requested in-place change may be reported as candidate local `window_change_requires_reset` (non-normative), but cannot change gate behavior. Leave the gate and perform bounded signature verification off-lock, retaining only tentative valid/invalid result. Passing preliminary checks is provisional: active status and all admission checks are repeated at finalization, and only signature verified with captured key matching current registered key or still-eligible enrollment exception may proceed. Do not hold the gate through crypto or handler execution.
3. Re-enter the serialized admission gate for the **final admission decision**. At gate entry, require service readiness, including an exact match between the actual effective configured window and the current accepting lease; on mismatch, close readiness and return candidate 503 before any nonce reservation or dispatch authorization. Then take a fresh raw integer-second `now`. This final sample—not an earlier sample and not the physical dispatch time—is authoritative for acceptance. First compare raw `now` with `H`: if lower, fail operationally with candidate 503 and do not clamp; otherwise update `H` immediately, including for safe samples that later fail another gate. Any observed backward sample at either serialized admission gate latches readiness unsafe; clock catch-up does not clear the latch, and explicit recovery is required before reopening. Then check that the captured boot lease is still the current accepting lease; if it changed or admission is closing, return candidate 503, with no stale insertion and no retry/re-evaluation under the new lease. Resolve and revalidate current registry/enrollment state. Preserve the existing pending-enrollment exception: if the request remains an eligible unregistered enrollment with the existing enrollment shape and was verified using its submitted public key whose hash matches `kid`, continue on that key and skip only the registered-key active-interval check; do not add or alter enrollment parsing. If it became registered meanwhile with the same key, use the normal registered path and current active-key check. If it is unknown outside that still-eligible exception, return existing `unknown_key`; if the registered key changed or enrollment/registry state otherwise makes the captured crypto snapshot unsafe, return candidate 503 `state_changed` and do not dispatch. For a registered matching key, require current public-key bytes equal the captured crypto snapshot, then check in this exact order: active-key status from current state (not applicable only to the still-unregistered eligible enrollment exception); inclusive ordinary freshness `abs(now-ts) <= Wcurrent`; strict restart floor `ts > F`; tentative signature result (invalid is existing 401 `bad_signature`); and atomic nonce check/reservation in the current map (duplicate is existing 401 `replayed_nonce`). Thus final freshness/floor failures override a deferred invalid-signature result. A floor denial is candidate 401 `restart_timestamp_fenced`. Safe high-water updates are retained even when later checks reject. Any unsafe clock/lease condition fails closed with candidate 503.
4. The atomic nonce reservation is the authorization linearization point. Only after it succeeds may the gate be left and the handler be invoked. Exactly one concurrent valid copy may reserve a `(kid, nonce)`; a later handler/authorization refusal still consumes the reservation. The gate and nonce critical section must be shared by all operations on this owner, not merely the `NonceStore` object's mutex.
5. A boot/cache reset uses this same gate: close old-lease admission and mark its generation non-accepting under the gate; let in-flight crypto reach the gate and fail without insertion, and drain every registered old-lease operation, including any handler already authorized, before resetting the map. Wait without holding the gate; once drained, reacquire it to establish the new lease carrying `Wnew`, empty map, high-water baseline `H=S`, and safe `S`/`F`, then atomically install the full new lease/window/floor/map/high-water state before reopening admission. Do not hold the gate across crypto, waiting/draining, or handler execution. A reset cannot make an old lease current again.

The final gate takes a fresh raw integer-second `now`; it must not rely on an earlier decisive sample, clamp, or substitute the high-water value for the raw sample. Compare raw `now` with `H` and fail with 503 on any decrease; otherwise advance `H` immediately, including when a later check rejects. This prevents a forward purge followed by rollback from making a purged nonce fresh again: [`server/nonce.go`](../../server/nonce.go) lines 30–46 purge based on caller-supplied `now`.

The final gate linearizes authorization; it does **not** guarantee that the physical handler dispatch or response return occurs at that same instant. Already-authorized operations may dispatch afterward, so reset must drain them before changing lifetime state. The design defines candidate semantics only; it does not prescribe an API or claim current code has this gate.

## 5. Comparison with alternatives

### 5.1 Durable nonce reservation

**INFERRED alternative:** persist each authenticated `(kid, nonce)` using an atomic, durable reserve *before* dispatch. Preserve the current order of cheap checks and signature verification, but do not invoke the wrapped handler until a durable reservation receipt exists. A successfully reserved nonce is consumed on any later authorization/dispatch rejection; never roll it back to make a retry succeed.

- **Benefit:** directly remembers prior requests across restart without rejecting all pre-restart timestamp values that happen to be above a startup floor. It can preserve more availability if persistence and clock retention are correct.
- **Unknown commit/error:** if reservation did not commit with certainty, do not dispatch. If the write may have committed or the receipt is unknown, fail closed, fence/reconcile the store, and do not guess or reserve a replacement. A request may be lost after a successful reservation and before dispatch; replay safety is preferred to implicit retry. Any authenticated refusal after confirmed reserve still consumes the nonce.
- **Retention:** preserve the existing inclusive liveness rule (`now <= ts + W`) for the observed implementation; it passes `retainUntil=ts+Window`. Purge only when the expiration is safely past under an approved nondecreasing-time policy. A forward-clock purge followed by rollback can erase a nonce while its timestamp becomes fresh again, so safe persisted high-water/retention policy or a sufficiently conservative reviewed bound remains a separate gate. An alternative retention policy based on `ts+Wmax` is unselected and would require prior approval of the historical bound **before any nonce reservations**, plus safepurge, clock, and memory review. It cannot restore history already purged under a smaller window.
- **Storage/platform gate:** require atomic cross-request and cross-process reservation, crash recovery, known commit outcomes, owner/rollback policy, and platform-specific durability evidence. The current `FileState` same-directory temp + sync + rename sequence is not that proof, and its mutex is object-local. Do not infer durable nonce safety from the registry state file.
- **Cost:** persistent writes on every authenticated request, storage growth/DoS and purge design, failure-to-serve behavior, and a substantially larger crash/platform contract. This is not the smallest candidate.

### 5.2 Epoch challenge / wire change

**INFERRED alternative:** add a boot epoch or challenge to the signed request/response contract so that a request from an earlier epoch is rejected. This is not a transparent implementation detail: a client needs an authenticated way to learn the current epoch and include it in the bytes it signs. An unauthenticated challenge or unsigned error body cannot safely authorize the retry; a signed challenge flow adds protocol sequencing and client behavior.

A wire epoch changes request signing bytes, error/retry behavior, fixtures, and every SDK. It needs a migration/compatibility decision for existing `mcp-jack/v1` clients, and exact epoch uniqueness, persistence/rollback, owner, and concurrent-old-process semantics. A volatile epoch alone does not help if old and new owners run together or epoch/history rolls back; durable monotonic epoch state reintroduces storage gates. No epoch field, challenge endpoint, or automatic retry is recommended for the minimal candidate.

## 6. Candidate verification order and externally visible failures

The following is a **proposed** order for a ready service, aligned with the existing authentication precedence; names/statuses for new failures are candidates, not normative protocol text. Service-unready/unsafe-clock admission, including an actual effective-configuration mismatch with the accepting lease, is a separate operational gate and fails with 503 before application processing.

1. Preliminary immutable/cheap checks may reject missing, repeated, malformed headers and version errors, preserving existing `missing_auth`, `malformed_auth`, and `unsupported_version` precedence (the version scheme is examined first as specified). They do not authorize admission.
2. Preliminary key lookup may reject an unknown key with its existing error outside the existing eligible pending-enrollment exception. Preserve that exception without changing enrollment parsing: an eligible pending enrollment may be verified with its submitted public key only when the hash matches `kid`. For a request continuing, enter the serialized preliminary rejection gate and require service readiness, including an exact match between the actual effective configured window and the current accepting lease; on mismatch, close readiness and return candidate 503. Take raw integer-second `now`, fail with candidate 503 on a decrease from `H` or otherwise update `H` immediately, then check registered active-key status (skipping only that interval check for the existing eligible pending-enrollment exception), inclusive freshness `abs(now-ts) <= Wcurrent`, and strict floor `ts > F`, in that order. Any such rejection is final at this preliminary decision, performs no crypto, reserves no nonce, and dispatches nothing; passing is provisional only. Under the same gate, capture the registered-key or eligible submitted-key public-key snapshot and current boot lease and register an in-flight operation.
3. Perform bounded signature verification off-lock using the captured public-key snapshot and retain a tentative valid/invalid result. A passing preliminary gate never authorizes admission; do not hold the gate through crypto or invoke the handler.
4. At the final serialized gate, first require service readiness, including an exact match between the actual effective configured window and the current accepting lease; on mismatch, close readiness and return candidate 503 before any nonce reservation or dispatch authorization. Then take fresh raw integer-second `now`; compare it to `H` and fail with candidate 503 on any decrease, otherwise update `H` immediately. Then check the captured boot lease is still current and accepting; a changed/closing lease returns candidate 503, with no insertion and no retry/re-evaluation under the new lease. Resolve and revalidate registry/enrollment state under the existing pending-enrollment exception in §4.4 step 3: a still-unregistered eligible enrollment must retain its existing shape and submitted-key hash binding, and skips only the registered-key active-interval check; if it became registered with that same key, apply the normal registered active-key check. Unknown keys outside the exception return existing `unknown_key`; a changed key/state that makes the captured crypto unsafe returns candidate 503 `state_changed`, with no dispatch. For a registered matching key, require current key bytes equal the captured crypto snapshot, then continue in exact order: active-key status at this final sample (existing 401 `key_inactive`; omitted only for the still-unregistered eligible enrollment exception); inclusive ordinary freshness `abs(now-ts) <= Wcurrent` (existing 401 `timestamp_out_of_window`); strict floor `ts > F` (candidate 401 `restart_timestamp_fenced`); tentative signature result (existing 401 `bad_signature`); atomic check/reservation of `(kid, nonce)` (existing 401 `replayed_nonce`). Final freshness/floor failures therefore override a deferred invalid-signature result. No safe time is clamped or replaced by `H`.
5. Successful nonce reservation linearizes authorization. Leave the gate before handler dispatch; reservation remains consumed on later 400/403/501 refusal. Track the authorized operation until handler completion so a lease reset can stop new admission and drain outstanding effects without holding a lock across the handler.

Consequences: if freshness and floor both fail at either gate, `timestamp_out_of_window` wins. A known active-key request that is fresh but fenced is rejected at the preliminary gate as `restart_timestamp_fenced`, before crypto, even if its signature is invalid; signature-call count is zero. If a request passes preliminary checks but becomes stale/fenced during crypto, the final freshness/floor error overrides a deferred `bad_signature`. A request that passes both gates' active/freshness/floor checks but has an invalid signature returns `bad_signature`. Unknown-key errors retain preliminary precedence; active-key status is checked at each gate before freshness/floor. A lease change, changed key snapshot, or backward clock fails closed with candidate 503 as specified. Preliminary rejection is final at its declared decision point, but preliminary passage never makes a request acceptable; final active-key, freshness, floor, signature, and nonce checks remain authoritative. This two-decision-point candidate behavior differs from the **OBSERVED** Go `Verify` behavior, which samples `Now` once at entry and uses that captured value through verification (see §2, [`server/verify.go`](../../server/verify.go), lines 194–248). It is not a description of current behavior or a normative change.

Pre-signature/fenced failures have no authenticated request nonce and must not be presented as signed refusals. Any unsigned pre-auth response is status-only to clients; its body is untrusted and must not trigger automatic retry or be parsed as policy. Do not add transparent retry. A caller retry requires constructing a fresh signed request with a new timestamp/nonce after service readiness and does not make application effects exactly once. This matches the MCP compatibility guidance to avoid automatic retries when a call may have reached the server ([`docs/design/mcp-compatibility.md`](mcp-compatibility.md) lines 92, 107). For a durable-nonce alternative, an unknown reservation outcome likewise must not trigger dispatch or automatic retry.

## 8. State loss, rollback, and recovery checklist

An empty in-memory nonce map is not evidence that no prior request was accepted. The candidate floor is safe only with the stated owner, clock-history/discrepancy, and window-history premises. On state loss or unsafe clock, do not automatically reopen service or retry application effects. Recovery is an explicit operational decision:

1. Stop and drain **all** verifier owners for the audience/state deployment, including in-flight authenticated handler operations; prevent any old owner from accepting or dispatching further requests.
2. Independently establish a trustworthy prior clock/sample history and historical `Wmax` for **all** lifetimes whose requests may still be replayed, including `Wmax >= max(Wold,Wnew)`. Either establish the globally nondecreasing-time premise and that all prior samples are `<=S`, or establish a justified finite `B` and prove all prior samples are `<=S+B`. A fresh wall-clock reading or NTP synchronization alone does not establish either history or bound. Check `S+B+Wmax` and, if used, `F+Wnew` for overflow. A window mismatch does not authorize discarding the cache or history; an already-purged nonce cannot be recovered by later selecting `Wmax`.
3. Under the serialized reset gate, keep admission closed; after old work is drained, sample `S`, create the new empty nonce map and lease with selected immutable `Wnew`, set `F=S+B+Wmax` and raw-time high-water baseline, then atomically install lease/window/floor/map/`H`. Reopen after readiness checks under the strict `ts>F` floor, whether `Wnew` differs from `Wold` or not; different windows incur no extra mandatory wait. Full quarantine until checked `now>F+Wnew` is a separate optional owner alternative. A mismatched configured window at startup is not permission to reuse or clear state: restore exact old config for normal readiness or perform this safe reset.
4. Do not automatically retry a request or application effect that may have reached a handler. A caller may later construct a fresh signed request after service readiness, but that can repeat an effect; this design makes no exactly-once or safe-retry claim.

If no trustworthy historical sample/discrepancy or window bound can be established, waiting an unknown duration does not recover the proof. Remain unavailable or choose a different separately approved mechanism. No cross-process owner lock or history source is observed in `FileState`; one-owner operation remains a deployment prerequisite.

The current nonce semantics are bounded by freshness, not an all-time ban on nonce-string reuse: the exact captured signed request must fail once it is stale, but a new signed message using the same `(kid, nonce)` with a new timestamp may be admitted after the old entry expires and ordinary final-gate checks pass. This is distinct from retrying the same captured request and does not promise application-effect deduplication.

- A timestamp floor does not detect two live processes. A restarted process must not serve while an old owner can still verify or dispatch requests.
- A per-lifetime backward clock jump after nonce purge can resurrect an old nonce unless the serialized nondecreasing clock gate rejects it. A forward jump can deny service. Without independent evidence, a process cannot prove current wall time safe relative to lost prior history.
- A changed window is not a live mitigation: keep `Wcurrent` immutable for each nonce-cache/boot-lease lifetime and tie it to `F`, map, and `H`. Refuse both increases and decreases without a safe reset; `Wmax` bounds only the historical floor for a new lifetime. The observed nonce-store retention is `ts+Window`, not `ts+Wmax` ([`server/nonce.go`](../../server/nonce.go) lines 20–25, 42–47). An alternative retention policy based on `ts+Wmax` would require prior approval of the historical bound before reservations, plus safe-purge, clock, and memory review; it cannot recover history already purged under a smaller window and is not selected here.
- In the durable-nonce alternative, state rollback, uncertain write/commit, expiry purge, and platform-specific crash behavior require explicit contracts. The current registry file is not evidence for those contracts.
- Once a request is dispatched, replay protection does not provide application exactly-once execution or safe retry semantics. A process can fail after a side effect; the same old signed request must still be rejected, but a caller-created new request could repeat that effect.

## 9. Boundary with server-key rotation and release scope

Restart replay protection concerns request nonce acceptance and verifier time. Server-key rotation concerns client trust in response-signing keys. Do not conflate their state, epochs, error handling, or recovery: a rotation pin/snapshot does not restore request nonces, and a nonce fence does not rotate or validate a server key. The unimplemented sr1 proposal explicitly leaves existing request replay controls unchanged. Review this candidate alongside the actual companion proposal [`minimal-server-rotation.md`](minimal-server-rotation.md) without importing sr1's rotation state as a nonce store.

The candidate leaves request/response signing domains and bytes unchanged, but changes server acceptance semantics and introduces a possible new observable 401 code/error precedence. [`docs/versioning.md`](../versioning.md) treats wire semantics and error precedence as compatibility dimensions; an owner must decide how to document/migrate the behavior before any normative spec or SDK change. No version, dependency, MSRV, or package metadata change is proposed; in particular preserve TypeScript `private: true` and Rust `publish = false`. No artifact/tag/publication action is proposed; any authorized RC remains artifact-only, with no tags, registry publication, GitHub Release, or public announcement. The separate Rust security-dependency-update/MSRV 1.88 approval and the separately accepted healthy/local bounded-latency filesystem deployment assumption (without an enforced hard-disk-stall deadline) do not approve clock history, nonce retention/store durability, protocol durability, rotation ACK, or fencing policy; this is an assumption, not an implementation/runtime health claim. Those choices remain subject to their own design owners and acceptance gates; no toolchain or policy change is made here.

For any in-memory candidate, `Wcurrent` is immutable per cache/boot-lease lifetime; neither a live increase nor decrease is allowed, and a different window requires the safe close/drain/prove/sample/new-empty-map reset above.
