## 1. Small protocol proposal

### 1.1 Binding and canonical record

Recommend one announcement `R`, bound to the configured endpoint and audience. The endpoint is its exact, nonempty configured raw URL string and must pass the existing client URL policy; the audience is its exact, nonempty configured string. Do not parse-and-reserialize, normalize, case-fold, follow redirects, substitute `Host`, or take either binding value from a response. Validate strings as Unicode scalar sequences encoded with strict UTF-8; reject invalid UTF-8 and lone surrogates (including unpaired escaped surrogates) rather than replacing them. Candidate bounds: endpoint at most 2048 UTF-8 bytes; audience 1–1024 UTF-8 bytes; decoded complete `R` at most 8192 bytes. Encode each binding string's UTF-8 bytes as canonical unpadded base64url.

Let `D` be the proposed, currently nonexistent domain `mcp-jack/server-key-rotation/min1`. `B` is exactly these seven ASCII lines joined by one LF, without a trailing LF, BOM, CR, spaces, or alternate spelling:

```text
mcp-jack/server-key-rotation/min1
<base64url(UTF8(exact_endpoint_url))>
<base64url(UTF8(exact_aud))>
<old_kid>
<next_kid>
<next_public_key>
<switch_at>
```

`old_kid` and `next_kid` are each exactly 43 canonical base64url characters decoding to 32 bytes. For a first transition, `old_kid` MUST equal `base64url(SHA-256(raw_authorizing_public_key))` for the independently trusted initial pin; for a successor, it MUST identify the settled current trusted `next_public_key`. Tentative or unacknowledged state never authorizes a new record. To recognize an exact duplicate of the retained latest `R`, instead verify its authorization with the stored `R.old_public_key`, even if settled trust has advanced to `R.next`; this duplicate exception does not make the old key eligible for responses. `next_public_key` is canonical base64url of exactly 32 bytes; `next_kid` MUST be recomputed from it. Admit both public keys under existing public-key rules. `switch_at` is canonical unsigned decimal Unix seconds, 0–999999999999, at most 12 digits, no sign or leading zero except `0`. Decode/re-encode checks reject padding, invalid alphabet, nonzero unused bits, and alternate encodings. Enforce bounds before unbounded parsing or cryptographic work.

```text
proof_next = Ed25519_sign(next_private,
    ASCII(D + "/next-proof\n") || B)
old_authorization = Ed25519_sign(old_private,
    ASCII(D + "/authorize\n") || B || LF || ASCII(base64url(proof_next)))
R = B || LF || ASCII(base64url(proof_next)) || LF ||
    ASCII(base64url(old_authorization))
```

`R` is exactly nine LF-separated ASCII lines, no trailing LF. Proof and authorization are canonical base64url encodings of exactly 64-byte signatures. There is no JSON/JCS or reserialization in `B` or `R`. Reject decoded records over 8192 bytes and encoded records over 10923 characters (the unpadded base64url ceiling for 8192 bytes).

**Crypto boundary:** use existing signature verification/admission rules; do not add sr1's separate Ed25519 equation or assert new backend guarantees. Cross-SDK acceptance at relevant existing Ed25519 signature edges is a gate, not a new cryptographic claim (`docs/threat-model.md`; `docs/design/server-key-rotation.md`).

### 1.2 Proposed tool and exact data result

Prefer one authenticated, read-only native tool, `jack.server.key`, with empty `params.arguments`, available to any registered active user. It grants no new authority and is not admin-only. The proposed result is an MCP `CallToolResult` with `isError: false`, exactly one `content` item of type `text`, and a `structuredContent` object with exactly these two fields and no unknown data members; `current` itself has exactly `kid` and `public_key`, with no extra members:

```json
{
  "current": { "kid": "<kid>", "public_key": "<base64url-32-bytes>" },
  "announcement": null
}
```

or:

```json
{
  "current": { "kid": "<kid>", "public_key": "<base64url-32-bytes>" },
  "announcement": "<base64url-of-one-complete-R>"
}
```

The sole text content is a JSON mirror of `structuredContent`. Parse and validate both surfaces, require exactly one record and semantic equality of their values, and reject extra/second content items or records, duplicate/unknown fields, malformed JSON, or a non-text item. Do **not** require raw JSON serialization equality between the two surfaces: the outer response signature authenticates the exact raw HTTP body bytes under the existing contract. The `current` tuple is the server key selected for the response signing-time sample: before `switch_at` it is `R.old`, at/after it is `R.next`. Strictly validate `current`: `public_key` must be canonical base64url for exactly 32 bytes, and its hash must recompute `kid`; `kid` must be canonical 43-character base64url for 32 bytes. For accepted `R`, including when `announcement` is null, check the authenticated timestamp assignment and schedule-selected key against the authenticated outer `kid` after ordinary outer authentication. For first-seen `R`, do not use its schedule for timestamp or selected-key checks until both proofs verify; a timestamp-assignment violation is `rotation_bad_schedule` and precedes any `rotation_bad_result` mismatch. After the applicable schedule check, require `current.kid` to equal the authenticated outer `kid` and decoded `current.public_key` bytes to equal the exact verification-key bytes. With no applicable `R` schedule, still require that exact current/outer key equality. A client cross-checks this tuple against its independently configured pin and/or accepted `R`; it is not itself authorization for the enclosing response. Return the exact latest published `R`, including after switch/expiry, until a later legally published record supersedes it. `announcement: null` never clears client state. No arrays, chains, multiple records, redirect URLs, or alternate discovery source.

A response header could carry independent signatures in a different proposal, but existing response headers are unsigned. Adding a header path would add a second parser, trust path, and duplicate-delivery handling; it is not impossible, but the tool is the smaller recommendation.

### 1.3 Authentication, result, and error precedence

Readiness gate: before any request/traffic, compare the locally configured positive-integer `response_window_seconds` with the immutable value stored in the initialized binding snapshot. Missing stored `W` for an initialized binding is recovery-required and must not default; known mismatch fails locally as candidate `rotation_window_mismatch` before traffic, outer-response processing, or callback, with no state mutation/adoption/recomputation. A matching configuration permits normal readiness subject to binding/state and clock checks. A first-time explicit OOB initialization must supply and persist `W`; it is not inferred from `R` or a response. Unknown, corrupt, fenced, unavailable, or unsafe-time state is not first initialization.

Only parse rotation content after ordinary response authentication succeeds using the client's pre-existing state. Outer errors are ordered exactly: ineligible outer `kid` is `unknown_server_key`, ordinary freshness failure is `timestamp_out_of_window`, and failed signature verification is `bad_signature`. For an outer key eligible under an accepted `R`, only after successful signature verification check the authenticated timestamp against its key assignment (`old.ts < switch_at`; `next.ts >= switch_at`); a violation is candidate `rotation_bad_schedule`, before result/content parsing. Then require the accepted schedule-selected key at that timestamp to match the authenticated outer `kid`; mismatch is `rotation_bad_result`. Once result data is parsed, require its strictly validated `current` tuple to equal the authenticated outer `kid` and exact verification-key bytes, also as `rotation_bad_result`. Apply retained-`R` timestamp/key checks when `announcement` is null. For first-seen `R`, do not use its candidate schedule for timestamp or selected-key checks until both proofs verify; then perform the timestamp-assignment gate before classification/callback, with `rotation_bad_schedule` taking precedence over a current/selected-key mismatch (`rotation_bad_result`). Never let an unverified timestamp direct trusted schedule policy. Signed remote errors are handled before inspecting rotation result data. An unsigned 401 remains status-only; ignore its body and all headers. `R` never authenticates its own enclosing response. Invalid or unverified input never mutates trust state. An ACK-confirmed authorized write may nevertheless commit even if the final gate returns an error; report the exact installed state and error, without rollback.

| Order | Check; stop at first failure |
|---|---|
| 0 | Before network/response processing, validate local binding/window/state readiness: configured positive-integer `response_window_seconds` must exactly match stored immutable `W`. Missing stored `W` for an initialized binding is recovery-required (no default); mismatch is candidate `rotation_window_mismatch`, before traffic, outer-response authentication, or callback, without state mutation/adoption/recomputation. |
| 1 | On the received response, check TLS/transport failure, redirect policy, stream handling, then response/body size limit. Failures stop before authentication parsing; enforce the body limit before parsing authentication. |
| 2 | Existing scheme-first/version and header multiplicity/grammar rules, preserving their specified precedence. |
| 3 | Outer key eligibility: an ineligible outer `kid` is `unknown_server_key`. |
| 4 | Ordinary outer freshness: an out-of-window timestamp is `timestamp_out_of_window`. |
| 5 | Verify the outer signature; failure is `bad_signature`. This preserves outer order: unknown key, freshness, bad signature. |
| 6 | After successful outer signature verification, for an accepted `R` check the authenticated `ts` assignment (`old.ts < switch_at`; `next.ts >= switch_at`), then require the schedule-selected key to equal the authenticated outer `kid`; assignment violation is `rotation_bad_schedule` and has precedence over key mismatch `rotation_bad_result`. Apply even when `announcement` is null; defer candidate first-seen `R` timestamp and selected-key checks until both proofs verify. |
| 7 | Authenticated remote error; otherwise result/body bounds, then exact result/envelope shape. |

Only then classify duplicate/conflict, equal `old_kid`/`next_kid`, retained-key reuse, and first-accept cutoff. These classification/reuse checks follow proof verification. |

Possible local categories include `rotation_bad_result`, `rotation_oversized`, `rotation_malformed`, `rotation_noncanonical`, `rotation_binding_mismatch`, `rotation_bad_key`, `rotation_bad_proof`, `rotation_bad_authorization`, `rotation_bad_schedule`, `rotation_expired`, `rotation_conflict`, `rotation_window_mismatch`, `rotation_clock_unsafe`, `rotation_revision_conflict`, `rotation_store_unavailable`, and `rotation_outcome_unknown`. These are candidate names only; existing static-client errors must not change. A server publication uncertainty likewise needs a candidate fail-closed service error, not a claim about an existing code. No error body or unsigned header is a pin update.

## 2. Schedule and eligibility proposal

Let `W` be the positive-integer `response_window_seconds` immutable in the initialized local binding. It is used for both response freshness and schedule overlap. A rotating client snapshot and a server publication snapshot each persist their own independently provisioned `W`; neither is carried by `R`, derived from network/profile/header data, nor negotiated with the other side. Use supported existing configuration and checked arithmetic; provision the value out of band alongside endpoint, audience, and pin. Client/server alignment is a deployment-owner choice, not an implied agreement. Every initialize/open/restore and pre-callback/final readiness gate compares configured `W` with stored `W`; mismatch is candidate `rotation_window_mismatch` before traffic/callback and does not mutate, adopt, or recompute state. Missing stored `W` for an initialized binding fails recovery closed, with no default. An equal configured/stored value is the only normal readiness path. The exact mismatch behavior is the same before first response processing, during ordinary refresh, after retirement, on restart restore, and at server publication restore: do not invoke HTTP/response authentication or callback on the client; do not publish/select a signer on the server; do not mutate pins, accepted `R`, retired keys, revision, or stored `W`. Restoring the exact old configured value returns to normal readiness; a different value requires a separately designed and explicitly authorized OOB migration/recovery, not implicit clear/reinitialize or reuse of accepted `R` under new settings. For a discriminating boundary vector, let `switch_at=1000`, stored `W=30`, and `R.old` retire at `t=1031`; at `t=1032`, config `W=60` makes old `ts=999` fresh by 33 seconds under the candidate setting, but the mismatch gate fires first, before HTTP/response authentication/callback, leaving the snapshot and retired-key state unchanged. Missing stored `W` never defaults; shrink from 30 to 15 also mismatches; equal 30 reload is a no-op, including an exact duplicate after retirement. An attempted callback/CAS replacement of W is rejected before callback (zero callbacks); an unknown ACK cannot authorize `W=60`. Offline restore uses persisted `W=30` for schedule derivation, never a newer local value. Server restore with stored 30/configured 60 stops rotation-enabled service before publication/traffic, with no fallback or mutation.

- Recommend publishing only when `switch_at > publication_now + W`; no maximum lead time. Once published, `R` and its schedule are immutable: one outstanding transition, no cancellation, replacement, reschedule, or queue. A successor may be proposed only after `t > prior_switch_at + W`, and only when the prior transition has completed its overlap.
- Server response signing chooses old iff the selection sample `t < switch_at`, otherwise next. The response-auth timestamp is that **same** sample, and the `current` tuple in the body is the selected key at that sample. Buffer the response and run a fresh final eligibility guard before success. If the selected key is no longer schedule-eligible at that guard (for example, old was selected and the switch passed), discard the precomputed signature/response and fail closed. Never fall back to the other signer, re-sign, or retry; the guard must not change the body to a tuple inconsistent with the signature's timestamp/key. A required signer unavailable means fail closed.
- A client uses a fresh final verification sample `t` and the existing `abs(t - ts) <= W` response freshness test. For an accepted `R`, old is eligible only when `t < switch_at - W`; both old and next are eligible for the inclusive interval `[switch_at - W, switch_at + W]`; next alone is eligible when `t > switch_at + W`. Also require old-key response `ts < switch_at` and next-key response `ts >= switch_at`. Without an accepted `R`, trust only the pre-existing pin.
- First-seen `R` is eligible for acceptance only when the fresh pre-callback authorization sample satisfies `t < switch_at`; equality is expired. An exact duplicate of the retained latest `R` is an idempotent no-op even after switch/expiry, subject to outer response eligibility, and can never reinstate old-key eligibility.

Clock policy for this candidate: live clock samples must be nondecreasing at each serialized binding gate. Any observed backward sample latches that binding unsafe until explicit recovery; clock catch-up does not clear the latch. No clock high-water mark is persisted, so cross-restart or backup-rollback detection is not provided. Irreversible key eligibility/retirement is conditional on a globally trusted nondecreasing clock; unknown time/history fails closed pending recovery. A forward jump may cause denial of service; there is no rollback oracle. These are design assumptions, not runtime claims.

The schedule always uses immutable `W` stored in the initialized binding, never a reloaded or candidate value. A window change is unsupported within an initialized binding even after retirement, duplicate delivery, or restart. Any future change would require a separately designed and explicitly authorized OOB migration/recovery; silent destroy/reinitialize or reuse of accepted `R` under new settings is forbidden. No migration is implemented here; if needed, owner choice must precede code. Client and server provision independent local values; alignment remains a deployment-owner choice.

Observable boundary table (`W=30`, `switch_at=1000`; timestamp window shown is inclusive `t-30..t+30`):

| Client final `t` | Fresh `ts` interval | Eligible outer key(s) with `R` | Valid `ts` for old | Valid `ts` for next | Honest server selection |
|---:|---:|---|---|---|---|
| 969 | 939–999 | old | 939–999 | none | old |
| 970 | 940–1000 | old, next | 940–999 | 1000 only | old |
| 999 | 969–1029 | old, next | 969–999 | 1000–1029 | old |
| 1000 | 970–1030 | old, next | 970–999 | 1000–1030 | next |
| 1001 | 971–1031 | old, next | 971–999 | 1000–1031 | next |
| 1029 | 999–1059 | old, next | 999 only | 1000–1059 | next |
| 1030 | 1000–1060 | old, next | none (old requires `ts < 1000`) | 1000–1060 | next |
| 1031 | 1001–1061 | next | none; old is unknown/ineligible | 1001–1061 | next |

Consequently, old `ts=999` at `t=1029` is valid (freshness 30 and schedule valid), but at `t=1030` it is freshness 31 and invalid even though both keys are in the schedule overlap. Next `ts=1000` at `t=970` is client-eligible (freshness 30 and schedule valid), although an honest server still selects old. At `t=1031`, an old-key response is `unknown_server_key` even with `ts=1001` fresh; a timestamp cannot restore eligibility. First acceptance at `t=999` may proceed conditionally on ACK; at `t=1000` it is expired. An exact duplicate after expiry is a no-op, never old-key revival.

## 3. Client state, acknowledgement, and recovery

### 3.1 Separate application-owned state and transitions

Static profile construction and imported credentials retain current behavior. Do not repurpose `Profile.kid`, add implicit rotation to static profiles, mutate a profile, or write SDK-owned files. Rotation is opt-in and uses an application-owned callback/store separate from user credentials and server registry/invite files. Its complete CAS snapshot includes exact public binding `(endpoint_url, aud)`, immutable positive-integer `response_window_seconds` `W`, current trusted `{kid, public_key}`, exact latest accepted `R` (if any), the `old_public_key` that authorized that `R`, a monotonically increasing concurrency revision, and bounded retired-key identity history. The callback receives the expected revision and desired snapshot. The expected revision must identify the exact persisted snapshot; that persisted snapshot and the desired snapshot must both carry the same exact public binding and persisted immutable `W`. A normal refresh/CAS cannot change either. Before invoking the callback, reject any attempted replacement of binding or `W`. ACK recognition, definite-failure handling, and unknown-outcome reconciliation validate exact binding, `W`, `R`, and revision against the expected/desired snapshot; no result may infer or adopt a different window. The `W` value is immutable per initialized rotating binding and must be compared with local configuration on every initialize/open/restore and before callback/final readiness gates. Retain the authorizing old public key explicitly with accepted `R`; do not try to reconstruct it from `old_kid` after promotion. Validate its admission and hash against `R.old_kid` when accepting/recognizing a record. Candidate history bound: the last 16 retired key identities (owner may revise); it detects reuse only while an identity remains retained. After retirement the authorizing key is history/duplicate-validation material only, never response trust. Keep private key material out of all public state.

| State/event | Trust and required effect |
|---|---|
| Initial `solepin` | Independently initialized pin and positive-integer local `W` only; persist both in the binding snapshot. Neither can be initialized from a server response. Trust only that pin and use the stored `W`. |
| First valid `R`, application ACK | Retain exact `R`, its validated authorizing `old_public_key`, next public key, schedule, and revision. Old/next response eligibility follows the table; ACK is required before using the new key. |
| After overlap, `nextonly` | Current trusted pin is next; old authorizing public key remains attached to retained `R` for exact duplicate/reuse checks, but is never a response key. Retire its identity subject to history bounds and trusted-clock assumption. |
| Exact retained-`R` duplicate | No-op, including after expiry; never re-add retired trust or change schedule/revision. |
| Successor `R` | Only after prior overlap end; its old key must be the current trusted next key. Preserve bounded reuse history. Replace the one retained `lastR` only after ACK of the successor snapshot. |
| Different pending/conflicting `R` | Reject with candidate `rotation_conflict`; do not replace current/accepted state. No durable `sr1` quarantine/fork guarantee. |
| Any `null` announcement | No-op; it never clears accepted state. |

There is one pending schedule, no cancellation, no replacement before overlap end, and no queued transition. Reject reuse of the current key or any key in retained history. An operator's knowledge of older, evicted keys is not an automatic global blacklist. A duplicate refers to the exact retained latest record; replacing `lastR` after a successor ACK does not imply unbounded past-record duplicate recognition.

### 3.2 Serialized ACK, CAS, and ambiguous outcomes

Before invoking the application callback, acquire a per-binding tentative-writer/busy token, serialize updates, and authorize first acceptance at a fresh time `t < switch_at`. Release the mutex before callback or network I/O, but retain the writer token: no other update may use tentative state, and concurrent identical refreshes converge only after ACK. The acceptance linearization time is this pre-callback authorization, conditional on ACK; it is not a promise that the physical response returns before `switch_at`. ACK may arrive after the switch: install the exact authorized `R` and schedule, do not roll back, then run the final gate against fresh time/state and the enclosing response. A late ACK may therefore commit without allowing this response's content to succeed.

Callback outcomes:

1. **Committed/acknowledged:** application confirms the exact desired snapshot reached its chosen durability level. Only then install/use accepted state or acknowledge first acceptance. Durability level is application-chosen; this proposal makes no platform-specific durability guarantee.
2. **Definitely not committed:** retain the prior snapshot and report no refresh success; continue only if the prior state remains eligible.
3. **Unknown after possible write:** immediately fence only that binding and prevent success at final gates ordered after the fence; do not imply an earlier authorized call can be revoked. Stop new traffic/content success on the fenced binding until an authoritative application reload/reconciliation verifies the exact expected or desired snapshot, including exact binding, persisted `W`, `R`, and revision. Never silently treat it as failure-before-write, roll back, reissue, adopt a changed `W`, or fall back to another key.

While a writer token is outstanding, the tentative snapshot is not trusted: final gates using the already committed snapshot may continue to succeed if that snapshot remains eligible, but no request may succeed on tentative pins. Serialize callback commit and installation with final-gate evaluation; installation/fencing is atomic, so a gate sees the full committed prior state or full new state/fence. An unknown-outcome fence applies to final gates ordered after the fence, not retroactively to a success authorized earlier. Final-gate authorization is the linearization point, not physical response-return order. A stale revision cannot overwrite newer state or authorize success from a captured pin. An exact concurrent duplicate can be a no-op only after the ACK and exact latest-state check. The final gate rereads authoritative state and fresh time and rechecks outer key eligibility, outer freshness, record/binding, and current result conditions before content success. Outer `unknown_server_key` precedes freshness, which precedes `bad_signature`, if a boundary has crossed. No mutex is held across callback or network I/O.

ACK means exactly the app's declared commit/durability result for the exact desired binding/`W`/`R`/revision snapshot; a definite failure retains the exact prior snapshot only if it remains eligible and its binding/`W`/`R`/revision validate. If callback outcome is unknown, fence this binding and prevent success at final gates ordered after the fence until reconciliation validates the exact authoritative binding/`W`/`R`/revision; do not imply that an earlier final-gate authorization can be revoked because its response physically returns later. Recheck configured/stored `W` at the post-ACK final gate. A mismatch blocks readiness/content success but never rolls back an ACK-confirmed exact snapshot.

**Deferred sr1 scope:** this candidate adds no generation/head chain, `server_id`, 24-hour stabilization, authenticated fork detection, durable quarantine, platform crash-durability contract, or persisted clock high-water mark. The independent application-owned unknown-outcome fence described above is not sr1 quarantine and is not a rollback oracle.

A missing/corrupt snapshot for an initialized binding is not an empty pin; fail closed and require separately authorized out-of-band recovery. Explicit initial setup independently supplies endpoint, audience, pin, and positive-integer `response_window_seconds` `W`. Once initialized, stored `W` remains authoritative and immutable across restart, duplicates, and retirement. Missing stored `W` fails closed with no default; a configured/stored mismatch does not clear retired keys or authorize recomputation/adoption. Exact matching-config restoration is the only normal readiness path. Changing `W` requires a separately designed, explicitly authorized OOB migration/recovery; no such migration is implemented here, and owner choice must come before code. Backup rollback remains unsolved; immutability is not sr1 anti-rollback protection.

### 3.3 Server publication and ACK outcomes

Server publication must keep exact published `R`, immutable per-binding local `W`, schedule, selected public tuple, and signer references consistent across restart. Persist `W` with binding/`R`/signer references; provision it OOB independently of `R`, endpoint, audience, and pin. Compare configured/stored `W` on initialize/open/restore and every pre-callback/final publication gate. Missing stored `W` for initialized state or known mismatch stops service fail-closed, without fallback, adoption, state mutation, or recomputation; exact matching-config restoration is the only normal readiness path. Validate the next signer matches `next_public_key` and is available before publication. Serialize publication with one writer token; do not hold a mutex across external persistence/network work. Definite publication failure leaves prior schedule/record intact. Unknown publication outcome fences rotation-enabled service until reload verifies exact authoritative publication/signer references and matching `W`; never select a fallback signer or expose a tuple inconsistent with committed schedule. Published state contains no private-key material; signer references/readiness are separate. Restore immutable schedule and `W` after restart; do not erase/cancel either. This is a single-owner recommendation, not a multi-instance/cluster contract. Client and server `W` values are independent local policies; no signed network agreement or negotiation is implied.

## 4. Security limits, refresh, and recovery

This transition proves continuity only while the old key remains trusted. A compromised old key can authorize an attacker-selected next key; next-key proof proves possession/readiness, not independent approval or recovery. Suspected current-key compromise, lost/unknown local state, or unjustified recovery requires independent out-of-band trust. Suppression is unsolved: if a client misses `R`, it rejects the post-switch outer key and needs manual OOB repinning. There is no TOFU, chain/catch-up, or trust of an announcement response's own key. Response signatures provide no confidentiality; existing TLS and endpoint policy remain necessary.

Refresh choice remains open. **Explicit caller-invoked refresh** is the current recommendation only: it avoids hidden SDK work, implicit connect calls and background callbacks, but leaves freshness/suppression detection to the application; no automatic retry of a side-effecting MCP operation. **Explicitly opted-in connect/periodic refresh** remains the unresolved D-3 alternative; it may improve timely discovery but adds calls, callback/persistence load, and lifecycle/scheduling behavior. Neither alternative is approved; any selected mode must be explicit, not a hidden default. In either mode, do not retry an operation whose response key is unknown: it may already have side effects.
