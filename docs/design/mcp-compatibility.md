# MCP compatibility design

**Status:** research and design only; no implementation or conformance claim. **Reviewed:** 2026-11-09. Scope: future mcp-jack bridge/gateway interoperability with MCP clients and servers. This document distinguishes repository observations, upstream requirements, inferences, and proposed tests. Recommendations are not approved product changes.

## Decision summary

| Decision | Recommendation | Gate / consequence |
|---|---|---|
| First bounded profile | Explicitly target legacy Streamable HTTP **2025-11-25** upstream, entered by stdio. Preserve one JSON-RPC object per POST. | Not general MCP compatibility; configure a JSON-response upstream for the initial bounded subset. |
| Streams and methods | Never flatten SSE or rewrite status. Preserve upstream-SSE signed 501 and no-SSE 405 as different outcomes. | A signed wrapper refusing SSE does not implement required SSE acceptance. |
| Modern MCP | Separate profile; do not imply legacy handshake/session semantics apply. | 2026-07-28 has per-request `_meta` and no initialize handshake. |
| SDK fixtures | Pinned official releases below are source-inspected E2E fixtures only. | No SDK installation, execution, CI wiring, or compatibility pass is claimed. |

The current official specification includes both legacy (through 2025-11-25) and modern (2026-07-28) eras. The first profile is intentionally limited, not full 2025-11-25 transport conformance.

## Repository observations and protocol eras

- Jack-Auth signs method, target, audience, key id, timestamp, nonce, and exact body hash (`spec/01-authentication.md:22-64`); response signature binds status and exact body (`:92-115`). `Accept`, `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, and `Mcp-Session-Id` are not signed. Headers may be validated/preserved as metadata, not treated as authenticated.
- Go accepts GET/POST before authentication (`server/middleware.go:109-112`), forwards verified requests (`:125-136`), turns event-stream into signed 501 (`:224-230`), and signs status/body (`:238-254`). Rust refuses event streams with signed 501 (`rust/src/server/http.rs:450-468`). TS returns signed 501 for `text/event-stream` (`ts/src/server/fetch.ts:255-270`).
- Current POST handling accepts response objects (`spec/02-authorization.md:39-48`, `server/verify.go:383-390`); array bodies are rejected as invalid requests (400).
- Local SSE guards: Rust `rust/src/client/transport.rs:302-307`; TS `ts/src/client/transport.ts:339-368`. Their RPC helpers (`rust/src/client/rpc.rs:201-209`, `ts/src/client/rpc.ts:117-125`) only set POST content type, not `Accept` or lifecycle. Go's local helper says it is not a full session/stream client (`client/rpc.go:343-346`). No MCP stdio bridge is implemented (`docs/release-plan.md:19-20`).
- The [2026-07-28 Versioning and Compatibility page](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md) describes modern per-request `_meta`, mirrored to `MCP-Protocol-Version` on HTTP, and no negotiation handshake; legacy through 2025-11-25 uses initialize. The fetch exposed page content, not HTTP status or redirect chain; no moved-page status is known. See also dated [2025-11-25 lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle.md) and [transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports.md).

- Historical transport distinctions: [2024-11-05](https://modelcontextprotocol.io/specification/2024-11-05/basic/transports.md) defines two-endpoint HTTP+SSE with an `endpoint` event (outside this Streamable HTTP profile); [2025-03-26](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports.md) permits batch arrays containing requests/notifications or responses; [2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports.md) requires single JSON-RPC objects. The dated modern sources are [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http.md), [stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio.md), and [versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md).
- Modern profile: servers MUST implement `server/discover`; clients MAY skip it. Every request carries `_meta` version metadata (HTTP also requires the matching `MCP-Protocol-Version`); `Mcp-Method`, applicable `Mcp-Name`, and schema `x-mcp-header` → `Mcp-Param-*` provide routing/projection. Header mismatch MUST yield HTTP 400 / JSON-RPC `-32020`. GET/DELETE and `Last-Event-ID` resumption are removed (ignore legacy session/resumption headers); there is no universal `initialize` handshake. These requirements are from the linked 2026-07-28 transport/versioning pages; versioning was fetched as content only, with no redirect or moved-page status asserted.

## Compatibility matrix

“Normative” is the specified wire rule. SDK acceptance of deviations is not normative.

| Wire item | Legacy 2025-11-25 | Modern 2026-07-28 | Bridge / local implication |
|---|---|---|---|
| Lifecycle | Initialize request → negotiated result → `notifications/initialized`; retain negotiated version and optional session id. | No initialize; each request carries `_meta`; HTTP mirrors version in header. | Relay exact caller initialize→result→initialized once. Do not perform a second handshake or rewrite capabilities. |
| POST Accept / body | Client MUST advertise both `application/json` and `text/event-stream`; one object per POST (2025-11-25; no batch). | Both response types; HTTP requests/notifications only, no client JSON-RPC responses. | Preserve both Accept values and exact body bytes. No JSON-only Accept rewrite or SSE flattening. |
| Version | Unsupported supplied version: HTTP 400. For legacy HTTP, if no header or other version signal exists, server SHOULD assume 2025-03-26. | `_meta` version required and HTTP header must match. | Test both invalid/unsupported 2025 version 400 and missing-version fallback with no negotiation state. |
| Session | Forward `Mcp-Session-Id` after assignment; a server requiring it SHOULD respond 400 when omitted; expired known session is 404. | No legacy session lifecycle. | Never blindly replay a call after session 404. |
| GET / DELETE | GET MUST offer SSE or return 405. DELETE terminates session; server may reject DELETE with 405. | GET and DELETE are removed; implementations SHOULD answer 405. | Distinguish no-GET 405 from signed upstream-SSE 501. No current DELETE passthrough claim. |
| Request response | JSON object or SSE stream; client MUST support both. | JSON or request-scoped SSE; stream closure cancels request. | A signed 501 refusal is not JSON-RPC success and means SSE is unsupported by this wrapper. |
| Notification / response POST | Accepted message MUST get 202 with empty body; 204 is not normative success. | Notifications use 202 empty; client-response messages are disallowed. | Preserve exact 202 empty response. Surface 204/200 as nonconforming even if an SDK tolerates it. Signed refusals are not JSON-RPC. |
| Framing / limits | Stdio is newline-delimited UTF-8 JSON-RPC; stdout is protocol only. | Same framing; modern message direction differs. | Strip only stdio delimiter newline before HTTP signing; add frame delimiter after response verification. Bound response body to 1 MiB (source-based cap; `server/middleware.go:17-20`, `client/transport.go:120-121`). |
| Stream refusal / timing | No stream transformation. | Same media-type response choices; request stream lifecycle differs. | Go SSE-to-501 may wait for handler return; Rust drops and TS cancels SSE. Source inspection only; no runtime timing claim. |
| Batches | [2025-03-26](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports.md) allows arrays of requests/notifications or responses; [2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports.md) removes them; 2025-11-25 requires one object. | One request/notification. | Test the version-dependent distinction; do not generalize legacy batch support. |

## Proposed bridge contract (not implemented)

1. Relay the caller's `initialize` → upstream `initialize` result → caller's `notifications/initialized` exactly once; store the negotiated protocol version and session id. Do not run a second handshake or rewrite capabilities.
2. For stdio, remove only the delimiter newline before signing the exact HTTP body bytes; after successful response verification, add the stdio frame delimiter. Bind/sign exact bytes. Framing and hop-by-hop headers may change; protocol metadata must not be arbitrarily rewritten.
3. Preserve `Accept: application/json, text/event-stream`. Do not replace it with JSON-only Accept or flatten SSE. Verify signed status/body before exposing or transforming either; signed body/status cannot be transformed before verification.
4. Session and protocol-version headers are not signed. Preserve and validate them as metadata. Current unsigned pre-auth DELETE 405 fails Go missing-auth verification except for 401; do not pass it through as an authenticated response. A future boundary needs authenticated signed 405 or a no-session profile.
5. Start with an explicit **no-session upstream JSON-response mode** as the bounded subset. Deployments requiring sessions are blocked pending a signed DELETE/refusal lifecycle. A deployment option is not transport negotiation and must be tested per server SDK.
6. Map signed non-JSON-RPC refusals to visible local transport/protocol failures, never fabricated JSON-RPC results.

### Pinned server JSON-response modes (source observations, not conformance claims)

| Server pin | Configuration and behavior |
|---|---|
| Go v1.8.0 | `StreamableHTTPOptions{Stateless:true, JSONResponse:true}`; GET/DELETE 405. `StreamableHTTPOptions`, `(*StreamableHTTPHandler).serveStateless`, `(*streamableServerConn).servePOST`, and `Write` describe the configuration and wire paths. Source: [server](https://raw.githubusercontent.com/modelcontextprotocol/go-sdk/v1.8.0/mcp/streamable.go). |
| TypeScript v2.4.0 | `createMcpHandler(factory, {responseMode:'json'})` drops mid-call notifications and returns the terminal result; subscriptions/listen remains SSE. Restrict handlers so no required notification is silently dropped. The pinned [HTTP serving guide](https://raw.githubusercontent.com/modelcontextprotocol/typescript-sdk/v2.4.0/docs/serving/http.md), section **“Shape the response stream,”** describes this mode and documents `createMcpHandler`. |
| Rust rmcp v3.9.0 | `legacy_session_mode:false, json_response:true` (defaults: `true`, `false`); simple terminal-first output is JSON, notification-first falls back to SSE, and subscriptions/listen stays SSE. Stateless legacy cancellation notification is ignored in the POST-notification branch; do not claim this mode provides functional cancellation. `StreamableHttpServerConfig` and `Default`, plus `StreamableHttpService::handle_post`, `serve_negotiated_request_directly`, and `handle`, identify configuration and request handling. Pinned server JSON-response modes are not interchangeable proof of notification support. The JSON-only gateway profile MUST restrict handlers so they do not emit required notifications: Go routes non-response messages to standalone SSE, TS `{responseMode:'json'}` drops mid-call notifications, and Rust falls back to SSE on notification-first output. Never approve silently dropped required notifications.

Pinned Go/Rust wire checks below are source-derived expectations, not executions:

| Request / response case | Go v1.8.0 / Rust rmcp v3.9.0 source behavior |
|---|---|
| POST Content-Type | On POST requests, `application/json` required; otherwise 415. |
| GET Accept | Must include `text/event-stream` on the legacy stateful GET path; otherwise 400 / 406. Stateless GET returns 405 before Accept validation. |
| POST Accept | Must include both `application/json` and `text/event-stream`; otherwise 400 / 406. |
| Accepted notification POST | 202 Accepted, empty body. |
| JSON request reply | `application/json` with the JSON-RPC body (Go/Rust JSON-response modes); verify and preserve exact signed status/body at the gateway. |
| Stateless GET/DELETE | 405 (Rust GET with no event store). |

A missing local-helper Accept header therefore fails Go/Rust, and the gateway MUST NOT rewrite the client's JSON+SSE Accept. General header copying is visible in Go `server/middleware.go:217-219,238-244`, Rust `rust/src/server/http.rs:435-436,488-499`, and TS `ts/src/server/fetch.ts:224-228,333-335`; this does not establish special session/version-header handling beyond each implementation's inspected code.

Cancellation and shutdown are separate gates: per [2025-03-26 transport](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports.md) disconnection SHOULD NOT be interpreted as cancellation; forward `notifications/cancelled` concurrently. HTTP DELETE terminates a session; stdio EOF shuts down the bridge process—neither means DELETE the upstream session nor cancel an individual RPC. Modern stdio cancellation MUST use `notifications/cancelled`; modern HTTP instead treats closing the request-scoped SSE stream as cancellation and does not expect a cancellation-notification POST, so bridge translation needs its own test gate. Sessionless JSON mode does not imply cancellation support: Rust ignores the legacy stateless cancellation notification, and a Go ephemeral peer may not locate the matching in-flight request (inference). Until negative controls certify this path, exclude cancellable long-running operations from the bounded MVP. No runtime cancellation claim is made.

## Proposed CI acceptance jobs (not wired or run)

- `mcp-compat-e2e` (proposed workflow target: `.github/workflows/ci.yml`; name/reference only, not edited): exercise the full official stdio client → bridge → signed gateway → official HTTP server chain as a 3-client × 3-server matrix (Go v1.8.0, TS v2.4.0, Rust rmcp-v3.9.0 on each side), for 9 cells. All nine cells are unrun and blocked on the bridge/gateway. Capture/assert each hop's method, target, exact body, status, media type, relevant headers, signatures, and JSON-RPC ids/results/errors. Record resolved commits and exact wire captures; keep fixture toolchains isolated.
- `mcp-http-client-transports` (separate proposed future-CI job; not wired or run): exercise each pinned official Streamable HTTP **client transport directly** against a controllable plain-HTTP MCP fixture, with no bridge or Jack wrapper in the baseline. The stdio-client chain above does not execute its client's HTTP transport, so its nine cells provide no direct evidence for these cases. Use real SDK HTTP transports (not handwritten JSON stub clients) and a controlled fixture server; do not imply three SDKs × statuses are nine passing cells.
  - For each client, run the 2025-11-25 configured initialize → initialized lifecycle (protocol version in initialize params; verify the negotiated HTTP version header), then a GET fixture response. Ensure GET is actually dispatched: Go `DisableStandaloneSSE:false`; TS's initialized notification starts GET; Rust baseline calls the public `StreamableHttpClient` GET method on the real reqwest implementation; connecting its `StreamableHttpClientTransport` worker and checking how that worker triggers/handles GET remains a separate integration gate. Exercise GET 405; JSON/non-SSE 501 (`application/json`, Jack-error-shaped body); and SSE 501 (`text/event-stream`, error body, zero events). Record request counts, callbacks/errors, deadlines, and subsequent `tools/call` outcome; bound waits/reconnects. Expected source observations: Go `connectStandaloneSSE` treats 405 as benign; non-SSE 501 warns/closes before status validation and may leave the call path usable, while SSE 501 reaches `checkResponse` and fails (not transient). TS `_startOrAuthSse` treats 405 as benign; either 501 content type throws `ClientHttpFailedToOpenStream` and invokes `onerror`. Rust `get_stream_with_max_sse_event_size` maps 405 to `ServerDoesNotSupportSse`; either 501 is an HTTP status error. Assert worker-level routing/failure propagation only through verified public worker behavior; do not infer termination semantics from transport-level errors.
  - POST controls: unsigned plain-HTTP fixture controls (no Jack wrapper in baseline): valid 200 JSON and 200 SSE; POST 501 with both content types must fail, never count as success. Exercise accepted notifications at 202 empty and tolerated SDK responses at 204 (and Rust empty 200 where relevant), while a separate strict normative oracle rejects every non-202 notification outcome. Report SDK-observed tolerance separately from spec conformance.
  - Separately proposed instrumented signing-wrapper boundary cases may use mcp-jack public signing-transport adapters, or an explicitly designed non-runtime integration seam: verify signed 501 before handing it to the official client or bridge, and unsigned DELETE 405 fails verification. This does not establish official-client support for Jack signing. Rust's reqwest trait integration is not proof of an existing signing seam.
- `mcp-public-consumers`: use public Go/Rust/TS package APIs against official-server lifecycle/raw-transport fixtures, not only native `callTool`/helper APIs or internal fakes; package archives follow existing `tools/consumer/{go,rust,ts}` patterns, with no new core dependencies.
- Gated modern cases: `server/discover`, request `_meta`/HTTP-version match, routing and schema projection, mismatch 400/-32020, no client-response POST, GET/DELETE 405, and HTTP stream-cancellation behavior.
- Framing oracles: split/coalesced chunks; multibyte UTF-8; JSON string newlines and escapes; stderr logging never on stdout; empty HTTP 202 emits no stdio frame.
- Refusal oracles: notification POST refusal goes to stderr and closes/fails the bridge without unsolicited `id:null`; refused stdio request retains its original id and becomes a local error (a reserved code such as `-32000` is an implementation recommendation, not a normative MCP rule, with clear origin). Signed POST 501 MUST remain visible failure; Go's optional GET may ignore a non-SSE 501, which is not acceptance proof.
- Future source-derived cases (not existing or executed tests): legacy `initialize` → `notifications/initialized` → `tools/list` → `tools/call`; negotiated and unsupported versions; disconnection.
- POST JSON success; upstream SSE refusal as signed 501; upstream with no GET as signed 405 versus upstream SSE as signed 501; normative 202 with empty body versus nonconforming 204 (normative conformance check rejects it even if a client SDK tolerates it); current unsigned pre-auth DELETE 405 failing authentication versus a future signed 405.
- Tampered status, body, or signature fails verification; a changed uncovered header with a valid signature demonstrates it is not covered. Preserve session/version headers; missing required session yields 400, expired session 404; clean reinitialize without automatic non-idempotent retry.
- Batch boundary: arrays legal in 2025-03 versus single objects in 2025-06/11, with local-wrapper arrays rejected as 400; interleaved ids, concurrent cancellation, bounded EOF/process cleanup, and stdout purity.

## Decisions still required

1. Confirm first profile and whether modern support is deferred.
2. Require explicit no-session JSON-response upstream mode, or defer session-required deployments until signed DELETE/refusal lifecycle exists.
3. Approve separate CI fixture toolchains and ownership/wiring of the three proposed CI jobs and their separate signing-boundary fixtures.

Until these gates close, this is a source-backed compatibility design, not evidence that a bridge exists, dependencies were installed, or interoperability tests pass.
