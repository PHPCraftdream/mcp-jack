Status: owner decision pending. This is a non-normative analysis for Task #293. Proposed changes below are not approved or implemented. No specification, fixture, workflow, version, or SDK change is made by this note.

## Current policy and implementation

[Spec 01](../../spec/01-authentication.md:11) requires HTTPS for every non-loopback connection; signatures do not replace TLS. [Interop section 9](interop.md#9-client-url-policy) defines a pure check of the raw URL: HTTPS accepts any syntactically acceptable host; HTTP accepts only canonical literal IPv4 in 127/8 or bracketed `[::1]`. It performs no DNS lookup or rewrite. Authority userinfo and percent escapes are refused. The fixture is the normative URL-policy oracle. Section 9.3 puts redirects and caller-supplied transports outside SDK control under an explicit contract; section 9.4 records fixture-driven coverage in all three languages.

Only Go has a `parse_reject` exception. The fixture is consumed by Go (`client/internal/testfixture/testfixture.go:36-62`, `client/transport_test.go:390-505`), Rust (`rust/tests/common/fixtures.rs:457-481`, `rust/tests/client/url_policy.rs:1-25,159-173,217+`) and TypeScript (`ts/test/client/transport/url-policy.test.ts:21-37,46-70,116+`).

## Threat analysis

Tor v3 onion addresses encode the service public key. Tor's [rendezvous specification](https://spec.torproject.org/rend-spec-v3), section 6, “Encoding onion addresses” (`[ONIONADDRESS]`), gives `onion_address = base32(PUBKEY | CHECKSUM | VERSION) + ".onion"`; `CHECKSUM = H(".onion checksum" | PUBKEY | VERSION)[:2]`; VERSION is byte `0x03`; checksum length is two bytes. Section 2.2.7 describes Tor client address validation. Source read date: 2026-11-27.

The address key binds service identity only when Tor verifies it through Tor protocol. It does not encrypt HTTP. If a connection does not go through Tor, a `.onion` name sent to an ordinary resolver leaks the name; a hostile resolver can answer with a chosen IP, and plaintext HTTP can then reach an attacker. This does not describe a transport that is guaranteed to use Tor SOCKS5h.

Jack request and response signatures (`spec/01-authentication.md:9-11,22-64,93-129`) provide authentication, integrity and freshness/nonce replay protection, not body encryption. Interception or redirection can expose a request body even if a later response fails verification. Clients act on responses only after pinned-key verification; a proxy or attacker can still deny service. The URL policy in all three languages lacks transport context, so a URL-only change cannot determine whether a SOCKS5h/Tor route is in use.

### Proposed (c) entrypoint and route-binding behavior

The following is a proposed design, not current behavior or an approved change. Keep profile data route-free: profiles have no SOCKS field. A pure profile loader/validator always refuses `http://<valid-onion>` because it has no transport context. Under this proposal, each SDK's constructor receives an in-memory profile plus an explicit SDK-owned SOCKS5h route and applies route-aware URL validation in place of the loader's route-free URL gate, while still validating every other profile field. This is construction, not a relaxation of profile loading: every JSON profile containing an onion HTTP URL is refused by the loader. The entry points are Go `NewClientFromProfile`, Rust `Client::from_profile`, and TypeScript `clientFromProfile`; today each of these constructors calls the same route-free validator as its loader before building the client (`client/rpc.go:844-858,916-926`, `rust/src/client/profile.rs:33-51,110-127`, `ts/src/client/profile.ts:128-136,174-187`), so the proposal changes the constructor path only. The TypeScript fixture must use an in-memory `Profile` object plus the route, distinct from JSON text passed through `loadProfile`, which must refuse it.

The raw-string policy function has no transport input, so it cannot classify a syntactically valid onion HTTP URL as simply “allowed.” It should return a classification such as `route_required`, or require a separate constructor-owned contextual gate. The raw-policy fixture expectation is `route_required`, with zero signer/transport activity until the caller-context gate. Without SOCKS5h opt-in, a constructor rejects before creating/using signer or transport. With explicit opt-in, the SDK constructs and owns the SOCKS5h route and can admit the URL; this is not a flag asserted by an arbitrary injected custom transport.

Signing transports repeat the policy check per request and bind that check and dispatch to the same private SDK-owned route. There is no direct fallback on route failure. In Go, the onion branch must use a separate unexported route field or distinct transport type holding the SOCKS5h `http.Transport`; it must neither read exported `Base` nor dispatch through `Base` or `http.DefaultTransport`. This matters because public `Base` can change, nil selects a default, and actual dispatch reads it at send time (`client/transport.go:110-143,212-229`). Non-onion paths may preserve public caller injection, but the onion path is distinct and has no path to either public `Base` or `http.DefaultTransport`. In Rust, the route is a private transport value within the SDK-built client, not a caller-supplied `Transport` trait object; each request's check and dispatch use that same value. In TypeScript, it is a private SDK-built fetch, not `fetchImpl`; each request's check and dispatch use that same private fetch. Proxy refusal or dial error fails the request without direct fallback. Go configures the SDK-owned `http.Transport` for SOCKS5h; Rust's `client-http` builder SOCKS option makes `HttpTransport` connect to the proxy and send the onion name in SOCKS CONNECT instead of invoking Hickory for that destination. TypeScript uses an SDK-constructed SOCKS-capable fetch/agent transport path. Whether a dependency is approved remains undecided; if an SDK cannot construct its own route, there is no qualifying opt-in. Existing built-in bridge support remains a separate explicit transport/config concern, not part of this client exception.

The fixture schema needs to encode policy classification plus context/path (or separate context cases), including raw-string policy, constructors with and without `socks5h_opt_in`, profile validation (always refuse), `from_profile`/equivalent constructors in both contexts, and signing transport with route/no-route. Existing `{name,url,allow}` cannot represent these distinctions. Extend it alongside [Interop section 9](interop.md#9-client-url-policy), especially `interop.md:28-30,59-67`, and assert exact cross-path expectations: raw policy is `route_required`; pure profile validation and all JSON profile loading refuse onion HTTP; no-opt-in constructors refuse before signer/transport; route-bound constructors can admit; signed requests recheck and dispatch only through the same owned SOCKS5h route and never fall back. The no-route fixture asserts zero signer calls and zero underlying transport calls. The proxy-failure fixture asserts a request error and zero direct dials. The cross-language fixture matrix must relate these expectations to Go `NewClientFromProfile` and its signing transport, Rust `Client::from_profile` and its private transport, and TypeScript `clientFromProfile` (using an in-memory `Profile` plus route) and its private fetch; its JSON-through-`loadProfile` case must refuse.

TypeScript has a WHATWG URL/Request serialization caveat ([Interop section 9](interop.md:30,67); `ts/src/client/transport/transport.ts:129-145`): raw strings can enforce exact lower-case spelling before parsing, but a parsed `URL`/`Request` serializes a normalized URL, so original uppercase host spelling cannot be recovered. Uppercase `.onion` refusal therefore applies only to raw-string entry points; parsed inputs are checked in canonical serialized form. If serialization lowercases the host, that canonical form can pass valid-onion syntax (under (c), only with route context). Do not promise rejection based on the original spelling of parsed input. Fixture cases should include raw uppercase refusal and a parse-produced normalized URL acceptance expectation.

## Recommendation and review sequence

Recommendation, not decision: start with (a), documenting supported routes. Separately seek owner decision and dependency/API approval for (b). If HTTP onion support is later required, prefer (c) over (d); do not recommend (d), because URL-only policy does not verify the route and HTTP can expose plaintext to an IP selected through ordinary resolution.

Reviewable tasks:

1. Document supported routes and record the owner decision; no code.
2. Choose proxy API and dependency approach per language.
3. Implement opt-in built-in SOCKS5h and local-stub tests with URL policy unchanged.
4. If the owner selects (c) or (d), propose spec and fixture changes for separate review, then implement and expand cross-language matrices. No spec edit belongs to this task.
