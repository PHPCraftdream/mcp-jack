# Design: MCP 2026-07-28 and the Events extension

Status: design, 2026-11-22; the owner answered the open questions on the same day (section 9). Not implemented. Release line: 0.1.0 was never published, so the first published release is 0.2.0 and carries this profile. The `mcp-jack/v1` wire bytes stay frozen as accepted at `c8ea1a0b37e68ab6dcdfb19fd0e427668cf1f343` ([versioning.md](../versioning.md)): this design only adds new identifiers and never reinterprets v1. The documents that say "frozen for 0.1.x" need rewording to the 0.2.0 line when the release PR is prepared.

Sources: [2026-07-28 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [Streamable HTTP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [Events overview](https://modelcontextprotocol.io/extensions/events/overview), [SEP-3415](https://modelcontextprotocol.io/seps/3415-events-extension), [ext-events specification](https://github.com/modelcontextprotocol/ext-events) (`specification/beta/events/events.mdx`). The Events extension is Beta; field names below follow that text as read on 2026-11-22 and must be re-checked against the pinned revision before implementation (section 8, M0).

## 1. Goal and acceptance

Goal: a Jack deployment can carry every feature of MCP 2026-07-28 and the Events extension, in all three SDKs (client and server side) and in the Go CLI (gateway, bridge), with the same guarantees Jack gives today: every byte the client acts on is authenticated by the server key, every request is authenticated by a user key, replay is bounded, and nothing unverified reaches the MCP host.

Acceptance:

- Each new feature in section 2 is either carried unchanged by the existing v1 wire or by a new, explicitly selected profile defined in this document.
- Every new verification rule has a generated vector, and every SDK runs every vector.
- Every client language works against every server language (3×3) for each new interaction class, and every webhook sender language works against every webhook receiver language (3×3).
- Official MCP SDK clients and servers work through the Go gateway and bridge in the modern profile.
- Legacy 2025-11-25 deployments keep working unchanged.

Scope rule from the owner: everything official is supported (all three Events delivery modes, all four endpoint-verification routes, the symmetric and the asymmetric Standard Webhooks signature) and earlier protocol versions keep working.

Non-goals: Jack does not implement events, tasks or MRTR semantics itself (the wrapped MCP server does); Jack does not add a policy engine; no multi-instance nonce sharing; the Jack server key is never used for Standard Webhooks `v1a` (section 6.3 uses a dedicated key).

## 3. Profiles and wire identifiers

- **Legacy profile** (today): Streamable HTTP of 2025-11-25 and 2025-06-18 (one JSON-RPC object per POST), `initialize` relay, JSON-only responses, SSE refused with signed `501 streaming_unsupported`. Unchanged. Older revisions break the frozen v1 body rule or need a second endpoint: 2025-03-26 allows batch arrays (v1 answers `400 invalid_request`) and 2024-11-05 HTTP+SSE needs a GET stream endpoint (deprecated by MCP itself). Their support is open decision 7 in section 9.
- **Modern profile** (new, release 0.2.0): MCP 2026-07-28. Requests keep the exact v1 request signature (`mcp-jack/v1/request`) and JSON responses keep the exact v1 response signature (`mcp-jack/v1/response`). New wire elements get new identifiers and never reinterpret v1:
  - signed streams: response scheme `s1`, domains `mcp-jack/stream1/open`, `mcp-jack/stream1/frame` (section 5);
  - webhook signature: header scheme `w1`, domain `mcp-jack/webhook1/delivery` (section 6).
- A server selects the profile per deployment (`legacy`, `modern`, or `both`). With `both`, the request era is decided first, after authentication: a request is modern if either version mirror (the unsigned `MCP-Protocol-Version` header or the signed `_meta` version) is ≥ `2026-07-28`; the two must then agree. This is fail-closed (stripping the unsigned header cannot downgrade a modern request to legacy handling) and supersedes the earlier "header present and equal" wording; see [spec/04-modern-profile.md](../../spec/04-modern-profile.md).
- A client opts into signed streams with the unsigned request header `Jack-Accept: s1`. Stripping it only turns a stream into the signed `501` refusal (fail closed; an on-path attacker can already deny service). A server never sends `s1` to a client that did not ask, so 0.1.x clients keep receiving `501`.
- Durable nonces and server-key rotation combine with the modern profile unchanged: the nonce is reserved before dispatch, including before a stream opens.

## 4. Modern request/response (classes T and H)

### 4.1 Server middleware (Go `server`, Rust `server`, TS `server`)

After the existing v1 verification (01 §4) and body classification (02 §2), in the modern profile:

1. `GET`, `DELETE` and other non-`POST` methods: signed `405`. (Legacy profile keeps today's GET rule.)
2. Version: in the modern era `MCP-Protocol-Version` must be present and equal to `params._meta["io.modelcontextprotocol/protocolVersion"]`, otherwise signed `400` with JSON-RPC `-32020` (the era is decided first, see section 3). Unknown version: the wrapped handler answers `-32022`; Jack does not keep its own version list.
3. Standard headers: `Mcp-Method` equals `method`; for `tools/call`, `resources/read`, `prompts/get`, `events/poll`, `events/stream`, `events/subscribe`, `events/unsubscribe`, `Mcp-Name` equals `params.name` or `params.uri` after base64-sentinel decoding. Mismatch, absence or invalid characters: signed `400`, `-32020`, with the request `id`. The nonce is consumed (as for every post-auth refusal).
4. `Mcp-Param-*`: Jack does not know tool schemas, so it forwards these headers unchanged and the wrapped handler validates them (the official SDKs do). Jack rejects only a header value with characters outside RFC 9110 field-value syntax.
5. `Mcp-Session-Id`, `Last-Event-ID`: removed before the handler sees the request.
6. Native `jack.*` tools in a modern-era request return `resultType: "complete"` and Jack `serverInfo` in `_meta`; their arguments and errors are otherwise unchanged. Legacy-era requests get byte-identical results to 0.1.x.
7. Responses `application/json`: signed with v1 exactly as today. `text/event-stream`: section 5 if the client sent `Jack-Accept: s1`, otherwise signed `501 streaming_unsupported`.

### 4.2 Client side (Go `client`, Rust `client`, TS `client`)

- RPC helpers build modern requests: `_meta` fields, `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` with the base64 sentinel rule (including the rule that a plain value matching the sentinel pattern is encoded).
- `x-mcp-header` projection: a helper that validates annotations exactly as the transport page requires (token syntax, uniqueness ignoring case, primitive types, safe integer range, static `properties` chain only) and drops invalid tools from `tools/list`. Projection runs before signing; headers are not signed (the body is).
- Era detection: optional `server/discover`; on a signed `400`, inspect the verified body: a modern JSON-RPC error means "modern server", anything else means fall back to `initialize`. A Jack refusal envelope (`{"error":{"code":"invalid_request"}}`) is never treated as an era signal.
- `CacheableResult`: Jack clients may cache verified results privately; never through a shared cache, whatever `cacheScope` says (documented, tested by a replay-to-other-request vector).

## 5. Signed streams (class S): `s1`

### 5.1 Shape

The server middleware reads the handler's SSE, signs each event and re-emits it. The Jack client verifies every frame before handing its data to the MCP layer.

Response headers:

```
Content-Type: text/event-stream
X-Accel-Buffering: no
Jack-Auth: s1 kid=<server kid>,ts=<ts>,sid=<sid>,sig=<sig>
```

`sid` is 16 CSPRNG bytes, base64url. Grammar as 01 §3 with the parameter set exactly `kid`, `ts`, `sid`, `sig`. Open signing string:

```
mcp-jack/stream1/open
<status>
<request-sig>
<kid>
<ts>
<sid>
```

Each SSE event carries one JSON-RPC message and one extra SSE field (unknown SSE fields are ignored by SSE parsers):

```
event: message
data: <JSON-RPC message, exact bytes>
jack: seq=<n>,ts=<ts>,sig=<sig>
```

Frame signing string (`seq` starts at 0, increases by exactly 1; `prev` is the open `sig` for frame 0, then the previous frame `sig`):

```
mcp-jack/stream1/frame
<sid>
<seq>
<ts>
<prev>
<data-hash>
```

`data-hash` = `base64url(SHA-256(data))`, where `data` is the SSE data value (data lines joined with LF) as UTF-8 bytes. The server always sends a final signed end frame with `event: jack-end` and empty data before it closes the stream.

### 5.2 Rules

- Server: drops handler `id:` and `retry:` fields; keep-alive comment lines are regenerated unsigned and carry no data; a handler message whose data exceeds `frameMaxBytes` (1 MiB default, at least 1024) ends the stream with a signed transport-signal frame that is the last message, followed by the end frame (spec/05 sections 2.18 and 3.2); per-identity concurrent stream limit and maximum stream duration are configurable; a client disconnect cancels the handler (request context cancellation), which is the MCP cancellation signal.
- Client verification order per stream: open header (as 01 §5 steps 1-6, scheme `s1`, `kid` pinned or rotation-known); then each frame: field grammar, `seq` continuity, `ts` within window of the client clock and not below the previous frame `ts`, signature over the chained string. Any failure aborts the stream with a client-side code (`stream_bad_frame`, `stream_out_of_order`, `stream_bad_signature`, `stream_stale_frame`) and nothing after the failing frame is delivered. A close without `jack-end` is `stream_truncated`; frames already verified stay valid.
- Server-key rotation: a stream is signed with the key that opened it. The server closes it (with `jack-end`) before that key's cutoff; a client rejects any frame whose `ts` is at or after the known successor activation for the stream's `kid`. The client then re-opens `subscriptions/listen` or `events/stream` with its stored cursor, as the MCP spec already requires after any break.
- Heartbeats (`notifications/events/heartbeat`) are ordinary signed frames; the client ends a stream that stays silent for `streamIdleMs` (default 90 s, error `stream_idle`; the MCP layer tightens it to 3 × the granted `heartbeatMs`) on top of Jack's per-frame `ts` window. A long quiet stream needs heartbeats more often than the Jack window, so the server grants `heartbeatMs` ≤ floor(window × 500) (milliseconds against a window in seconds).

### 5.3 Where streams are re-emitted

- In-process SDK clients that wrap an official MCP client (Go `http.RoundTripper`, TS `fetch`, Rust transport): after verification, re-emit plain SSE (`event: message`, `data:`) to the official client; never pass an unverified byte through.
- Go bridge (stdio): each verified frame becomes one stdout line; `jack-end` and keep-alives are not forwarded.

## 6. Webhooks (class W)

### 6.1 Server side: `WebhookSender` (all three SDKs)

The wrapped MCP server owns subscriptions and events; Jack supplies a sender it can use:

- Standard Webhooks: `webhook-id`, `webhook-timestamp`, `webhook-signature: v1,<HMAC-SHA256(secret, id.ts.body)>`, `X-MCP-Subscription-Id`; several signatures during secret rotation; same `webhook-id` and fresh timestamp on every retry; bounded retries (3-5 attempts within 10-15 minutes); `410` and `413` are final; body ≤ 256 KiB; `lastError` only from the fixed category list.
- SSRF: `https` only; resolve at delivery time, reject non-global addresses (IANA special-purpose registries for IPv4 and IPv6, including mapped and NAT64 forms), connect to the validated address with the original host in `Host` and SNI, never follow redirects; the same path is used for the verification challenge and the well-known document.
- Endpoint verification before the first delivery, all four official routes: (1) `verification` envelope with a single-use challenge compared in constant time; (2) operator allowlist; (3) out-of-band confirmation (a hook the application implements); (4) the receiver's `/.well-known/mcp-webhook-receiver.json` document (`{"receivers": ["/hooks/"]}`), fetched over the same SSRF-hardened path. Cached per `(principal, url)`.
- Signatures: HMAC `v1,` always; asymmetric `v1a,` when the application configures a webhook signing key (section 6.4); both may be present, space-delimited.
- Jack signature (section 6.3) on every delivery and challenge.
- Principal mapping: the subscription key uses the verified Jack identity `name` (stable across `jack.key.rotate`), not `kid`. The SDK exposes an identity re-check (`still registered`, `not revoked`) so the app can re-authorize at delivery time and send `terminated` on revocation, as SEP-3415 requires.
- The `secret` from `events/subscribe` travels in a signed body over TLS; Jack audit records never contain it.

### 6.2 Client side: `WebhookReceiver` (all three SDKs) and `jack events receive` (Go CLI)

- Verify before parsing: pick the secret by `X-MCP-Subscription-Id` (or pending secrets for a challenge), HMAC over the raw body, timestamp within 5 minutes, then the Jack signature with the pinned or rotation-known server key.
- Answer challenges in the HTTP response; never forward them. Return `503` for a delivery whose subscription id is not routed yet.
- Deduplicate by `webhook-id` only after a `2xx`; deduplicate events by `eventId` within a subscription; return `2xx` only after durable enqueue.
- Forward `gap`, `terminated`, `cursor` and `eventId` to the consumer unchanged.
- Verify `v1a,` signatures when present, with the key from the Server Card of the origin the client connects to (section 6.4); never from the delivery body or the challenge. Serve the `/.well-known/mcp-webhook-receiver.json` document when the operator enables route (4).
- The CLI receiver writes verified envelopes as JSON lines (stdout or a local socket); the host decides how to react. Event payloads are untrusted data.
- The stdio bridge never listens. `events/subscribe` with webhook delivery passes through it unchanged (class T); the delivery URL must point at a separately deployed receiver with a public https address. The host gives the receiver the subscription secret (receiver configuration or a private pending-secret file); the bridge never logs request bodies containing `secret`.

### 6.3 Jack webhook signature `w1`

```
Jack-Webhook-Auth: w1 kid=<server kid>,sig=<sig>
```

Signing string:

```
mcp-jack/webhook1/delivery
<aud>
<subscription-id>
<webhook-id>
<webhook-timestamp>
<callback-url>
<body-hash>
```

Binding the callback URL and audience means a delivery captured at one receiver cannot be replayed to another. The window is the Jack response window (default 30 s, at most 120 s); every retry carries a fresh timestamp, so the shorter window costs nothing. The Jack server key is not used for Standard Webhooks `v1a`, because `v1a` has no domain separation.

### 6.4 Asymmetric signatures (`v1a`, `v2a`) and the Server Card

The MCP Events text names `v1a,` (Ed25519, appended next to `v1,`), while the current Standard Webhooks specification deprecates `v1a` in favour of `v2a` (Ed25519 over SHA-256 of `endpoint_id.msg_id.timestamp.payload`). Jack verifies both and a Jack sender emits both. Both use a **dedicated webhook signing key**, never the server key (no domain separation, different rotation lifetime, no cross-protocol risk). The public keys are published in the MCP Server Card of the same origin the client connects to, as a JWK set (`kty`:`OKP`, `crv`:`Ed25519`, with `kid`) in `remotes[].extensionsInfo["io.modelcontextprotocol/events"].webhooks.signingKeys`; the optional `egressIpRanges` lives next to it (extension repository experimental-ext-server-card, `extensionsInfo` merged; revisions in [spec/modern-pins.md](../../spec/modern-pins.md)). A receiver takes keys only from that card, over https, from the pinned origin, without cross-origin redirects, never from a delivery or a challenge. Where a deployment has a Jack-authenticated channel, the same key set is also available through the read-only native tool `jack.server.webhook_key` so a receiver can cross-check the card (spec/06 R7.6).

Jack adds a Server Card publisher in the SDK servers and a card fetcher in the receivers. The authoritative rules are in [spec/06-webhooks.md](../../spec/06-webhooks.md).

Why both signatures: HMAC is what the MCP spec requires and what off-the-shelf receivers check; it proves the delivery comes from someone who knows the client's secret. `w1` proves it comes from the pinned Jack server and lets a receiver reject a leaked secret used by anyone else.

## 7. Test design

### 7.1 Generated vectors (`spec/fixtures/modern/`, reference verifier extended)

- Headers: method/name/version mismatch, missing headers, base64 sentinel (non-ASCII, padding, sentinel-looking plain values), invalid header characters, `x-mcp-header` annotation validity (every forbidden path: `items`, composition, conditional, `$ref`, `number`, unsafe integer, duplicate names ignoring case).
- Streams: valid chain; and one vector per check that fails only that check (wrong `sid`, gap, repeat, reorder, `ts` regress, stale `ts`, bad open signature, bad frame signature, oversize frame, missing `jack-end`, frame after cutoff, unknown scheme `s2`).
- Webhooks: Standard Webhooks known-answer vectors (shared with the upstream project's examples), multi-signature rotation, stale timestamp, wrong subscription id, challenge echo; `w1` valid and one vector per bound field.
- SSRF table: every IANA special-purpose range for IPv4 and IPv6, mapped and NAT64 forms, decimal/octal host spellings, redirect refusal.

Each SDK runs every vector (unit level), with a pinned vector count checked like today's VECTOR-SUMMARY lines.

### 7.2 Unit and property tests per SDK

Client header projection and era detection; server header validation and 405; native tools in both eras; stream signer and verifier state machines; cancellation propagation (handler observes cancellation when the client closes); per-identity stream limits; webhook sender retry schedule with a fake clock; SSRF dialer with an injected resolver (including DNS rebinding between resolve and connect); receiver dedup and challenge handling. Go fuzz targets for the SSE frame parser, header decoder and webhook verifier; Rust and TS property tests share their corpora.

### 7.3 Interop matrices (3×3, `interop/scenarios.json` extended)

| Matrix | Axis | Scenarios |
|---|---|---|
| modern-request | client lang × server lang | discover, `_meta`, header mismatch `-32020`, unsupported version `-32022`, GET/DELETE `405`, MRTR round trip, tasks get/update, `events/list`, `events/poll` with cursor and `truncated`, native tools in the modern era |
| stream | client lang × server lang | progress then final response; `subscriptions/listen` with `list_changed`; `events/stream` with `active`, `event`, `heartbeat`, `terminated`; client cancel observed by the server; tamper proxy drops, reorders, edits, truncates frames (each must fail with its code) |
| webhook | sender lang × receiver lang | subscribe through a signed request, challenge, delivery, retry with the same `webhook-id`, secret rotation dual-sign, `gap`, `terminated`, `w1` rejection with a wrong key |
| rotation-stream | client lang × server lang | server key rotation during a long stream: server closes before cutoff; client rejects a forged post-cutoff frame |
| durable-stream | client lang × server lang | nonce reserved before the stream opens; replay of the opening request refused after restart |
| era-mix | client lang × server lang | modern client to legacy server (fallback to `initialize`); legacy client to `both` server |

The SSRF refusals are a per-sender suite (3 runs), not a matrix.

### 7.4 Official MCP SDK end-to-end (`tools/mcp-e2e`)

Official clients (go-sdk, TypeScript, rmcp) × official servers, through the Go bridge and gateway, in the modern profile: discover, tools, MRTR, `subscriptions/listen`, and Events if the pinned SDK versions implement it (to be checked in M0; otherwise an in-repo fixture server implements Events in each language). Legacy cells stay as they are.

### 7.5 Coverage gates

New modules keep at least today's per-SDK coverage level; every verification step has a negative test that fails only that step; CI reports verdict counters per matrix.

## 9. Owner decisions

Answered by the owner on 2026-11-22:

1. **Version line: 0.2.0.** 0.1.0 was never published, so the first published release is 0.2.0 and includes the modern profile. The v1 wire bytes remain frozen; wording that ties the freeze to "0.1.x" is updated in the release PR.
2. **Everything official is supported.** HMAC `v1,` and asymmetric `v1a,`; poll, push and webhook; all four endpoint-verification routes; Server Card. Jack's own `w1` signature stays as an additional layer (it does not replace any official one).
3. **Earlier versions stay supported.** 2025-11-25 and 2025-06-18 stay in the legacy profile (`both` selection). 2025-03-26 and 2024-11-05: see decision 7.
4. **Rust HMAC: a recognised crate.** Use `hmac` from RustCrypto, the release line that matches the digest line of the existing `sha2 = "0.10"` (verify the exact pairing in M0); a local implementation is also allowed by the owner but not preferred. The new dependency goes through the existing licence, vulnerability and Dependabot checks and into the package inventory. Go and TypeScript use their standard libraries.
5. **Bridge scope** (adviser `om`, adopted): the bridge carries requests, poll and signed streams only; it never listens. Webhook delivery is received by `WebhookReceiver` or `jack events receive`. Reasons: the sender's SSRF rules make a loopback or NAT callback undeliverable, a public listener and durable secret/dedup state do not belong in a stdio process, and stdio hosts have `events/stream` and `events/poll`. Consequences: the bridge must run a long stream concurrently with ordinary calls (today it allows one HTTP call at a time; `cli.md` is reworded), a verified frame containing a raw LF aborts the stream, and a webhook-only subscription through the bridge gives a clear error pointing to the receiver. A `jack bridge --receive` mode is a possible later addition on request.
6. **Merge.** The design is documentation only and is merged directly into `main`.

Open:

7. **Earlier protocol revisions beyond 2025-06-18 (open; default applied).** 2025-03-26 batch arrays contradict the frozen v1 rule "one JSON-RPC object per body" (`400 invalid_request`); supporting them means a profile-level rule that the signed body may be an array. 2024-11-05 HTTP+SSE needs a GET stream endpoint and is deprecated by MCP. Until the owner says otherwise neither is supported (to be stated in the compatibility document).
