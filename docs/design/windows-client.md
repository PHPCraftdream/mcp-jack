# Windows client design

**Status:** design only; no Windows implementation or support claim. Repository observations below are cited with full repo-relative paths and line ranges. Every Windows API-specific behavior and Windows-specific implementation guarantee is **UNVERIFIED**; no Windows API semantics are asserted as established. This design note is the only current task; no code work has been performed.

## 1. Current state and evidence

The CLI's shared storage layer is implemented in `internal/cli/internal/storage/storage.go`: `ReadPrivate` checks the parent, regular-file type, mode 0600, ownership and size, then opens and stats the file and compares identity before a bounded read (`internal/cli/internal/storage/storage.go:13-34`). Creation reserves destinations exclusively with `O_CREATE|O_EXCL`, writes, syncs and closes; the same mechanism creates the owner marker (`internal/cli/internal/storage/storage.go:37-86`). Config decoding is strict and bounded through `ReadPrivate` (`internal/cli/internal/storage/storage.go:89-102`). These shared CLI internals serve CLI commands broadly, not just enrollment and bridge.

The Unix implementation enforces current-UID ownership, absolute clean paths, a directly owned mode-0700 parent, directory/non-symlink ancestors, root-or-current-user ownership, and no group/world write except a root-owned sticky directory (`internal/cli/internal/storage/storage_unix.go:13-44`). The non-Unix build-tag implementation returns `Owned=false` and rejects every private parent; Windows is included (`internal/cli/internal/storage/storage_other.go:1-14`). This is a deliberate fail-closed platform guard, not a partial Windows storage implementation.

A separate durable-store feature has another Go private-file backend under `durable/internal/ownedfile`: its Linux implementation is Linux-only (`durable/internal/ownedfile/private_linux.go:1-6`), and its non-Linux implementation returns `ErrUnsupported` (`durable/internal/ownedfile/private_other.go:1-13`). This backend is separate from the enroll/bridge client path; DACL work in the CLI alone would not enable the durable-store backend.

Key generation and bootstrap/enrollment enter through `keys.Keygen` and `keys.Bootstrap`/`keys.Enroll` (`internal/cli/internal/keys/keys.go:32-100`); configured transport loads config and keys (`internal/cli/internal/transport/connection.go:48-60`). The command router dispatches enrollment and bridge into their implementations (`internal/cli/run.go:122-130,243-250,273-277`), but the storage and process-stdio gates still block these flows.

For bridge I/O, Unix accepts pipes/FIFOs or Unix sockets, duplicates handles, makes them nonblocking and sets deadlines (`internal/cli/internal/stdio/process_io_unix.go:13-57,60-71`). Tests verify socketpair support and regular-file rejection (`internal/cli/internal/stdio/process_io_unix_test.go:328-377`). Comments explain that process stdio must be owned and interruptible, and bridge pipes exclusively used by this process (`internal/cli/process_io.go:11-12`); closing the bridge I/O is required to unblock reads/writes during cleanup (`internal/cli/run.go:56-57`). Non-Unix process I/O currently always fails closed (`internal/cli/internal/stdio/process_io_other.go:1-13`), and the executable emits `interruptible bridge stdio unavailable` (`internal/cli/process_io.go:24-35`). This guard is distinct from missing Windows handle classification and interruption logic. Do not treat console or redirected disk files as bridge protocol streams.

The stated platform support remains in `docs/operations.md:50-59`; it is not changed here. SDK packages `client`, `client/rotation`, `userkey` and `rotation` should remain free of CLI-internal Windows storage/stdio dependencies. Their production import closure is described in §6. Keep any platform implementation inside CLI-only `internal/cli/internal/storage` or `internal/cli/internal/stdio`.

## 2. Storage requirements and Windows mirror

The requirements below derive from Unix behavior; they are not claims that Windows provides equivalent semantics. In particular, do not assume an equivalent of the Unix root/sticky-ancestor policy. Define and approve Windows ancestor traversal policy separately.

| Requirement | Existing basis | Windows design target |
|---|---|---|
| Absolute, clean path; private direct parent | `internal/cli/internal/storage/storage_unix.go:18-25` | Require an absolute clean path. Require a private parent with owner-only equivalent access, inheritance disabled, and an explicit parent-traversal policy. Owner-only DACL/security descriptor implementation: **UNVERIFIED**. |
| Private file and owner | `internal/cli/internal/storage/storage.go:17-20`; `internal/cli/internal/storage/storage_unix.go:13-16` | Require regular file, owner-only access (Unix mode 0600 analogue), and expected owner SID. Windows owner SID/security descriptor checks: **UNVERIFIED**. |
| No symlink components; close lookup/open race | `internal/cli/internal/storage/storage_unix.go:27-42`; `internal/cli/internal/storage/storage.go:17-28` | Reject reparse points/junctions at every path component. Validate the opened handle's identity and security rather than trusting a prior path lookup. `CreateFile` reparse-point flags, handle-based checks, and `GetFileInformationByHandleEx`/security APIs: **UNVERIFIED**. |
| Bounded read and regular-file check | `internal/cli/internal/storage/storage.go:17-34` | Enforce the configured size limit on the opened object and reject non-regular objects. Windows classification/handle behavior: **UNVERIFIED**. |
| Exclusive create; no overwrite | `internal/cli/internal/storage/storage.go:37-79` | Preserve absent-destination reservation, fail if destination exists, and write/sync/close. Install an owner-only DACL with inheritance disabled atomically/in the create call, before the file becomes usable; a later read-time validation is additional defense, not a substitute. Windows exclusive-create and security-descriptor-at-creation behavior: **UNVERIFIED**. |
| SDK state registry replacement (out of scope) | `server/internal/state/statefile.go:349-388`; `internal/cli/internal/gateway/gateway.go:159-168` | This is an SDK `FileState` registry update used by gateway state loading, not a first-tranche CLI private-file requirement. Do not implement or claim Windows server registry replacement in the first tranche. Windows rename/replacement behavior: **UNVERIFIED**. |

Candidate API names are research leads, not validated instructions: owner SID/security descriptor and protected DACL inheritance; `CreateFile` with reparse-point flags plus handle-based checks; `GetFileInformationByHandleEx` and security APIs. Every Windows-specific behavior here remains **UNVERIFIED** until reviewed against Microsoft documentation and implementation tests.

## 3. First-tranche command scope

The Windows client tranche is deliberately narrow: client configuration and user-key loading, enrollment's invite read, bridge, and `jack keygen user` public/secret output creation. `keys.Enroll` only loads the connection and reads the invite; it does not locally write enrollment state (`internal/cli/internal/keys/keys.go:91-143`). Connection setup loads config and the user key (`internal/cli/internal/transport/connection.go:46-88`); bounded private reads are in `internal/cli/internal/storage/storage.go:13-34`. `keys.Keygen` creates public and secret outputs, with the user role representing the client key (`internal/cli/internal/keys/keys.go:32-63`). `jack keygen server` is excluded. `jack bootstrap` is also excluded: it locks server state and creates state plus an invite (`internal/cli/internal/keys/keys.go:65-89`). An invite read by client enrollment is in scope; bootstrap invite generation is a server-bootstrap operation and is not.

| Surface | First-tranche decision | Why / evidence |
|---|---|---|
| `jack enroll`, `jack bridge`, client config/user-key reads, `jack keygen user` | In scope | The requested client enrollment/bridge paths and user client-key output; `internal/cli/run.go:122-130,243-250,273-277`; `internal/cli/internal/keys/keys.go:32-63,91-143`; `internal/cli/internal/transport/connection.go:46-88`. |
| `jack bootstrap`, `jack gateway` | Excluded | Bootstrap creates server state/invite (`internal/cli/internal/keys/keys.go:65-89`). Gateway loads SDK state (`internal/cli/internal/gateway/gateway.go:159-168`); state rename is an SDK registry update (`server/internal/state/statefile.go:349-388`). |
| `jack events receive`, nonce commands, server-key commands | Excluded | These are independent receiver/receipt-state, nonce/durable-store, and server signing/config/seed workflows; command names are routed in `internal/cli/run.go:114-128`, receiver implementation in `internal/cli/internal/eventsreceiver/events_receive.go:153-200,259-266`, nonce implementations in `internal/cli/internal/nonce/nonce_admin.go:15-52` and `internal/cli/internal/nonce/nonce_reconcile.go:17-20,49-65`, and server-key implementations in `internal/cli/internal/serverkey/server_key_admin.go:31-80` and `internal/cli/internal/serverkey/server_key_signers.go:55-84`. `.github/workflows` is not involved. |
| Administrator commands (`invite-create/list/revoke`, `user-create/list/get/revoke/set-admin`) | Excluded | They are named in `internal/cli/run.go:118-121` and dispatched in `internal/cli/run.go:204-240`; implementations use shared admin functionality, including config/public-key reads and invite output writes (`internal/cli/internal/admin/admin.go:21-49,72-115,159-213`); incidental enablement through a shared storage backend is not authorization to include these commands. |
| SDK state-registry replacement / durable storage | Excluded | Separate SDK/gateway and durable-store backends; neither is required for the client tranche (`server/internal/state/statefile.go:349-388`; `durable/internal/ownedfile/private_other.go:1-13`). |

The CLI `storage.*` package is shared well beyond enrollment and bridge. Its Windows backend alone could make excluded flows usable. Any implementation must therefore retain explicit command-level scope/qualification: do not imply gateway, bootstrap, admin, receiver, nonce or server-key support merely because common storage works. Gateway and bootstrap remain unsupported in the first tranche.

## 4. Bridge stdio policy

The Unix source accepts only `ModeNamedPipe|ModeSocket` (`internal/cli/internal/stdio/process_io_unix.go:17-20`), so regular files are excluded and terminals are excluded by inference from that source predicate. Existing tests explicitly test regular-file rejection, not terminals (`internal/cli/internal/stdio/process_io_unix_test.go:365-377`). The operations policy also explicitly rejects regular files and terminals (`docs/operations.md:59`). The Windows target should accept anonymous pipes and, if approved, named pipes only when safely duplicable, in the expected direction, exclusively owned under the bridge model, and interruptible by owned-handle closure. Reject console handles and redirected disk files; a console handle is not simply interchangeable with every `FILE_TYPE_CHAR` classification.

Candidate classification leads: `GetFileType` (disk/pipe/character category), `GetConsoleMode` (console check), and named-pipe type/direction queries such as `GetNamedPipeInfo`. What these APIs report, whether they distinguish anonymous from named pipes as needed, and whether close/duplication gives the required cancellation behavior are all **UNVERIFIED**. Validate actual handles and ownership/lifecycle, not just a category label. Keep stdout protocol-only; diagnostics go to stderr. Is named-pipe support in scope, or should the first Windows profile accept anonymous pipes only? (Recommendation: support either pipe kind only after the interruption/ownership contract is demonstrated.)

## 5. Options

| Option | Cost / risk | Leaves unsolved |
|---|---|---|
| **(a) Windows DACL storage and Windows stdio in the existing Go CLI** | Implement and review ACL, path traversal, handle identity, interruption and native tests for only the first-tranche client files and commands in §3—not all commands that use shared storage and not server features. Security mistakes can weaken the existing fail-closed boundary. | Does not prove support until native Windows behavior and all required workflows are qualified. |
| **(b) DPAPI-protected key, instead of or in addition to DACLs** | Adds key wrapping/unwrapping lifecycle and platform-specific behavior. DPAPI API and semantics: **UNVERIFIED**. | DACLs remain necessary for the client config and invite files (and the key file unless DPAPI replaces it); server registry state is out of the first tranche (§3). DPAPI does not solve bridge stdio. Requires a threat-model decision. |
| **(c) Bridge in the Rust SDK** | Library scope must cover framing/size limits/JSON-RPC validation, lifecycle, signed HTTP transport/pin/trust, error mapping, timeout/cancel/EOF and I/O ownership. Security ownership must be explicit: either the library owns secure config/secret custody and stdio, or the caller injects signer/pinned connection and owns storage/pipe policy. | The CLI is not distributed: `README.md:44-49` says packages are unpublished and `jack` is not distributed. Consumers get the CLI by building from source; the SDK likewise remains a source-checkout dependency until separately authorized publication. A library does not magically deliver an executable. |
| **(d) Do nothing; document unsupported platform** | Lowest engineering cost; preserves current guard. | Windows users remain blocked from private-storage workflows and bridge. |

Package boundary for each option: **(a)** keep Windows code CLI-only under `internal/cli/internal/...`; **(b)** keep DPAPI code OS-specific and CLI-only under `internal/cli/internal/...`, leaving SDK key/config/storage callers unaffected; **(c)** a Rust library bridge adds no Go imports and cannot place Windows-only code in `client`, `client/rotation`, `userkey`, or `rotation`—any Go CLI adapter belongs under CLI internals; **(d)** makes no imports or code changes. All options satisfy the package rule if they keep OS-specific Go in CLI internals and do not modify production imports of those SDK packages. This preserves the constraint that these SDK packages depend only on standard-library and mcp-jack production packages; see the source-inspected production closure in §6.

## 6. Dependency and SDK impact

The production import closure was inspected by source across all non-test `.go` sources in the four requested packages (`client`, `client/rotation`, `userkey`, and `rotation`) and recursively imported first-party packages. Its first-party package edges are: `client -> root jack, client/internal/modern, client/internal/stream, client/internal/urlpolicy, client/stream, rotation`; `client/rotation -> root jack, client, rotation`; `userkey -> root jack`; `rotation -> root jack, rotation/internal/strictjson`. Major edge sources include `client/transport.go:17-22`, `client/stream/stream.go:10-16`, `client/internal/stream/stream.go:3-17`, `client/internal/modern/values.go:13-21`, `client/internal/urlpolicy/urlpolicy.go:4-7`, `client/rotation/controller.go:12-14`, `client/rotation/http.go:15-18`, `userkey/key.go:3-9`, `userkey/transfer.go:3-16`, `rotation/result.go:3-12`, and `rotation/internal/strictjson/strict_json.go:3-10`. Root-package production imports in the closure are located at `base64.go:3-7`, `ed25519.go:3-7`, `syntax.go:1-6`, `signing.go:1-6`, and `authheader.go:1-8`.

The exact standard-library package union in that production closure is `bytes`, `context`, `crypto/ed25519`, `crypto/rand`, `crypto/sha256`, `crypto/tls`, `encoding/base64`, `encoding/json`, `errors`, `fmt`, `io`, `math`, `math/big`, `net`, `net/http`, `net/url`, `reflect`, `regexp`, `sort`, `strconv`, `strings`, `sync`, `sync/atomic`, `time`, `unicode/utf16`, and `unicode/utf8`. No third-party imports were found in any production package in this closure. No `go list` or other Go commands were run; this is a source-inspection result, not an assertion about the exact compiler module graph.

The root module already requires `golang.org/x/sys v0.45.0` as an indirect dependency (`go.mod:1-7`). A Windows-only import would reuse the existing module/version and would likely reclassify it as direct in `go.mod`; the exact `go mod tidy`/module-graph impact remains **UNVERIFIED** because no Go tools were run. This Windows-only file does not remove the rule that OS-specific imports stay in CLI internals.

Tests are a separate closure and are not included in the production closure above. The Linux-tagged `client/rotation/controller_linux_test.go:16-20` and `client/rotation/rotation_state_vectors_linux_test.go:58-60` import `durable`. The portable `client/rotation/internal/portable/memstore_test.go:6-9` has no Linux build tag, is included in Windows builds, and imports `durable`; `durable/store.go:18-23` imports `go.etcd.io/bbolt`. Other test fixture/spec imports are likewise test-only. Keep OS-specific code in CLI internals and preserve one-way imports from CLI to those packages.

## 7. Test and qualification gaps

The Go job matrix explicitly runs on `ubuntu-latest` and `windows-latest`; both run `gofmt`, `go vet ./...`, and `go test ./...` (`.github/workflows/ci.yml:11-33`). Thus Windows executes the module-wide Go test suite, not merely a storage-only test subset: it includes the unsupported-platform storage test (`internal/cli/internal/storage/storage_other_test.go:1-25`) and the durable refusal test (`durable/tests/platform/private_other_test.go:1-29`), along with applicable tests across the module. This is not native Windows qualification of enrollment/bridge behavior: the process-qualification job runs only Ubuntu and macOS (`.github/workflows/ci.yml:62-104`). There is no cited native Windows qualification of the enrollment/bridge executable. The Rust Windows matrix job runs `fmt`, `clippy` and `test` (`.github/workflows/ci.yml:162-183`). The TypeScript Windows matrix runs on Node 20 and 22 and executes install, typecheck and test (`.github/workflows/ci.yml:218-240`). Unix process tests are Unix build-tagged (`internal/cli/internal/stdio/process_io_unix.go:1`; `internal/cli/internal/stdio/process_io_unix_test.go:1`). The Windows CLI artifact is cross-built from Ubuntu, and only a host-matching artifact runs `help` (`tools/binaries/README.md:7-31`). Cross-build success is not native storage, stdio or process qualification.

Add native tests that inspect the actual security descriptor owner/DACL, inherited versus explicit ACEs and access outcome/owner SID; test reparse-point/junction rejection and race-resistant opened-handle identity. Do not use `FileMode.Perm` or Unix mode-bit emulation as evidence of ACL security. Ideally verify denial for an unrelated SID using a real access check/impersonation or second account; runner availability is **UNVERIFIED**.

## 8. Recommendation, gates and owner decisions

Recommend **(a)** only if Windows client enrollment and bridge are product requirements. The design note itself is the only current task; no code work has been performed. If approved, proceed in this order as small, reviewable tasks:

1. Decide the owner/security boundary and approve the acceptance contract, including which client workflows and pipe kinds are in scope.
2. Design CLI storage and obtain an independent security review of the DACL, traversal, reparse-point and handle-identity contract.
3. Implement and test storage separately, including Windows-native DACL, reparse-point and handle tests.
4. Implement and test stdio separately, including ownership, direction and interruption behavior for the approved pipe types.
5. Wire native Windows CLI process qualification into CI.
6. Update operations/support documentation only after implementation and qualification evidence exists.

Keep changes in CLI internals. Defer DPAPI pending an explicit threat model. If Windows CLI support is not a requirement, choose **(d)** and retain/document the fail-closed behavior.

1. Is the Windows deliverable limited to client-side enrollment and bridge against a non-Windows Jack server? **Recommendation:** yes; leave gateway out.
2. Is current-user owner-only DACL the storage guarantee, without DPAPI in the first tranche? **Recommendation:** yes.
3. Which stdio handles are supported: anonymous pipes only, or anonymous and named pipes? **Recommendation:** both only when interruption and exclusive ownership are demonstrated.
4. Are native Windows CI tests required before claiming support? **Recommendation:** yes.
5. Is a Rust bridge preferred over the CLI? **Recommendation:** no for the first path given source/distribution friction; revisit if consumers are Rust applications.

**Unverified list:** all Microsoft API names and behaviors and their security semantics stated above; Windows ACL inheritance/owner/access-check behavior; reparse-point handling and handle-race properties; pipe classification, direction, duplication and close-to-interrupt behavior; DPAPI semantics; availability of an unrelated-SID test account/access-check mechanism on the chosen CI runner; exact future `go mod tidy` diff and module-graph/tool behavior. Windows server registry replacement is out of scope for this tranche and is not a support claim. Resolve API-specific entries against Microsoft documentation with a recorded review date before relying on them.
