# Durable nonce backend feasibility: transactional-library direction

**Status:** design only; not normative, implemented, or evidence of durability. The owner approved selecting a vetted transaction library for the Go operator gateway and subsequently approved raising the entire Go SDK/CLI module's compatibility floor to **Go 1.25**, with corresponding CI/consumer adaptation. Deployment builds retain the separately approved patched Go 1.26.10 toolchain. This removes the former Go 1.22 selection blocker; the proposed backend is bbolt v1.5.0, subject to source, dependency/advisory, platform, and runtime qualification below. No dependency or manifest has been changed here. Product versions and publication restrictions remain unchanged; no CGO requirement is introduced. No local tests, builds, or scans were run; executable acceptance remains parent CI only.

**Relationship to D2:** this document makes concrete one conditional Go storage design for [`restart-replay.md`](restart-replay.md). It does not change the accepted nonce-before-dispatch contract, inclusive expiry, persisted clock high-water `H`, immutable generation/window checks, unknown-outcome fence, or migration limits. It does not design a custom journal. No Rust or TypeScript dependency, API, or implementation is proposed.

## 1. Decision and blocker

`go.etcd.io/bbolt` is a plausible *candidate for vetting*, not yet a selected backend. Its embedded single-file key/value transactions, exclusive file lock, single writer, and pure-Go implementation fit a single-owner Go gateway better than a hand-built journal. Its official package documentation describes transaction commits, lock timeout, and durability-related options; its README also documents real filesystem and initialization caveats. These properties make it worth evaluating, not automatically safe for this protocol.

Historical version comparison before the owner approved the Go 1.25 target (the current source manifest has not yet migrated):

|---|---|---|
| `v1.5.0` (latest stable shown, 2026-06-21) | `go 1.25.0`, `toolchain go1.25.11` | Meets the newly approved Go 1.25 target; dependency and runtime qualification remain required. |
| `v1.4.3` (2025-08-19) | `go 1.23`, `toolchain go1.23.12` | Too new for Go 1.22; its newer module directive is not bypassed by merely using a patched compiler while retaining the project floor. |

The review did not establish that no Go 1.22-compatible transaction library exists; it establishes only that no safe bbolt version has yet been selected on the evidence reviewed.

**Decision boundary:** the owner explicitly approved the Go 1.25 floor after reviewing this comparison. Parent independently verified the v1.5.0 published manifest and upstream latest-release identity, MIT license, and relevant database/transaction source. The candidate may therefore target bbolt v1.5.0 rather than an unqualified older Go-1.22 pin. Exact dependency/advisory, CGO-disabled compatibility, platform and crash-recovery qualification remain implementation/CI acceptance gates; no checksum, lock or manifest entry is invented or changed here.

## 2. Conditional backend mapping

If a vetted version is later selected, put a narrow Go gateway adapter over one long-lived database handle and one application-owned admission gate. Keep database callbacks private, deterministic, bounded, and free of network, signer, registry, handler, or other external side effects.

### File, ownership, and startup

- Store the database under a trusted private local directory; on Unix target directory mode `0700` and database mode `0600`. File mode arguments alone are not an ACL/security proof on every OS. Do not put it beside or inside the existing registry/invite state file and do not treat that file as nonce history.
- The serving-open path must first establish that the file already exists. bbolt `Open` creates a missing database, so call it only for an explicitly initialized store; never let a missing initialized store become an implicit empty store. Use a positive bounded lock timeout (proposal: **1 second**), not the default indefinite wait. Hold the exclusive database ownership for the full serving lifetime. A second owner fails closed; no shared-file multi-process, network filesystem, distributed lock, or cluster mode.
- Explicit first initialization is a separate out-of-band operation for a proven never-used deployment. Write and validate versioned deployment metadata, immutable `W`, `H`, generation, and required buckets; obtain the required file and parent-directory durability before admitting. bbolt's README warns of corruption during first initialization on abrupt power loss. If initialization or its receipt is uncertain, do not serve; require operator recovery, not an empty-store retry.
- On each startup, validate the complete schema and state. A durably set `dirty_epoch`/unclean-session marker is written before opening admission. Keep it set while serving. Only after admission is closed, all authorized handlers are drained, and all operations are settled may clean shutdown durably clear it. If startup finds the dirty marker, perform bounded integrity/state and operation-receipt reconciliation under exclusive ownership before opening admission; never reset history or redispatch an uncertain operation. For an unknown operation, preserve its exact identity and a durable terminal no-redelivery receipt after reconciliation; if that receipt cannot be persisted/retained within bounds, remain fenced for explicit operator recovery. Do not clear the global dirty marker and later permit the same operation to be automatically redelivered. If reconciliation or marker write has an unknown outcome, remain fenced. This makes ordinary crash recovery possible without treating every crash as a permanent outage; it does not detect restoration of a self-consistent old backup.
- A current process that sees a commit error/unknown outcome disables admission immediately. If storage cannot durably record a new fence, rely on the already-durable dirty marker to force startup reconciliation; if even that precondition cannot be proved, an external startup gate must prevent reopening. Do not claim the library's lock can fence a process that has lost the underlying filesystem lock.

### Logical layout and atomic reservation

Use separate buckets/namespaces for metadata, live nonce reservations, expiry index, pending operation intents/no-redelivery receipts, and—if separately approved—public server-rotation state. The backend's ACID transaction does not include `FileState`, signer custody, handler effects, or other files. Those remain separate resources coordinated by the single-owner gateway's short final admission gate; do not claim cross-file ACID.

- Reservation primary key is exactly `raw_kid[32] || nonce[16]`; request ID is not part of uniqueness. A live reservation's value holds the authenticated request-identity hash, exact operation identity/receipt data needed for reconciliation, `ts`, and checked `retainUntil = ts + W`. A normal committed-operation receipt is part of this nonce value and has the same retention boundary: retain through `now <= retainUntil`, and expire it only after `now > retainUntil` is safely established under the durable `H` rule. Do not accumulate an append-only receipt per successful request. Count live reservations plus outstanding intents against the 4096-entry reservation capacity, inclusively; reserve a slot in the confirmed intent write so concurrent final commits cannot overbook it. Different request identities/bodies that collide on the same `(kid, nonce)` pair conflict; at most one can win.
- Expiry index key is `bigEndian(retainUntil)[8] || raw_kid[32] || nonce[16]`, allowing an ordered bounded prefix purge. Its entry and primary record/ordinary receipt are inserted/deleted atomically. Keep only unresolved unknown-outcome tombstones in a separate tightly bounded set; do not expire those automatically as nonce-cache rows, but do not treat them as an all-time deduplication ledger for every successful request.
- Metadata binds format version, deployment/store identity, immutable `W`, durable `H`, owner/generation state, and startup/operation recovery markers. Decode strictly and reject unknown versions, malformed or inconsistent rows, duplicates, impossible times, and missing metadata. Missing/corrupt state is not an empty cache.
- Reservation flow:
  - For the first intent transaction, after signature verification take a fresh raw sample and revalidate owner/store generation, exact immutable `W`, persistent clock-unsafe/fence state and readiness, `rawNow >= H`, freshness `abs(rawNow-ts) <= W`, and the captured active-key/enrollment snapshot through the gateway's coordinated final gate. Changed snapshots fail closed without retry. If `rawNow < H`, durably latch `clock_unsafe` before rejecting; never clamp or clear it at catch-up. If the latch write fails or is unknown, the already-durable dirty-session marker must force startup reconciliation and admission remains closed; otherwise an external startup gate is required.
  - Durably prepare a bounded intent keyed by `(raw_kid, nonce)` and carrying exact request/operation identity, `ts`, and checked expiry. Atomically advance `H` before any expiry-based decision, apply at most 128 index cleanup operations, and check the exact primary/intent keys and capacity including outstanding intents. A matching live reservation at `rawNow <= retainUntil` or any unresolved intent refuses without dispatch; remove a primary only when `rawNow > retainUntil`, atomically with its index deletion after the `H` advance. Reserve its capacity slot in the confirmed intent write. The intent blocks conflicting use of the pair but is **not** dispatch permission.
  - Only after a confirmed intent receipt may the adapter attempt the final `Update`. Take another fresh raw sample and revalidate persistent clock-unsafe/fence state and readiness, exact immutable `W`, `rawNow >= H`, inclusive freshness, owner/store generation, and the captured active-key/enrollment snapshot. Changed snapshots fail closed without retry. The transaction atomically stages new monotone `H`, converts the matching intent to the live nonce record, adds its expiry-index row, records the bounded ordinary operation receipt, and removes the intent. Dispatch only after this final transaction returns a confirmed commit receipt. This two-step database protocol makes the exact operation identity durable before a possibly ambiguous final commit; it is not a custom journal or an external side-effect transaction.
- Before the final reservation write, the confirmed durable intent already records the exact operation identity and prevents reuse of its `(kid, nonce)` pair. If the final commit is unknown, fence the live owner and do not retry. On startup, if the transaction committed, reconcile the live reservation/receipt and never dispatch that operation (the prior process received no commit receipt); if it did not commit, retain/reconcile the intent as a terminal no-redelivery tombstone and never automatically dispatch the operation whether the reservation is found or absent. These unknown-outcome tombstones are not time-expired: clear one only through explicit operator resolution that establishes the no-redelivery disposition. Bound their count; if the bounded reserve is exhausted, stop admission and remain fenced pending operator action rather than evicting a tombstone. A definitely aborted final transaction may clear its intent only after a confirmed cleanup commit; uncertainty during cleanup is treated as unknown, and cleanup never consumes the nonce. If the *intent-creation commit itself* is unknown, fence admission and require external/manual operator recovery before reopening even if startup sees no intent—the absence is not an operation receipt or permission to retry. A definite validation/duplicate/capacity refusal before any intent is committed does not consume the nonce. Any authorization refusal or later handler failure after a confirmed reservation leaves it consumed; a crash after that ACK but before handler dispatch does not automatically redispatch.
- Use ordinary single `Update` transactions only. The documented `Batch` callback may run more than once; it is unsuitable where callback side effects or automatic retry are forbidden. `Update` returning a callback error can represent a definite precommit abort; any other error must be classified conservatively as possible commit failure/unknown. The adapter must not leak error ambiguity into dispatch permission.
- Copy all bytes needed after a transaction closes; do not retain mmap-backed slices, share a transaction across goroutines, or keep long-lived read transactions that delay page reclamation. No network, logging side effect with semantic impact, callback into application code, or handler work inside a database transaction.

This preserves `restart-replay.md`'s inclusive expiry and `H` ordering, one-owner generation fence, unknown-outcome behavior, and complete possibly-live-history migration rules. In particular, do not change `W` in place, initialize empty after volatile history, evict live entries, use a startup timestamp floor, or claim local `H` detects an old but self-consistent backup. See that document's §§2 and 4–5 for the full normative-design boundary and migration barriers.

The expiry index orders nonce rows by big-endian expiry time, but purge work still has a strict batch cap. Because bbolt documents that deleting a cursor's current row and then calling `Next` may skip a row, collect at most the bounded key batch first and delete those keys afterward (or reposition with a reviewed seek strategy) within the transaction. Intents may be cleared after a confirmed definite-abort cleanup; terminal unknown-outcome no-redelivery tombstones are not expiry-index entries and are never garbage-collected automatically. If their bounded reserve fills, stop/fence admission for explicit operator resolution. Do not claim bounded purge based on an unbounded full scan.


If server-rotation state is ever stored in this database, keep it in its own namespace and preserve the rotation design's generation/head, immutable schedule, and multi-successor pending schedule rules. Store public statement bytes, public-key references, and bounded metadata only; private signing material stays in the existing protected signer provider. The registry/invite store remains distinct. Database transactions serialize only changes inside this database; the gateway gate coordinates registry/key/enrollment edits as described above and never claims cross-file ACID. A signer change likewise needs explicit coordination and cannot be described as part of the database commit. This document does not approve or implement rotation storage.

## 3. Resource bounds and safe operational modes

Proposed engineering starting limits for future CI qualification and implementation review (not additional product decisions): **4096 live reservations plus outstanding intents in total**, **64 authenticated admissions/second** (existing gateway-level rate limit), **32 concurrent in-flight validations**, **64 queued admissions**, at most **128 expiry-index removals per purge transaction**, a **16 MiB database budget**, and a separately bounded reserve of **64 unresolved unknown-outcome intents/tombstones**. At capacity, refuse admission without evicting a live nonce; if unknown-outcome records exhaust their reserve, fence admission for explicit operator resolution. Keep each transaction bounded; if more expired rows remain, continue in separate bounded transactions only after each transaction has safely advanced/preserved `H`. Do not scan an unindexed unbounded row set or claim a work bound from a row cap alone.

bbolt files retain freed pages for reuse rather than shrinking automatically, so deleting expired rows does not bound physical file size. The `MaxSize` option is documented as added in `v1.5.0`, not available in the Go-1.22-compatible `v1.3.11` candidate. Therefore the 16 MiB value is not enforceable by this design on an unselected old version without a separately reviewed volume quota or equivalent. Select a version/API with a reliable physical cap or provide reviewed external quota enforcement before promising that bound. Apply process memory/mmap and reader-lifetime limits as well. Do not enable `NoSync`, `NoGrowSync`, or `NoFreelistSync`; they weaken sync/recovery assumptions or, for `NoGrowSync`, are documented unsafe on ext3/ext4.

The initial platform proposal is local, trusted Linux/macOS storage only, and only after per-filesystem crash/durability evidence and CI qualification. Do not infer durability from bbolt's advertised Windows support or private-file support in the gateway. No NFS, network filesystem, multi-host access, removable/cloud-synced directory, read-only fallback, or unqualified filesystems. Upstream documents Linux ext4 fast-commit corruption caveats and specific kernel fixes; this is a qualification gate, not a blanket kernel certification. The cited bbolt docs do not prove macOS power-loss flush semantics either. If directory metadata, lock behavior, storage barriers, or crash recovery cannot be proven for the deployment filesystem, refuse durable mode. No healthy-filesystem success or ordinary unit test alone establishes power-loss durability or rollback resistance.

### Design vectors (not tests)

| Case | Required outcome |
|---|---|
| Same `(kid, nonce)`, different request identity/body | The pair is unique irrespective of request ID; at most one reservation wins. |
| Expiry equality and receipt retention | At `now == retainUntil`, reservation and ordinary committed-operation receipt remain live; only after `now > retainUntil` is safely established under `H` may they expire. A captured signed request is then stale and cannot be reused. |
| Crash after confirmed intent, before final transaction | No dispatch; resolve/clean up only with a confirmed safe outcome, and never automatically redispatch. |
| Unknown final transaction outcome | Whether reservation/receipt is found or absent after restart, do not automatically redispatch the operation. |
| Unknown intent-creation outcome, no intent found | Keep the manual-recovery/startup fence; absence is not permission to retry. |
| Purge followed by `H` rollback | Persisting `H` precedes expiry-based absence; a raw sample below `H` fails closed. |
| Database capacity | Count reservations and old intents inclusively toward 4096; enforce the qualified physical database-size budget too. Refuse at either limit without eviction or dispatch. |
| Same-`W` migration/recovery | Exact stored immutable `W` is required; mismatched `W` does not reopen admission or reset history. |

## 4. Feasibility and acceptance gates

Before choosing a version or implementing the adapter, the parent security/release lane must establish all of the following:

1. Qualify bbolt v1.5.0 against the owner-approved Go 1.25 target: exact source/provenance, dependency/advisory results, CGO-disabled compatibility, and the API properties below. The former Go 1.22 floor blocker is resolved by explicit approval, not bypassed.
2. Reviewed library source and exact-version API semantics for file locking, timeout, callback/commit error distinctions, commit receipt, mmap lifetimes, first initialization, all durability options, maximum database sizing, and recovery. In particular, a nil transaction error is a candidate receipt, while a commit error is treated as unknown unless source-level evidence supports a stronger conclusion.
3. Per-supported-OS/filesystem evidence for power-loss ordering, file and directory durability, lock exclusion, reopen/recovery, storage-barrier failure, and the dirty-epoch startup gate. Include abrupt first-init failure and crashes around every transaction and clean-shutdown boundary. Exclude unsupported environments explicitly.
4. Operational procedure for explicit never-used initialization, dirty-start reconciliation, exact unknown-operation resolution, corrupted/missing state, backup/restore, and separately authorized history-preserving migration. A local backup restore is not rollback proof; no automatic empty reset.
5. Qualified and enforced capacity/rate/queue/work/physical-size limits and refusal behavior. Include bounded expiry index, unresolved-tombstone cleanup, database growth after deletions, and storage exhaustion while persisting `H` or a fence. Startup scans/reconciliation are not bounded until physical-size and row/work caps are actually enforceable for the selected version/filesystem.
6. Integration design proving the final authenticated reservation occurs before dispatch, current key/enrollment/generation cannot race it, request refusal still consumes a committed nonce, and no state/handler changes are falsely included in the backend transaction.

After the gates above establish a maintained, compatible version and its source/artifact/recovery properties, the owner-approved direction permits selecting a version. Adding a dependency or beginning implementation remains a separate authorized task. This design does not authorize a Go implementation, migration, API change, Rust/TypeScript work, normative-spec change, or release action.

## Parent source qualification — 2026-11-10

Parent independently fetched the published v1.5.0 manifest (Go 1.25.0, toolchain go1.25.11), v1.3.11 manifest (Go 1.22), and upstream latest-release receipt for v1.5.0 published 2026-06-21. The v1.5.0 LICENSE is MIT with the Ben Johnson copyright notice. The owner then approved Go 1.25 for the whole SDK/CLI module, including compatibility/consumer adaptation, while retaining patched Go 1.26.10 deployment builds and unchanged product versions/publication flags. Earlier Go 1.22 compatibility blockers in this note are historical comparison, not a remaining permission gate.

Parent inspected [v1.5.0 db.go](https://github.com/etcd-io/bbolt/blob/v1.5.0/db.go) and [tx.go](https://github.com/etcd-io/bbolt/blob/v1.5.0/tx.go). Writable Open requests an exclusive lock and zero lock timeout waits indefinitely; use an explicit positive bound. Update returns callback/commit errors, so the adapter must conservatively distinguish precommit validation from possible commit failure. Default skip-sync options are false. With sync enabled, Commit writes and synchronizes data/freelist pages before writing and synchronizing metadata; rollback bookkeeping does not prove disk writes were undone. These are source facts, not independent power-loss qualification.

MaxSize bounds selected growth/allocation paths, not every file state: Open does not reject an already oversized file, empty initialization writes four pages without that check, and existing freelist allocation bypasses growth checks. The adapter must separately reject oversized existing files, verify initialization and growth boundaries under exclusive ownership, and qualify any external quota needed. Treat the proposed 16 MiB limit as a logical database-file budget, not a proven physical-volume/block-allocation cap. Do not advertise a physical bound from MaxSize alone. Full source/artifact advisory, license, OS/filesystem crash tests and fault-injection CI remain required before durable runtime acceptance.
