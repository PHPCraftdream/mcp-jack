# Dependency vulnerability scanning

**Review baseline: 2026-11-09.** This describes the intended CI-only checks in `.github/workflows/vulnerabilities.yml`; it is not a vulnerability assessment, release approval, or risk acceptance. The workflow was read as it exists at this review point. Existing CI, manifests, lockfiles, and product toolchain baselines are not changed by this document.

## Workflow and trust boundary

The `vulnerabilities` workflow runs for pull requests, pushes to `main`, the weekly schedule `29 5 * * 1` (Monday 05:29 UTC), and manual `workflow_dispatch`. Scheduled scans matter even when source and lockfiles are unchanged: upstream advisory databases can add records later.

Workflow permissions are `contents: read`; checkout sets `persist-credentials: false`. It declares no secrets, artifact upload, advisory cache restore, or repository-settings changes. The Go checks use `GOTOOLCHAIN=local` and `GOFLAGS=-mod=readonly`. Independent Go scan-matrix entries, separate Rust and npm jobs, and `fail-fast: false` on the matrices keep one finding from suppressing another scan. In particular, each Go level and each npm lockfile root is checked independently; a module-level result does not stand in for package/symbol analysis or the other npm tree.

The workflow calls the scanners directly; there are no local helper wrappers to control and no synthetic scanner tests or refusal fixtures are claimed. CI is the execution and acceptance environment for this check. No local scan, build, or test is implied by this document.

## Scope and exact scan commands

| Ecosystem/root | Graph and purpose | CI command |
|---|---|---|
| Go, repository root module (`go.mod`) | Three complementary source scans of the root module. `go.mod` declares `go 1.22` and no third-party requirements. The scan still includes Go standard-library/toolchain vulnerability data and, for package/symbol levels, test imports and source. | `govulncheck -version`<br>`govulncheck -format=text -scan=module`<br>`govulncheck -format=text -scan=package -test ./...`<br>`govulncheck -format=text -scan=symbol -test ./...` |
| Rust, `rust/` | Locked root crate graph with all declared features, development dependencies, build dependencies, and target-specific lockfile entries considered; no target filter or dev exclusion is passed. Uses `rust/deny.toml`. | `cargo deny --version`<br>`cargo deny --locked --all-features --config deny.toml check advisories` |
| TypeScript product/development graph, `ts/` | The committed `ts/package-lock.json` graph, including production and development dependencies; `optional` and `peer` are explicitly included. The package declares zero runtime dependencies, but its locked development tools are still scanned. | `npm --version`<br>`npm audit --package-lock-only --include=dev --include=optional --include=peer --audit-level=info --registry=https://registry.npmjs.org` |
| Licence-tooling graph, `tools/license/tooling/` | Its separate committed package lock is audited independently; it is CI tooling, not a shipped TypeScript dependency graph. | Same npm audit command, run with working directory `tools/license/tooling/`. |

Go's scan levels answer different questions: a vulnerable **module** is present in the dependency graph; a vulnerable **package** is included by the selected build; a vulnerable **symbol** is statically reachable according to the analyzer. They are not interchangeable. The module-only invocation intentionally has no package pattern or `-test`: govulncheck v1.1.4 rejects patterns for `-scan=module` (see upstream [`flags.go`](https://raw.githubusercontent.com/golang/vuln/v1.1.4/internal/scan/flags.go)). The package and symbol invocations explicitly use text output and `-test ./...`. The workflow also records safe scanner version evidence with `govulncheck -version`, `cargo deny --version`, and `npm --version` before the scans; these are separate from the advisory scan results.

Cargo's `--locked` prevents dependency resolution from changing `Cargo.lock`; `--all-features` includes `http`, `client-http`, and `interop` alongside default features. Cargo deny checks advisory policy only in this workflow command; it does not compile or execute product code. The checked graph is the lockfile metadata graph, not proof that every target or feature was built.

The npm command is audit-only: it does not use `npm audit fix`, `npm ci`, or product lifecycle scripts. It audits the lockfile graph without installing the product graph. Npm submits dependency information to the public registry audit API. Npm 10 can try the Bulk Advisory endpoint and fall back to Quick Audit; this audit deliberately includes dev/optional/peer dependencies rather than omitting them. An entry lacking a package version may be omitted by npm's bulk audit protocol, as documented by upstream npm.

## Advisory freshness, output, and failure meaning

- **Go:** govulncheck v1.1.4 uses the Go vulnerability database at `https://vuln.go.dev` by default. It reports known records available to that service; upstream provides no freshness SLA for this check. Text output is intentional. For text mode a finding at the selected scan level exits `3`; other scan, database, loading, or usage errors are nonzero (ordinary scan errors exit `1`, usage errors `2`). Findings must not be converted into a successful check. Do not switch to JSON, SARIF, or OpenVEX as a way to interpret status: v1.1.4 documents those formats as exiting successfully regardless of findings. See upstream [exit codes and limitations](https://pkg.go.dev/golang.org/x/vuln/cmd/govulncheck@v1.1.4#hdr-Exit_codes), [exit-code definitions](https://raw.githubusercontent.com/golang/vuln/v1.1.4/internal/scan/errors.go), and [source flags](https://raw.githubusercontent.com/golang/vuln/v1.1.4/internal/scan/flags.go).
- **Rust:** cargo-deny uses the RustSec advisory database (`https://github.com/RustSec/advisory-db`) and the online fetch path on each run. No advisory database cache is restored and there is no offline fallback. A database fetch, open, advisory parse, or scan error returned by cargo-deny is a failed/incomplete check, never evidence of a clean graph. Upstream's tagged [`db.rs`](https://raw.githubusercontent.com/EmbarkStudios/cargo-deny/0.20.2/src/advisories/helpers/db.rs) propagates those failures; it does not use a cached database as an online fallback. The same source warns and skips on directory-entry traversal errors, a limitation of the scanner rather than evidence that every database file was read. `maximum-db-staleness = P90D` is cargo-deny's default only when fetching is disabled; it is not a freshness cap for this online job. There is no configured vulnerability-severity threshold: upstream cargo-deny treats all vulnerability advisories as errors. The `unmaintained = all` default also errors for all matching unmaintained advisories; yanked versions have a distinct default warning, not a security-pass signal. The checked `rust/deny.toml` contains no advisory `ignore` overrides. References: [advisory configuration and staleness semantics](https://embarkstudios.github.io/cargo-deny/checks/advisories/cfg.html), [common options](https://embarkstudios.github.io/cargo-deny/cli/common.html), and [`check` command](https://embarkstudios.github.io/cargo-deny/cli/check.html).
- **npm:** npm asks `https://registry.npmjs.org` for current registry advisory data; there is no configured freshness SLA or maximum age. A failed or invalid Bulk Advisory response may prompt npm's documented Quick Audit fallback. If the final report contains an `error`, npm's [`audit-error.js`](https://raw.githubusercontent.com/npm/cli/v10.9.4/lib/utils/audit-error.js) throws; this is a failed/incomplete check, not a clean result. The [`audit.js` implementation](https://raw.githubusercontent.com/npm/cli/v10.9.4/lib/commands/audit.js) applies the report exit code after error handling. `--audit-level=info` is the lowest configured threshold, so findings at any npm severity fail; this option changes the failure threshold, not the report contents. See [npm audit's endpoint and exit-code documentation](https://raw.githubusercontent.com/npm/cli/v10.9.4/docs/lib/content/commands/npm-audit.md).

All three data sources are upstream-maintained and can lag or change. A successful run describes the selected graph and database responses at that run time only; it is not a guarantee about future advisories, undisclosed issues, or every build configuration.

## Limits and excluded graphs

- Go analysis is static and build-configuration-specific. This workflow checks Linux's default environment and does not enumerate platform build tags/GOOS/GOARCH combinations. Reflection calls are not visible to source analysis; `unsafe` can cause false negatives; interface/function-pointer analysis can be conservative and produce false positives or imprecise call stacks. A package/symbol result is not dynamic execution evidence or proof that a vulnerable path can or cannot be exploited.
- Rust advisory scanning consumes dependency and advisory metadata, not compiled binaries, executed tests, unsafe-code behavior, or runtime reachability. Optional/all-feature lock graph coverage does not prove all platform behavior.
- npm relies on registry advisory coverage and the locked tree data; package metadata absent from the audit request can limit coverage. The two npm roots are audited separately, not merged.
- The checks cover the repository root Go module, `rust/Cargo.lock`, `ts/package-lock.json`, and `tools/license/tooling/package-lock.json` observed on this review date. Generated/package-consumer graphs, generated consumer install trees, licence fixtures, and ephemeral dependency graphs for `npx`, `go-licenses`, cargo-deny itself, or GitHub Actions are not covered by these invocations. No OS package, container/base-image, vendored-code, or compiler/toolchain vulnerability guarantee is made. Add any new product or tooling dependency root only after explicitly reviewing and updating scanner scope.

## CI acceptance and triage

Acceptance is a maintainer review of the actual CI run for the proposed commit: confirm each Go matrix entry and both npm roots ran, the Rust advisory job ran, and every expected job completed successfully. The workflow itself does not change branch-protection or required-check settings; any project-required status policy must require these checks. A missing, skipped, cancelled, timed-out, setup-failed, database-fetch-failed, transport-failed, or parse-failed job provides no clean-scan evidence. Do not reclassify any nonzero result as clean; distinguish scanner/setup/data-service failure from an advisory finding and rerun or investigate the former.

For findings, inspect the named advisory, affected package/module and version, scan level, dependency path, and relevant source/build scope. Fix or remove/update the affected dependency where feasible. If the owner proposes retaining it, require a narrow, documented, human risk decision for that specific finding before acceptance. There is no preauthorized risk acceptance, automatic allowlist, severity downgrade, advisory ignore, or scope weakening in this policy. Workflow success alone is not an approval, and this document does not claim that any current run passed or that any dependency is vulnerability-free.

Retain only ordinary text diagnostics needed for CI triage (tool/check identity, affected package and version, advisory identifier, and relevant path). Do not enable debug/verbose output, dump environment variables, tokens, registry config, or raw JSON/SARIF/VEX, or upload scan reports as artifacts. The workflow is read-only and does not change dependency locks, install product trees, run product scripts, or alter repository settings.
