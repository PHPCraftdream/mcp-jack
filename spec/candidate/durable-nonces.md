# Candidate profile: durable authenticated nonces

**Status:** candidate normative for a future explicitly selected durable profile only; not current SDK behavior, a current durable guarantee, freeze, or Task 57 acceptance. The owner-selected mechanism is a durable authenticated nonce commit before any authorization/state mutation or wrapped-handler dispatch. A timestamp startup floor is rejected and MUST NOT be used as an alternative or fallback. This text makes concrete candidate technical semantics; it does not approve an implementation or platform durability claim.

## 1. Scope and unchanged v1 behavior

The candidate preserves all existing `mcp-jack/v1` request and response signing bytes, Ed25519 rules, strict base64url, method/target/audience/body hashing, inclusive freshness, and pre-authentication failure precedence from [../01-authentication.md](../01-authentication.md). It changes replay-state durability only for a deployment that deliberately selects this profile. Do not reinterpret a v1 signature, profile, static pin, user key, credential, registry, invite, or current SDK as durable-profile opt-in. Invalid signatures and all failures before successful authentication MUST cause no nonce reservation.

For accepted requests, the unique nonce key is the exact authenticated `(kid, nonce)` pair, independent of request id or body. Bind the stored reservation to the exact v1 request-signing bytes and deployment-local operation identity, not to a reserialized request, JSON-RPC id alone, or an assumed database row number. Let `S` be the exact UTF-8 bytes of the existing eight-line `mcp-jack/v1/request` signing string (01 §3.1), `sig_raw` the exact decoded 64-byte authenticated Ed25519 signature, `kid_raw` the exact 32-byte public-key hash, and `nonce_raw` the exact 16-byte nonce. Before preparing an intent, allocate a 16-byte `operation_id` from the configured CSPRNG and durably bind it to the deployment/store identity. The local intent key is:

```text
intent_id = SHA-256(
  ASCII("mcp-jack/durable-nonce/intent/v1\n") ||
  uint16be(len(deployment_id_utf8)) || deployment_id_utf8 ||
  kid_raw || nonce_raw || sig_raw || SHA-256(S) || operation_id
)
```

`deployment_id_utf8` is the exact, locally provisioned, nonempty deployment identity in the store metadata, at most 1024 UTF-8 bytes; it is not supplied by a request and is not a network trust root. `operation_id` is unique within that deployment for all retained intents/receipts; on collision, allocate a new ID before any intent commit. This domain is local storage identity only and is never signed on the wire. The digest binds the exact existing v1 signing bytes plus the raw authenticated signature and local operation ID; do not parse and reconstruct `S` to compare operations. Preserve `S`, `sig_raw`, `operation_id`, and `intent_id` in the bounded exact intent/receipt record as needed for byte-for-byte reconciliation. The request signature itself already authenticates the exact HTTP body hash and all v1 fields; do not invent a second request canonicalization.

Portable outcome comparison uses only the backend's exact persisted intent/receipt fields and byte equality, not an external ledger or opaque receipt-token ordering. A confirmed receipt is the tuple `(format_version, deployment_id_utf8, store_generation, intent_id, operation_id, kid_raw, nonce_raw, SHA-256(S), sig_raw, ts, retainUntil, outcome=committed)` with every byte/string/integer equal to the prepared intent and exact desired reservation. A definite noncommit is recorded for the exact `intent_id`. For a final-transaction definite abort after a confirmed intent, it is authoritative only after the backend confirms that no matching reservation committed and confirms cleanup so no unresolved intent remains. For a definitely aborted intent-creation transaction, it is authoritative only when no intent/reservation was committed. A cleanup with unknown outcome is unknown, not definite noncommit. Unknown is any outcome that cannot establish one of those exact results. After restart compare the exact persisted fields; never infer commit from a merely similar operation, a row count, or absence alone. This receipt is local transactional state, not an independently trusted external operation ledger.

Another authenticated request with the same pair conflicts, even if its body/request id differs. A successfully committed nonce is consumed even when later authorization, native tool validation, handler execution, or response generation fails. The protocol does not provide exactly-once handler effects. A committed reservation blocks future admission; it does not undo already authorized work.

For the enrollment exception, verify the submitted key and the existing signature/hash binding as specified in [../03-user-management.md](../03-user-management.md); then durably reserve before invite consumption, enrollment, or other state change. Do not alter enrollment parsing or error ordering.

## 2. Authentication, freshness, and admission linearization

The selected durable profile requires configured `W` to be a positive integer number of seconds, at most 120; 30 seconds is the current v1 default. This is a candidate profile default, not a claim that current implementations have a durable backend. It is immutable for the store generation.

| HTTP | Code | First applicable post-signature failure |
|---|---|---|
| 401 | `timestamp_out_of_window` | Fresh final raw sample fails inclusive freshness, or checked expiry arithmetic/domain fails. This is not a committed replay result. |
| 401 | `replayed_nonce` | Exact `(kid,nonce)` already has a live committed reservation. This existing error precedes capacity errors; do not replace it with `503 capacity_exhausted`. |
| 503 | `state_changed` | Ready store, but captured accepting owner, owner/store generation, immutable W, active-key, registered-caller, or enrollment snapshot changed. |
| 503 | `clock_unsafe` | Final raw clock sample is invalid/out of domain or below H and the unsafe fence was durably latched. |
| 503 | `durability_unavailable` | Store not ready/already fenced; replay/intent lookup unavailable; conflicting unresolved intent/tombstone; required H/unknown fence or intent cleanup cannot be confirmed; forward-H write is uncertain; or any intent/final commit outcome is unknown. |
| 503 | `capacity_exhausted` | Atomic capacity check fails after replay/intent checks; no live or unresolved row is evicted. |

### Admission sequence

The verification-entry sample is preliminary only. Before crypto, capture immutable active-key/registered-caller/enrollment snapshot, positive immutable W, accepting owner and store generation. After valid signature, the intent transaction takes fresh raw time and revalidates the captured state, W, H, freshness, replay and capacity; confirmed intent is not dispatch permission. After confirmed intent, a second fresh raw sample and full revalidation precede the final transaction, which replaces its exact intent slot with the live reservation and returns the exact durable receipt. Any changed snapshot fails without retry. Exactly one lifetime store owner is permitted; another opening process is refused. Never hold an admission mutex across crypto or handler dispatch.

Store admission uses a lifetime-exclusive owner; a second process opening it is refused. Do not hold admission locks across crypto or handler execution; instead capture immutable key/enrollment state and revalidate it in the exact intent and final transactions. Preserve immutable `W` and reject changes. No timestamp startup floor is selected.

Use existing unsigned decimal timestamp domain 0..999999999999 and checked arithmetic. At each authoritative transaction require inclusive `abs(rawNow-ts)<=W`; calculate `retainUntil=checkedAdd(ts,W)`. A signed `ts` outside the domain, checked expiry overflow, or stale final sample is `401 timestamp_out_of_window`; no reservation is made. A raw clock sample outside the domain or below H follows §2: return `503 clock_unsafe` only after the unsafe fence is durably latched, otherwise `503 durability_unavailable`. Expiry is inclusive: retain while `now<=retainUntil`, and treat absent only when `now>retainUntil` after durable H advancement. Replay never extends expiry; live rows are never evicted. The configured `W` MUST be a positive integer seconds value no greater than 120; 30 seconds is the current v1 default. This candidate bound does not change current v1 configuration behavior.

After signature verification, each intent transaction and final reservation transaction stops at the first failure in this order: (1) readiness/fence and captured owner/store generation/W/key/enrollment snapshot (`503 durability_unavailable` if unavailable, `503 state_changed` if changed); (2) fresh raw clock and H (`503 clock_unsafe` only after confirmed durable rollback latch, otherwise `503 durability_unavailable`); (3) fresh inclusive timestamp and checked expiry (`401 timestamp_out_of_window`); (4) authoritative replay/intent lookup (`401 replayed_nonce` for live committed duplicate; `503 durability_unavailable` for unresolved conflicting intent or unavailable lookup); (5) capacity (`503 capacity_exhausted` only after authoritative lookup); (6) durable intent/final commit outcome (unknown is `503 durability_unavailable`, fences, no dispatch/retry). Before signature preserve v1 order, including unknown key, preliminary freshness, signature. A forward-H write must be durably confirmed before using expiry to decide absence. After confirmed intent, repeat the entire order with a fresh raw sample. Any failure needing intent cleanup is reported with its step's status only after cleanup is confirmed; uncertain cleanup/fence becomes unknown `503 durability_unavailable`.

At final conversion, exclude the exact current intent from capacity and atomically replace its reserved slot with the live reservation. A store containing 4096 entries including that intent MUST permit its exact conversion; never double-count it or reject solely for capacity exhaustion. No other intent may be converted. Keep lifetime-exclusive ownership, refuse the second process, and hold no request admission mutex across cryptography or handler execution.

## 3. Durable state and clock high-water

The persistent representation MUST have an exact version-1 metadata schema: `format_version=1`, exact nonempty `deployment_id_utf8`, store identity and store generation, current owner generation, immutable `W`, monotone `H`, dirty-serving epoch, and durable unsafe/unknown/fence state. Deployment identity is the locally provisioned UTF-8 identity defined in §1. Store identity/generation and owner generation are compared exactly on open; a new owner generation is established only by the exclusive owner. Metadata and every record have fixed, typed fields and bounded encodings; the backend representation may be binary, but this contract does not define a universal portable file codec.

A reservation's primary key is exactly `kid_raw || nonce_raw` (32 plus 16 raw bytes, exactly 48 bytes). Its persisted fields MUST reproduce the exact committed receipt in §1, including format/deployment/store generation, exact intent and operation identities, raw key and nonce, `SHA-256(S)`, signature, signed `ts`, checked `retainUntil`, and committed outcome; no reconstructed or normalized receipt is accepted. An intent is keyed by that same raw pair identity, carries the exact §1 intent identity and prepared-operation fields, and atomically reserves one capacity slot. Conversion replaces only that exact intent and slot with its reservation. The expiry index key is exactly `uint64be(retainUntil) || kid_raw || nonce_raw` and its value is empty; primary-row and expiry-index insertion, conversion, purge, and deletion MUST be atomic. Index entries and primary rows MUST agree exactly. Unknown-outcome tombstones preserve the exact terminal operation identity, mean no redelivery, are not ordinary reservations, and MUST NOT expire automatically.

The loader MUST reject absent metadata for an initialized store (never reinterpret it as an empty initialized store), unsupported versions or fields, missing/extra/wrongly typed fields, duplicate encoded fields, trailing bytes, malformed or noncanonical keys, out-of-domain persisted timestamps/expiries or `ts`/`W`/`retainUntil` inconsistency, inconsistent/missing/duplicate expiry-index entries, and any record or aggregate exceeding the configured caps. Enforce the limits in §6 at load and write time, including 4096 combined reservations/intents, 64 unresolved unknown intents/tombstones, and the 16 MiB logical database budget; reject rather than truncate, repair silently, or evict. Raw clock samples outside the timestamp domain are not signed timestamps: they require a durably latched unsafe result (`503 clock_unsafe`), and return `503 durability_unavailable` if that latch cannot be confirmed. By contrast, an authenticated signed `ts` outside the domain or checked `ts+W` expiry overflow is `401 timestamp_out_of_window`.

The selected durable profile requires configured `W` to be a positive integer number of seconds, at most 120; 30 seconds is the current v1 default. This is a candidate profile default, not a claim that current implementations have a durable backend. It is immutable for the store generation.

Every raw sample used for admission or to establish nonce absence by expiry MUST satisfy `rawNow>=H`. Below H, durably latch unsafe across restart and reject; never clamp or clear at catch-up. Before every expiry-based absence decision, durably advance H to the raw sample in an atomic ordered transaction, then expire/purge and reserve; unknown H write fences. Purge is bounded but no absence decision may precede its H receipt. H advancement is not required solely to reject a confirmed live duplicate when no expiry-based absence decision is made. Purge at 216 followed by restart at 215 must fail closed.

Keep a dirty-serving epoch before admission; only clear it after closing and draining authorized handlers and settling operations. Startup uses exclusive owner and bounded reconciliation; unresolved unknown intent absent still requires manual/external gate, never empty reset. A self-consistent older backup cannot be detected by local H alone; independent monotonic evidence or operator recovery is needed.

An empty-store initialization is permitted only by an explicit out-of-band initialization operation for a proven never-used deployment, with metadata durably established before admission. It cannot migrate an old volatile nonce cache. Migration from volatile or other state must either atomically hand off every possibly-live tuple and exact `W/H` while all old owners are stopped/drained, or establish a trusted all-lifetime accepted-timestamp bound `U` and trusted raw time strictly greater than checked `U+W`; unknown historical windows or missing bounds fail closed. For separately authorized `W_new`, preserve every possibly-live tuple with its original checked expiry and historical W, OR prove every accepted historical window `W_j<=W_new`, a trusted all-lifetime timestamp bound U, and trusted raw time strictly greater than checked `U+W_new` before old tuples are absent. Unknown historical windows/timestamps, unbounded history, smaller W than any possible historical window, or overflow fails closed. Waiting, NTP correction, or a current-process floor is not proof.

## 4. Commit outcomes and operation lifecycle

The storage interface MUST expose three non-interchangeable outcomes for exact intent identity. **Confirmed commit:** exact durable reservation receipt. **Definitely not committed:** no reservation committed and, if an intent had committed, confirmed cleanup leaves no unresolved intent. **Unknown:** any other result; no dispatch/retry, durable owner fence, exact identity recovery and terminal no-redelivery. Unknown tombstones do not expire automatically; no external ledger is assumed.

Committed-operation receipt is part of the live nonce reservation and shares its checked expiry. It is retained while `now<=retainUntil` and removed only after `now>retainUntil` is durably established under H; no append-only successful-operation ledger. Unknown no-redelivery tombstones remain outside normal expiry until explicit operator disposition.

Final intent conversion and outcomes follow section 2. Only the final confirmed reservation receipt permits authorization/state mutation/dispatch or successful native response, including read-only `jack.server.key`; response signing/emission failure does not undo the consumed nonce. For unknown final commit, regardless of whether recovery finds the live reservation or finds it absent, persist a terminal no-redelivery tombstone under exact operation identity; never dispatch or retry. If intent creation is unknown, absence of the intent row does not clear the fence: durably preserve unknown/fence or dirty-epoch state before reopening, and if that write is uncertain an external startup gate MUST block every owner pending manual/operator reconciliation. Crash after confirmed intent but before final commit never auto-redelivers; crash after confirmed reservation but before dispatch leaves the pair consumed and never auto-redelivers. Dirty restart reconciliation follows these rules; no external ledger is assumed.

## 5. HTTP failures and client behavior

The following are candidate new authenticated-profile storage errors, deliberately distinct from the existing authentication/authorization/native codes and deliberately generic (no database paths, backend errors, commit ambiguity, or sensitive state):

| HTTP | Code | Meaning and effect |
|---|---|---|
| 503 | `durability_unavailable` | Store unavailable, uncertain commit, recovery/fence active, or durable clock state unavailable. Never dispatch. |
| 503 | `state_changed` | Final owner/generation/W/key/enrollment snapshot differs from the captured snapshot. Never dispatch; no automatic retry. |
| 503 | `clock_unsafe` | Raw clock is invalid, out of domain, or below H and the unsafe fence was durably latched. |
| 503 | `capacity_exhausted` | Live reservations, intents, unknown tombstones, bounded queue, or configured store budget is exhausted after replay lookup. Never evict live or unresolved state; no dispatch. |

A live committed duplicate retains existing `401 replayed_nonce` response signedness: current Go replay rejection has no new nonce-recorded receipt and is unsigned. This candidate does not change its HTTP status/code precedence.

The existing v1 client does not accept unsigned 503 as an authenticated error: its current verifier returns `missing_auth` (or the applicable missing/malformed-auth error), not a trusted HTTP code. Old-client automatic retry behavior is not asserted. Candidate clients MUST NOT trust an unsigned error body or automatically retry an ambiguous failure; issuing a later request with a fresh nonce does not prove the previous operation had no side effects.

Preserve exact current outer auth precedence for requests admitted to authentication. Separately, bounded transport controls may refuse before auth (e.g. body/rate/queue limits); those are pre-admission refusals, not nonce/storage outcomes and cannot claim authenticated errors or nonce consumption. Once a signed request reaches durable admission, section 2 ordering governs and storage errors cannot mask an earlier auth failure.

## 6. Candidate engineering limits and backend direction

These are bounded engineering defaults for implementation/qualification, not product timing restrictions or demonstrated platform guarantees: 4096 combined live reservations plus outstanding intents; 64 authenticated admissions/second; 32 concurrent validations; 64 queued admissions; at most 128 expiry-index removals per purge transaction; 16 MiB logical database-file budget; and 64 unresolved unknown-outcome intents/tombstones. Check capacities atomically before confirming an intent, counting intents in all applicable limits. At capacity reject before dispatch without live-entry eviction. Physical database growth, filesystems, fsync, locking, rollback detection, and power-loss behavior require exact-backend/platform qualification; these numerical caps do not prove a physical disk bound.

The reviewed Go gateway direction is a vetted transactional library, specifically bbolt v1.5.0 as a candidate for later source/dependency/advisory/platform qualification, not a custom journal. The owner explicitly approved Go 1.25 as the floor for the entire Go SDK/CLI module; deployment builds use Go 1.26.10. Neither dependency nor source manifest is changed here. A library's transaction return is not by itself a universal power-loss guarantee. Use ordinary non-retrying transactions, bounded positive owner-lock timeout, dirty startup recovery, exact receipts, and reviewed durability options; do not use a callback-only backend to claim durability. No Rust or TypeScript dependency is selected. No platform is certified here. The adapter must not imply one transaction covers registry files, signer custody, or handler effects.

## 7. Required implementation and acceptance evidence

The future selected profile requires an application-owned durable-backend seam with the above semantic outcomes and a real Go operator-gateway adapter. Acceptance is on the same full source SHA and must include independent Go, Rust, and TypeScript references/runners, cross-language exact accept/reject/status/error-order and nonce-state matrices, MCP end-to-end integration, and security review. Backend acceptance additionally requires dependency provenance/advisories/license/source review, CGO-disabled compatibility, bounded size/work enforcement, crash/fault injection around every intent/final/cleanup/dirty-epoch/clock/purge transition, exclusive-owner/reopen evidence, and per-supported-OS/filesystem sync/lock/recovery qualification. Tests on a healthy filesystem alone do not prove power-loss durability or backup rollback detection.

At minimum discriminate:

- same-key/same-nonce duplicate and different-body collision; concurrent arrivals yield at most one confirmed commit/dispatch; second owner refuses;
- invalid signature performs zero writes; enrollment commits nonce before invite/state mutation; every authenticated refusal after commit consumes it;
- equality at `retainUntil` stays live; only `now=retainUntil+1` after a durable `H` advance expires; replay never extends retention;
- delayed crypto: preliminary `now=100`, `W=30`, final `now=131` refuses without commit/dispatch;
- owner/generation/`W`/active-key/enrollment change between precheck and final transaction refuses without retry;
- definite abort does not dispatch/consume after confirmed cleanup; unknown final commit fences and never dispatches/retries, with found and absent reconciliation both terminal no-redelivery; unknown intent creation absent remains manually fenced;
- crash after confirmed reservation but before handler dispatch leaves nonce consumed and no auto-redispatch; crash after intent but before final commit never auto-redispatches;
- persist/purge at `H=216`, then raw time 215 on restart: fail closed before absence; clock latch persists at catch-up;
- capacity includes outstanding intents and unknown tombstones; refuse without evicting live rows; `W` changes, missing/corrupt store, lost backup/history and unsupported migration fail closed;
- status/error precedence: pre-authentication failures retain current order; new generic 503s do not disclose backend detail; unsigned 503 cannot be trusted or trigger an old client's automatic retry.

No executable acceptance, platform guarantee, dependency migration, or current SDK support is claimed by this candidate document.
