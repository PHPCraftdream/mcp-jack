# Signed-stream executable contract

Normative wire rules are [`../../spec/05-signed-streams.md`](../../spec/05-signed-streams.md); authentication/refusals are [`../../spec/01-authentication.md`](../../spec/01-authentication.md); modern metadata/mirrors are [`../../spec/04-modern-profile.md`](../../spec/04-modern-profile.md) S4/S5/S6 and `spec/tests/modern/CASES.md`. [`../stream-scenarios.json`](../stream-scenarios.json) is the source of the active and deferred oracles. This is the executable contract and current status, not passing SDK evidence. Active `matrices.stream` has exactly fifteen cases. `matrices.staged` is still empty and keeps its staging semantics; lifecycle matrices `rotation-stream` (one row, all platforms) and `durable-stream` (two rows, Linux-only) are runnable matrices: the self-test exercises them against the fakes and CI hard-gates them against the real executables of all nine client/server pairs. The default `--list`/default run still shows exactly the active fifteen; `--matrix rotation-stream`/`--matrix durable-stream` run their own rows and never change the default pool. The fakes self-test exercises the active scenarios. Do not overstate implementation. No scenario execution is asserted here.

## Driver commands and process protocol

Node >=20, built-ins only:

```sh
node interop/stream.mjs [--matrix stream|rotation-stream|durable-stream] [--targets <file>] [--servers <l,l,...>] [--clients <l,l,...>] [--scenario <id[,id...]>] [--include-staged|--staged-only] [--list] [--self-test]
node interop/stream.mjs --list
node interop/stream.mjs --self-test
node interop/stream.mjs
node interop/stream.mjs --matrix rotation-stream
node interop/stream.mjs --matrix durable-stream
node interop/stream.mjs --servers go --clients go --scenario progress-final
```

Omitted matrix means `stream`; omitted language selections mean all languages in targets. `--scenario` selects comma-separated IDs. `--list` prints the selected pool (active by default; `--include-staged` appends staged rows, `--staged-only` prints only them) and exits 0; when the staged pool is empty, `--include-staged` adds nothing and `--staged-only` prints the usage error `no scenario is staged for matrix stream` and exits 2; deferred rows are never included. `--list` with `--self-test` is a usage error. The lifecycle matrices are runnable staged matrices: `--list` prints their rows and exits 0; the default fifteen-row pool and its list output never change. `--matrix durable-stream` off Linux prints `SKIP matrix=durable-stream: durable replay is a Linux-only matrix (host <platform>)` and exits 0 (before target resolution); on Linux it runs like any matrix. Exit codes are unchanged: 0 pass/skip, 1 scenario failure, 2 usage/harness error. Staged-pool flags remain stream-only.

For each selected client/server/scenario, the driver creates temporary fixture state, fixed clock and request log; starts the server on loopback, verifies its ready identity against pinned fixture `svc`, and starts the client. Relay cases interpose the relay and provide its actual port. Only owned children are terminated. `stream_options` become matching `--<hyphenated-option>` flags when applicable; `idleTimeoutMs` maps to `--idle-timeout-ms`. Both roles receive `--profile modern`.

### Server argv and stdout

The selected server target argv is followed by:

```text
--profile modern --matrix NAME --scenario ID --aud AUD --state PATH --server-seed-hex HEX --clock-file PATH --request-log PATH --port 0
[--frame-max-bytes N] [--max-concurrent-streams N] [--max-stream-duration-ms N] [--heartbeat-ms N] [--idle-timeout-ms N]
[--ring-seed ring-1=HEX --successor-activation UNIX_SECONDS --rotation-store PATH]
[--durable-dir PATH]
```

`AUD` is `https://svc.example.test` from `spec/fixtures/registry.json`; state is version 1 `{version:1,keys:registry.keys,invites:[]}` and server seed is fixture `svc`. Server binds `127.0.0.1`; port 0 chooses an available port. Its first nonblank stdout JSONL line is `{"ready":true,"port":N,"server_public_key":"B64U","server_kid":"kid"}` and public key/kid must equal fixture `svc`. Stderr is diagnostic. Request-log output is append-only JSONL with one event object per line, flushed at lifecycle evidence boundaries. Rotation rows add `--ring-seed ring-1=<successor seed hex> --successor-activation A --rotation-store PATH`; durable rows add `--durable-dir PATH` and, before first start, the same server argv plus the bare flag `--durable-init` (no value), which must print exactly `{"durable_initialized":true}`, exit 0, and create the store (the fake creates `committed-nonces.json`) without starting the HTTP listener.

Server stdin control JSONL when used: rotation announcement input `{ "op":"announce", "reference":"ring-1", "kid":"<successor kid>" }` and reply `{announced:true,ordinal:1,head_ordinal:1,published_at:P,activates_at:A,head_hash:<string>}`; controlled duration input `{action:"clock_advanced",clock:T,start:P,duration_ms:D}` and acknowledgement `{control:"clock_advanced",clock:T}`; held stream release input `{action:"release"}` and acknowledgement `{control:"released",sid:<held stream sid>}`. Rotation rows must also write a `rotation_announced` request-log event carrying `reference`, successor `kid`, `published_at: P`, `activates_at: A` and `head_hash` before replying to the announce control. Rotation rows also use the release control while the old stream is held after its first two messages: after the driver advances the shared clock to A it sends `{action:"release"}`; the server then acknowledges `{control:"released",sid:<held sid>}` and either ends the stream with a signed end frame (the relay replaces it) or without one (the relay injects the predecessor-signed cutoff frame in its place, completing the response on the chunked terminator without waiting for socket end). EOF cleanly stops server (exit 0); signals are cleanup, not lifecycle evidence.

### Client argv and stdout

Base client invocation:

```text
--profile modern --matrix NAME --scenario ID --url URL --aud AUD --clock-file PATH --server-public-key B64U --seed-hex HEX --request-log PATH --nonce B64U --sid B64U --request-body-json JSON --jack-accept s1 --modern-version 2026-07-28 --mirror-headers-json JSON
[--action cancel|hold|once] [--frame-max-bytes N] [--max-concurrent-streams N] [--max-stream-duration-ms N] [--heartbeat-ms N] [--idle-timeout-ms N]
[--successor-activation UNIX_SECONDS --rotation-store PATH] [--durable-dir PATH] [--known-server-key kid=<kid>,public=<b64url>,activation=<UNIX_SECONDS>]...
```

`--url` is a bare origin (`http://127.0.0.1:PORT`); the signed and sent request target is always `/mcp`. For `opt-in-required`, empty `--jack-accept` omits streaming opt-in; otherwise it is `s1`. Alice fixture signs; `svc` is the pinned verifier key. `--mirror-headers-json` is an ordered array of name/value pairs. One JSON object per newline-terminated stdout line; no chatter on stdout. Each delivered MCP message is recorded before exactly one terminal record. `hold` retains a stream after first message; `cancel` closes after first notification; `once` denotes independent refusal request. `--known-server-key` is repeatable and declares a successor server identity: before the entry's `activation` only the pinned predecessor `--server-public-key` verifies opens, frames and signed responses; at/after the activation that entry is the ONLY acceptable verifier for new streams. A stream opened under the predecessor identity that receives a frame with `ts` >= activation must end `stream_after_cutoff` with `failure_frame.ts >= activation` evidence (spec 05 4.3 order: window check, then cutoff, then signature — the harness advances the shared clock to A before the injected frame is processed, so it passes the window check too); a stream opened under the successor identity verifies frames under that successor key. Cutoff rejection applies only to predecessor-identity streams.

Message record fields are `type:"message"`, `scenario`, `stream_index`, `request_method`, `request_target`, `request_body_b64u`, ordered `request_headers`, `request_sig`, `request_ts`, `nonce`, signed `open`, verified `frames`, exact signed UTF-8 `data`, and parsed `message`. Example:

```json
{"type":"message","scenario":"progress-final","stream_index":0,"request_method":"POST","request_target":"/mcp","request_body_b64u":"<canonical-base64url-raw-body>","request_headers":[["Jack-Auth","v1 kid=<alice-kid>,ts=1800000000,nonce=<nonce>,sig=<request-signature>"],["Content-Length","<byte-length>"]],"request_sig":"<request-signature>","request_ts":1800000000,"nonce":"<nonce>","open":{"sid":"<sid>","kid":"<svc-kid>","ts":1800000000,"sig":"<open-signature>"},"frames":[{"kind":"message","sid":"<sid>","kid":"<svc-kid>","seq":0,"ts":1800000000,"data":"{\"jsonrpc\":\"2.0\",\"method\":\"notifications/progress\",\"params\":{\"progress\":1}}","sig":"<frame-signature>"}],"data":"{\"jsonrpc\":\"2.0\",\"method\":\"notifications/progress\",\"params\":{\"progress\":1}}","message":{"jsonrpc":"2.0","method":"notifications/progress","params":{"progress":1}}}
```

Exactly one terminal record follows delivered messages. Terminal records carry the applicable schema fields; inapplicable values are null or omitted, and `frames` is an array when present. Stream terminal records with `outcome:"complete"` or `outcome:"error"` require a non-null signed `open`, a 64-byte `request_sig`, and a `frames` array (including an empty array when no frames were verified). Example complete terminal:

```json
{"type":"terminal","scenario":"progress-final","outcome":"complete","code":null,"http_status":null,"http_code":null,"frames_verified":3,"request_id":1,"mcp_complete":true,"terminal_frame":{"kind":"end","sig":"<end-signature>"},"request_sig":"<request-signature>","v1_evidence":null,"open":{"sid":"<sid>","kid":"<svc-kid>","ts":1800000000,"sig":"<open-signature>"},"frames":[{"kind":"message","sid":"<sid>","kid":"<svc-kid>","seq":0,"ts":1800000000,"data":"<signed-message-data>","sig":"<frame-signature>"},{"kind":"end","sid":"<sid>","kid":"<svc-kid>","seq":1,"ts":1800000000,"data":"","sig":"<end-signature>"}],"failure_frame":null,"successor_activation":null}
```

Stream error uses the same fields, `outcome:"error"`, non-null code, open and request signature, and every verified frame. Example relay truncation has `code:"stream_truncated"`, `frames_verified:2` if two messages verified, `mcp_complete:false`, null terminal frame and no end in frames. A separately evidenced failure frame follows the corresponding protocol definition.

Refusal is a separate model: `outcome:"refused"`; `mcp_complete:false`; `request_sig` is required and must be a 64-byte signature. It is not a stream: `open` is null or omitted, `frames` is empty or omitted, and `terminal_frame`, `failure_frame`, and `successor_activation` are null or omitted. A signed refusal requires non-null `v1_evidence`, independently verified against the request signature and pinned server key; the signature binds HTTP status and exact raw response body. HTTP 501 has the bare envelope `{"error":{"code":"streaming_unsupported","message":"..."}}`; HTTP 429 has JSON-RPC `{"jsonrpc":"2.0","id":<request_id>,"error":{"code":-32603,"message":"stream_limit_exceeded"}}`. The 429 id must match the request, and its semantic `http_code`/terminal code is `error.message`; the 501 semantic code is `error.code`. The only permitted unsigned refusal is HTTP 401 `replayed_nonce`, with `v1_evidence:null`; `http_status` and `code` or `http_code` identify that exact status/code, and when `http_body_b64u` is present it must contain the exact raw JSON response body identifying `replayed_nonce`. Exact request evidence remains on its message record. Refusals return no stream evidence messages. Rotation terminals may carry `successor_activation: A` on both invocations; refusal terminals for durable replay are unsigned 401 `replayed_nonce` with `v1_evidence:null`. `complete` and `error` require non-null open/request_sig and frame arrays. No undocumented keys are defined. Driver compares `{messages:[parsed delivered message objects],terminal:<terminal>}` as recursive expected subsets, with arrays exact length/order.

## Modern requests and cryptographic evidence

Each POST body is `{jsonrpc:"2.0",id:request_id,method:request_method,params:{...request_params,_meta:{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{},"io.modelcontextprotocol/clientInfo":{"name":"mcp-jack-interop-stream-client","version":"1.0.0"}}}}`; `_meta` is inside params. Mirrors include protocol version and `Mcp-Method`; `Mcp-Name` only applies where S6 has a `params.name`/`params.uri` source and is byte-equal. `subscriptions/listen` has no `Mcp-Name` and carries `params.notifications:["notifications/events/list_changed"]` to opt in. No active row defines annotated arguments. S4 requires equal well-formed version mirror and `_meta`; S5 requires method mirror; S6 forbids an unsourced name mirror. Mirrors are unsigned; exact body is signed.

Request signature input is eight LF-separated UTF-8 fields, no trailing LF: `mcp-jack/v1/request`, method, exact origin-form target, audience, Alice kid, decimal Unix seconds, canonical unpadded base64url 16-byte nonce, canonical base64url SHA-256 of exact body bytes. Jack-Auth contains the actual signature. V1 response input is `mcp-jack/v1/response\n<status>\n<request-sig>\n<server-kid>\n<ts>\n<base64url(SHA-256(exact raw body bytes))>`; signed refusal evidence binds status, bytes and signature. Stream open input: `mcp-jack/stream1/open\n200\n<request-sig>\n<kid>\n<ts>\n<sid>`. Frame input: `mcp-jack/stream1/frame\n<sid>\n<seq>\n<ts>\n<prev>\n<base64url(SHA-256(UTF8(data)))>`. Sequence begins at 0 and prev is open signature then previous frame signature. End has empty data and is verified. `mcp_complete:true` only if verified end follows matching JSON-RPC final response (same id, jsonrpc 2.0, exactly result or error, no method). Notification-last does not complete MCP.

Driver clock defaults to 1800000000. Duration control advances by ceil(durationMs/1000); idle uses a fixed shared clock and waits for idleTimeoutMs. Scenario nonce/sid are fixed 16-byte base64url test inputs. The concurrency second request derives its nonce and sid from the first 16 SHA-256 bytes of UTF-8 `<original>\nsecond`; it receives signed HTTP 429 before any stream bytes, after which the first stream is released and required to complete.

## Request log and producer obligations

Authenticated log events expose at least `request_verified:true`, `request_sig`, method, exact body, params including `_meta`, nonce, protocol-version and method mirror, `mirror_name` null/absent as appropriate, and projected mirror fields. Cancellation evidence uses `handler_cancelled`/`request_cancelled`; duration evidence orders `clock_changed` then `duration_elapsed` or equivalent observed change; heartbeat evidence identifies grant. `frame_suppressed` with `data_bytes` and `frame_max_bytes` is required evidence for the active `oversize` scenario, whose signed signal must advertise the configured `frameMaxBytes`. These are evidence requirements for relevant behavior, not claims about inactive/deferred scenarios.

Active producer behavior: `progress-final` emits progress, matching response and signed end. Active `list-changed` is producer `subscriptions-listen`: acknowledges first, emits only opted-in events/list_changed, then matching response and end. `events-stream` emits active, event, heartbeat, terminated, end; no final response. `cancel` blocks after first notification until client close and handler cancellation evidence. `max-duration` is an `events/stream` request (name `demo`, id 7): the handler writes one progress notification and then holds; the driver writes the advanced clock file and sends the `clock_advanced` control line; the SERVER SDK duration timer (spec 05 3.4 and 6.3) then writes the final `events/stream` response `{"jsonrpc":"2.0","id":7,"result":{"resultType":"complete","_meta":{"io.modelcontextprotocol/subscriptionId":7}}}` and the signed end (the application must not write that final itself). The SDK timer may fire before the control line is read, so the executable logs `clock_changed` when it reads the control line and logs `duration_elapsed` only after it has logged `clock_changed` AND observed the handler cancellation, in that order. `opt-in-required` without `s1` gives signed v1 501 `streaming_unsupported`. Active relay cases: `relay-drop` drops seq 1; `relay-edit-data` changes a UTF-8 data byte without resigning; `relay-truncate` removes signed end. Staged producer behavior: `relay-reorder`, `relay-splice`, and `relay-replay` transform decoded chunked HTTP framing and must fail the sequence/signature oracle; `oversize` suppresses the too-large message and final then signs the canonical `stream_frame_too_large` signal; `idle` holds the connection open with the shared clock frozen and emits no frames; `concurrency-limit` holds the first stream, rejects the distinct second signed request before stream bytes, then completes the first on release. These are active fake-harness checks, not claims that active binaries pass. The harness verifies both refusal body shapes for active scenarios.

## Active and deferred oracle

Exactly these fifteen IDs are in the default active matrix, in order: `progress-final`, `list-changed`, `events-stream`, `cancel`, `opt-in-required`, `max-duration`, `relay-drop`, `relay-edit-data`, `relay-truncate`, `relay-reorder`, `relay-splice`, `relay-replay`, `oversize`, `idle`, `concurrency-limit`. With an empty staged pool, `--include-staged` is a no-op and `--staged-only` is a usage error (exit 2); `--scenario` validates IDs against the selected pool. Default `--list` and default run show only the active fifteen; list flags follow the same pool selection. `list-changed` has id `list-changed`, request method `subscriptions/listen`, producer `subscriptions-listen`, request id 3, opt-in notification filter, unique nonce/sid, acknowledged/list_changed/final messages, and complete end.

`deferred` now holds empty pools for `stream`, `rotation-stream` and `durable-stream`; nothing is hidden from listing. Both lifecycle matrices run against the real executables in the CI job `stream interop matrix (3x3)` as hard gates (nine client/server pairs; rotation one row, durable two rows). The rotation row does not require the server to honour the fixture sid (the driver uses the observed sid) or to write the old stream's end frame (the relay injects the cutoff frame with or without an end frame). SDK notes for the executables (verified by reading the sources): Go's `client/stream` has no deterministic SID source, so the Go client ignores the driver `--sid` and records the server's sid; the server-side rotation and durable stores of the Go and Rust SDKs are Linux-only, so both lifecycle matrices are Linux matrices in practice; the Rust stream client verifies through `StreamVerifier` directly and selects the key by activation (the transport pins one key); the TypeScript client selects the key through its per-request `resolveKey` hook. Partial durable raw replay does not establish durable lifecycle success. Active self-tests exercise fake harness behavior only; fakes are not SDK evidence.

## Rotation-stream matrix

`rotation-stream` has exactly one row, `rotation-cutoff-reopen`, and runs on all platforms. The fixture is `erin` (`ring-1`); the shared clock starts at publish `P=1767052810` and successor activation `A=1767225610`.

| Stage | Orchestration and evidence |
| --- | --- |
| Server and announce | Start with `--ring-seed ring-1=<successor seed hex> --successor-activation A --rotation-store PATH`. Send `{op:"announce",reference:"ring-1",kid:<erin kid>}`; validate `{announced:true,ordinal:1,head_ordinal:1,published_at:P,activates_at:A,head_hash}` and a `rotation_announced` request-log row. |
| Old stream cutoff | Relay transform `after-cutoff` STREAMS each decoded event live, so the client verifies progress and final under clock P while the server holds before its end. The driver then advances the shared clock file to A, sends `{action:"release"}` and awaits `{control:"released",sid}`; the relay replaces the server's end frame with a predecessor-signed frame — the frame is injected whether or not the server writes an end frame (a server whose clock jumped past A may refuse to sign the old stream's end and simply end or abort the response; the relay then injects the same frame, bound to `seq` = last forwarded frame seq + 1 and `prev` = the last forwarded frame signature or the open signature) — bound to the live chain — `seq` = the replaced end frame's sequence, `prev` = the previous frame's signature (the open signature when the end is seq 0), `ts` exactly A, signature computed AFTER `seq`/`prev` are fixed — so the frame passes the window check at clock A and the client must end `stream_after_cutoff` with `failure_frame.ts >= A`. |
| Reopen | The SECOND invocation goes directly against the server (never through the cutoff relay) with nonce and SID derived as the first 16 SHA-256 bytes of `<original>\nreopen` and `--known-server-key kid=<erin kid>,public=<erin public>,activation=A`; it verifies only under Erin (`open.kid === erin kid` on every message record) and completes with `frames_verified:3`, `mcp_complete:true`, and a signed end. |

The oracle compares `expected.old` and `expected.reopened` as recursive subsets, with exact arrays. Exit 0 requires both; request logs must contain `rotation_announced` and `request_verified` rows for both nonces.

The old stream's sid is the OBSERVED sid: the driver requires every old-stream message record to carry the same canonical 16-byte base64url `open.sid` and uses that sid for matching the `{control:"released",sid}` acknowledgement. A real SDK server may generate its own sid and need not honour the fixture `--sid`. Fake-only deviating variants (never evidence about real executables): `JACK_STREAM_FAKE_ROTATION_NO_END=clean` releases the held old stream without writing an end frame and ends the response cleanly; `JACK_STREAM_FAKE_ROTATION_NO_END=abort` releases it by closing the socket; `JACK_STREAM_FAKE_RANDOM_SID=1` makes the server derive its own sid for the held old rotation stream before the open is signed, so the open header, every frame signature input and the release acknowledgement all carry that observed sid, which the reopen invocation does not use; `JACK_STREAM_FAKE_ROTATION_NO_END=keepalive` releases it with a clean chunked terminator while the client pins `Connection: keep-alive`, so the relay must finish on the terminator rather than on socket end; `JACK_STREAM_FAKE_ROTATION_BAD_RELEASE_SID=1` makes the acknowledgement report a sid different from the observed one (negative control runs against the normal fixture-sid stream). The driver does not chain-verify the injected cutoff frame's signature (cutoff evidence is exempt from the failure-frame chain check); it asserts only the `stream_after_cutoff` terminal and `failure_frame.ts >= A`.

## Durable-stream matrix (Linux-only)

Off Linux, `--matrix durable-stream` prints `SKIP matrix=durable-stream: durable replay is a Linux-only matrix (host <platform>)`, exits 0, and skips before target resolution. On Linux the matrix has `durable-live-replay` and `durable-restart-replay`.

Initialize the store out-of-band using the server argv plus `--durable-dir PATH` plus the bare flag `--durable-init` (no value), requiring exact stdout `{"durable_initialized":true}`, exit 0, and store creation. Reuse that `--durable-dir` for both server roles. For `durable-live-replay`, the first client opens with `--action hold`; for `durable-restart-replay`, it streams to completion. Capture the byte-identical signed request from the first message record: `request_method`, `request_target`, `request_body_b64u`, ordered `request_headers`, `request_sig`, and `nonce`. Replay it raw over a fresh connection while the first stream is still open (live), or after a clean stdin-EOF server stop (exit 0) and restart on the same store (restart). The fake client's message records carry `nonce`, which the driver verifies against the captured Jack-Auth. In the live row the first client is held and is RELEASED through the stdin release control after the replay; its then-completing records are verified for integrity but the scenario terminal remains the driver-synthesized unsigned 401 refusal.

Only accepted replay answer: unsigned HTTP 401 `replayed_nonce` refusal (`v1_evidence:null`), the only permitted unsigned refusal. The request log must prove `nonce_committed` (`nonce_committed_before_first_byte:true`) strictly before `stream_open`, and `replayed_nonce` strictly after `stream_open`, for the same `request_sig` and `nonce`. Oracles follow the scenario rows: live `messages` contains the first stream's delivered progress `{progress:1,message:"stream:first"}`; restart `messages` is empty; both terminals are refused 401.

## Limits, API boundaries and targets

Defaults: frameMaxBytes 1048576 data-value bytes (minimum 1024), maxConcurrentStreams 4 per identity, maxStreamDurationMs 3600000, heartbeat default 15000ms for verification window W=30 seconds and grant <= floor(W*500), idleTimeoutMs 90000. These options are not all active scenarios. Cancellation uses Go context, Rust request extension/framework mechanism, TS AbortSignal in `JackStreamContext`; no common extension API is implied. APIs are language-specific: Go `Transport.OpenStream`/`client/stream`, `HandlerConfig.Streams`/`StreamFromContext`; Rust `SigningTransport.open_stream`/`open_stream_as`, `StreamLayer`; TS `openSignedStream`, `JackStreamContext`. Do not imply Go deterministic SID hook exists.

Targets: Go `interop/bin/go-stream-server` and `interop/bin/go-stream-client`; Rust `interop/rust/target/release/interop-server --mode stream-server` and `interop-client --mode stream-client`; TypeScript `node ts/dist/interop/stream/server.js` and `node ts/dist/interop/stream/client.js`. These are output paths, not claims binaries exist. Future Go source paths `interop/go/streamserver`, `interop/go/streamclient` and TS sources `ts/src/interop/stream/server.ts`, `client.ts` are absent; Rust uses the interop crate modes. Build plans (not executed):
